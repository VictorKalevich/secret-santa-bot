Вторая версия, 2026-11-14. Основа — полный обзор кода `main` на коммите `24b85d3` (после фичи 015): серверный код
прочитан целиком, часть выводов проверена запуском (замеры жеребьёвки, число запросов на действие, одновременные
вызовы, сборка wrangler). Что изменилось относительно первой версии — в конце файла.

Этот файл — оглавление и правила. Подробности каждого шага — в отдельном файле `docs/refactoring/step-N-….md`:
его достаточно, чтобы выполнить шаг в новой сессии и на другой модели.

## Ограничения (обязательны для каждого шага)

- Поведение и дизайн не меняются. Исключения перечислены поимённо в разделе «Исправления внутри шагов»; всё
  остальное, что меняет поведение, — в разделе «Решения владельца» и в шаги не входит.
- Тесты остаются зелёными: `npm test` перед каждым коммитом, `npm run test:e2e` перед слиянием шага.
- Правила `CLAUDE.md` и Конституции действуют полностью: тайна, дизайн-система, слова, лимиты бесплатного тарифа,
  без рантайм-зависимостей и без сборщика.
- Жеребьёвка не становится медленнее — см. раздел «Жеребьёвка».
- В базе живые данные. Ни один шаг не меняет схему и не требует миграции.

## Порядок работы над шагом

1. Прочитать этот файл, файл шага и `refactoring/baseline.md`. Рабочее дерево чистое, ветка `main`, свежая.
2. Сверить номера строк из файла шага с кодом: они верны для коммита `24b85d3`. Если предыдущие шаги их
   сдвинули — искать по именам функций.
3. Снять замеры «до»: `npm test`; для шагов 2, 4, 5 — замер жеребьёвки; после шага 1 — число запросов.
4. `/speckit-specify` с текстом из конца файла шага → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`.
   Без `/speckit-clarify`: спецификации заполняются самостоятельно, спорное — в раздел допущений.
   - В `spec.md` требования — это инварианты («ответы, тексты, коды те же»), критерии успеха — раздел «Приёмка».
   - В `plan.md` — проверка по всем семи принципам Конституции. Для этих шагов главные: I (тайна), V (лимиты
     бесплатного тарифа), VI (проверено до выката), VII (владелец ⊇ админ).
   - В `tasks.md` — отдельная задача на README и `CLAUDE.md`.
5. Одна логическая единица на коммит, перед каждым — `npm test`.
6. Перед слиянием: `npm run test:e2e`, замеры «после», сравнение с базовыми.
7. Обновить: таблицу фич в `CLAUDE.md`, статус шага в таблице выше, `refactoring/baseline.md` (если числа
   изменились), память проекта.
8. Слияние в `main` и отправка на сервер — после зелёных тестов.

Остановиться и спросить владельца, если: тест показывает изменение поведения, которого нет в файле шага; приёмка
не выполняется; оказалось, что нужно менять схему базы или Конституцию (кроме шага 7).

Если шаг не помещается в одну сессию — закончить на зелёных тестах, закоммитить и продолжить в новой сессии с
`tasks.md` фичи.

## Что показал обзор

### Высокий приоритет

1. **Два действия портят данные при одновременном вызове** (воспроизведено, `baseline.md`, раздел 4).
   - Двойной перенос участия, когда новый аккаунт уже участник события: участие нового аккаунта пропадает вместе
     с письмом (`src/roles.js:165`, действие ничего не захватывает).
   - Выход админа из участия одновременно с жеребьёвкой: в парах остаётся человек, которого нет в событии
     (`src/api.js:525–535` — без условия «жеребьёвки не было», которое есть у штатного удаления).
   → шаг 3.
2. **Тайну, права и атомарность проверяет только e2e — 194 секунды, перед выкатом.** Проверки гонок в e2e не
   навязывают чередование и проходят, даже если запросы выполнились по очереди. Автотест «владелец ⊇ админ»
   пропускает два действия с «_» в имени и не проверяет право владельца на сброс. «Нет пар в ответе» проверяется
   по именам ключей. → шаг 1.
3. **Каскады данных написаны руками в пяти местах** (`src/events.js:82`, `:106`; `src/pairs.js:215`;
   `src/api.js:528`; `src/roles.js:137`). Внешних ключей нет. Оба дефекта из пункта 1 — следствие расхождения
   этих мест. → шаг 3.
4. **Права размазаны по `switch` на 470 строк** (`src/api.js:283–752`, 46 действий): проверка владельца — внутри
   веток, список разрешённого в завершённом событии — в стороне, предметная логика с SQL — там же. → шаг 4.

### Средний приоритет

5. **Повторные чтения.** Настройки читаются 2–3 раза на вызов, список пользователей — 2 раза; `admin.state` — 15
   запросов, `admin.remove` — 16, `admin.draw` — 14 при лимите 50. Тексты писем читаются там, где нужен признак
   или число, в том числе в запросе жеребьёвки. → шаг 4.
6. **Свой захват узнаётся пятью способами**, часть — по метке времени. Из 27 проверок одновременных вызовов 16
   дают один результат, 11 — дубль или порчу данных: 5 исправляют шаги 3 и 5, 6 — действия вовсе без захвата.
   Условия склеиваются из строк с незакрытыми скобками (`src/support.js:44–46`). → шаг 5.
7. **`src/app.html` — один скрипт на 1845 строк**, `renderAdmin` — 653 строки. Проверить правку можно только
   статическими тестами и скриншотами; iOS локально не проверить. → шаг 6.
8. **Актуальный контракт API собирается из девяти файлов**, `admin.ring` не описан нигде; `CLAUDE.md`, README и
   Конституция в нескольких местах расходятся с кодом. → шаг 7.
9. **Запас по CPU жеребьёвки.** Холодный вызов на 200 человек — 5,6–5,9 мс от сети и 9–12 мс от батареи при
   лимите 10 мс. Есть проверенная правка: −40% при том же результате. → шаг 2 (выполнен: 3,5 мс на 200 человек).

### Низкий приоритет

10. Снимок исключений не различает перестановку партнёров (`src/pairs.js:78`); окно гонки — миллисекунды. → шаг 5.
11. `src/db.js` смешивает схему, запросы и предметные правила; предикаты состояния события живут в
    `src/events.js`, который импортируют семь модулей. Циклов импорта сейчас нет. → шаг 4.
12. Рассылки без захвата (объявление, напоминания, сброс, роли, приглашение из события): двойной вызов — двойная
    рассылка. → «Решения владельца».
13. Полный просмотр таблицы `messages` при каждом открытии приложения. → «Решения владельца».
14. Мелочи — раздел ниже.

### Что проверено и в порядке

- `db.batch()` считается одним запросом в лимите 50 на вызов (документация Cloudflare D1, Limits).
- Тяжёлые действия укладываются в лимит: самое тяжёлое — `admin.draw`, около 40 запросов из 50 вместе с отправкой
  очереди.
- Надёжные захваты: жеребьёвка, раскрытие, завершение, удаление события, обе отмены, удаление и вписывание после
  жеребьёвки, заявки, обращения двумя админами, ссылка владельца.
- `events.id` объявлен `AUTOINCREMENT`: номер удалённого события не переиспользуется, его журнал не всплывёт в
  новом событии.
- Циклов импорта между модулями нет.
- `npm test` (61 тест) и `npm run test:e2e` (8 сценариев, 61 подтест) зелёные на `24b85d3`.
- `diagnose` в `src/draw.js` в обычном случае стоит O(n): `some` останавливается на первом подходящем.

получает существующий отказ. Они включены в шаги; владелец может исключить любую.

| 3 | Выход админа из участия одновременно с жеребьёвкой не оставляет человека в парах |
| 3 | Двойное удаление участника до жеребьёвки — одно уведомление и одна запись журнала |

## Что не трогаем

- Алгоритм `src/draw.js`: порядок попыток, бюджет шагов, порядок вызовов `rng`. Шаг 2 меняет только способ
  заполнения матрицы и перестановку в `shuffle`; результат при том же зерне обязан совпасть.
- `src/outbox.js`, `src/budget.js` — очередь и счётчик запросов.
- Смысл SQL-захватов. Меняется способ сборки и, в шаге 5, признак «свой захват» там, где это метка времени.
- Схему базы и файлы миграций.
- Тексты для людей: ни одного слова.

## Жеребьёвка: что записать в каждую спецификацию

- После шага 1 требование «результат при том же зерне не меняется» проверяет тест с эталонными результатами
  (`tests/draw-golden.test.mjs`). Эталон не пересоздаётся ни в одном шаге этого плана.
- Сохраняются оптимизации 015: матрица допустимости на `Uint8Array`, `range` простым циклом, `pairRules` на
  `Map<число, Set>` без строковых ключей, общий бюджет попыток в `planDraw`; и шага 2 (017): перестановка в `shuffle`
  без деструктуризации, матрица из `fillMatrix` правил `pairRules` (правила передаются в `findAssignment` напрямую,
  без обёртки).
- Шаги 4 и 5 трогают `checkDraw` и `runDraw` в `src/pairs.js` — чтение данных и запись результата, не поиск.
  `checkDraw` не получает дополнительных запросов и проходов по данным.
- Замер «до и после» обязателен для шагов 2, 4, 5: `planDraw` на 50, 100, 150 и 200 человек, холодный и
  прогретый вызов, медианы, на одной машине и в одном режиме питания. Критерий — ни одна медиана не выросла
  больше, чем разброс между двумя прогонами «до». Проверки `< 10 мс` в `tests/draw.test.mjs` для этого слишком
  грубые.
- «Быстрая попытка» (случайные круги до построения матрицы) в план не входит: она меняет пары при том же зерне.

## Решения владельца

Это изменения поведения или эксплуатации. В шаги не входят; каждое — отдельное решение.

**Проверить до ближайшего выката.** В резервной копии от 2026-11-13 18:01 нет таблицы `fixed_pairs`, в копии от
14:32 нет и таблиц обращений: миграции применялись в течение дня. Код требует версию схемы 11
(`src/db.js:6`). Перед выкатом — `npx wrangler d1 migrations list secret-santa-db --remote`.

**Данные и безопасность.**

- Резервные копии базы (`backup-2026-11-13-1432.sql`, `backup-2026-11-13-1801.sql`) лежат в папке проекта
  открытым текстом: пары, письма, адреса. В git не попадают, но хранить их стоит в другом месте.
- Заголовок `Content-Security-Policy` для `/app` — сейчас его нет (`src/index.js:65–69`). Нужна проверка на iOS и
  в веб-клиенте Telegram.
- Служебный просмотр: слово «ОТКРЫТЬ» проверяет только приложение, API `admin.vault.*` его не требует
  (`src/api.js:733–742`) — в отличие от `СБРОС`, `УДАЛИТЬ`, `ОТМЕНА`. Доступ всё равно только у владельца, каждое
  открытие пишется в журнал.

**Поведение.**

- Переносить ли при переносе участия ссылки «кто сделал». Сейчас после переноса админа его записи журнала
  подписаны «кто-то», объявления — «Организатор».
- Рассылки без защиты от двойного вызова: объявление, напоминания, полный сброс, назначение админа, передача
  владения, приглашение из события. Защита означает отказ второму вызову.
- Двойное сохранение новой семьи: второй вызов получает 500 «Ошибка сервера» вместо понятного отказа.
- `admin.rename` не пишет журнал, хотя `CLAUDE.md` обещает запись на каждое действие админа.
- Недочёты интерфейса — список в `refactoring/step-6-app-split.md`.

**Производительность.**

- Индекс для непрочитанных сообщений: при каждом открытии приложения просматривается вся таблица `messages`.
  Нужна миграция (без потери данных); имеет смысл, когда сообщений станут тысячи.
- «Быстрая попытка» жеребьёвки для групп больше 200 человек — меняет пары при том же зерне. Замеры и идея — в
  памяти проекта.

## Что изменилось относительно первой версии

- **Шаг 1** теперь не «тесты уровня модулей», а запуск всего Worker в одном процессе. Прототип работает на
  текущем коде: 46 действий за 96 мс. Добавлены эталон жеребьёвки, навязанное чередование одновременных вызовов
  и исправление автотеста прав.
- **Новый шаг 2** — ускорение жеребьёвки. В первой версии `src/draw.js` стоял в «не трогаем»; замер показал, что
  две трети холодного времени — перестановка через деструктуризацию и `n²` вызовов функции правил, и обе правки
  не меняют результат (6000 случаев, 0 расхождений).
- **Данные события и человека**: к общему риску добавлены три воспроизведённых дефекта, один — с потерей данных.
- **Таблица действий**: записан точный порядок проверок, который нужно сохранить (владелец проверяется после
  «событие завершено»), и три механизма «разрешено в завершённом».
- **Чтения**: вместо оценки «2–4 лишних запроса» — измеренная таблица по 46 действиям; добавлены чтение писем
  ради признака и объединение чтений в `batch`.
- **Захваты**: вместо «худший исход — дубль уведомления» — таблица из 27 проверок; предложен приём «условие по
  прежнему состоянию» вместо метки времени.
- **Снимок жеребьёвки**: риск понижен со среднего до низкого.
- **`app.html`**: вопрос о расширении частей закрыт сборкой — `.js` под правилом `Text` не работает; дана карта
  из восьми частей с номерами строк и контрольная сумма.
- **Мелочи**: «Событие завершено больше недели назад…» — это четыре разных текста, объединять их нельзя; в первой
  версии они числились дублями.
- **Новый шаг 7** — документы: расхождения контрактов, `CLAUDE.md`, README и Конституции с кодом.
- Исправлены неточности: `renderAdmin` занимает строки 781–1433; мест вызова API в приложении 60, а не 64;
  `diagnose` и прежняя оценка числа запросов уточнены замерами.
