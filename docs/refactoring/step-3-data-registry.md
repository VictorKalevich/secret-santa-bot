# Шаг 3. Один список данных события и человека

Фича Spec Kit: следующий свободный номер (ожидается `018`), короткое имя `data-registry`.
Нужен шаг 1 (быстрые тесты). Сначала прочитай `docs/refactoring-roadmap.md`.

## Цель

Какие таблицы хранят данные события и человека, записано в одном месте. Удаление события, сброс, удаление
участника, выход админа из участия и перенос участия строятся из этого списка. Тест падает, если в схеме
появилась колонка с событием или человеком, которой в списке нет.

Заодно закрываются три дефекта одновременных вызовов в этих же действиях.

## Зачем

Внешних ключей в схеме нет (0 вхождений `REFERENCES` в `migrations/`): все каскады написаны руками в пяти местах.

| Действие | Где | Особенности |
|---|---|---|
| Удаление события | `deleteEvent`, `src/events.js:82–103` | Журнал события остаётся; операторы — пока событие существует |
| Полный сброс | `resetEvent`, `src/events.js:106–134` | Владелец остаётся участником, его письмо и адрес стираются |
| Удаление участника | `removeMember`, `src/pairs.js:215–252` | Условие — версия пар или «жеребьёвки не было» |
| Выход админа из участия | `admin.participate`, `src/api.js:528–535` | Свои операторы, без условия |
| Перенос участия | `transferAccount`, `src/roles.js:137–219` | Без условия; старая запись человека удаляется |

Фичи 012 и 014 правили каждое из этих мест (комментарии `// 012`, `// 014`). Пропуск одного оставляет исключения,
закреплённые пары или обращения человека, который потом вернётся в событие.

Что уже разошлось:

1. **Выход админа из участия не защищён от одновременной жеребьёвки.** `removeMember` ставит всем операторам
   условие «жеребьёвка не проведена» (`src/pairs.js:160`), а `admin.participate` проверяет `ev.draw_done` только
   по прочитанному раньше событию (`src/api.js:525`). Если жеребьёвка записалась между чтением и удалением, в
   парах остаётся человек, которого нет в событии. Воспроизведено: `atomic.mjs`, строка «жеребьёвка пишет первой».
2. **Двойной перенос участия теряет данные.** `transferAccount` ничего не захватывает. Если новый аккаунт уже
   участник того же события, второй вызов повторяет `DELETE FROM members … user_id = новый` (`src/roles.js:165`)
   и удаляет участие, только что перенесённое первым вызовом, вместе с письмом. Воспроизведено: 8 участников → 6
   вместо 7.
3. **Двойное удаление участника до жеребьёвки** даёт два уведомления и две записи журнала: условие «жеребьёвки не
   было» верно для обоих вызовов (`src/pairs.js:244–245`).
4. **Перенос не трогает ссылки «кто сделал»**: `audit.actor`, `announcements.author`, `events.created_by`,
   `families.created_by`, `join_requests.decided_by`, `removed_members.removed_by`, `support_threads.closed_by`.
   После переноса админа его записи журнала подписаны «кто-то» (`src/db.js:299`), объявления — «Организатор»
   (`src/db.js:313`). Менять ли это — решение владельца; в этом шаге поведение сохраняется.

## Что сделать

1. **Список** в `src/db.js`: для каждой таблицы — колонка события и колонки человека с ролью («участник» или «кто
   сделал»). Колонки «кто сделал» в списке есть, но операции их пока не трогают.
2. **Построители операторов** из списка, каждый принимает условие `guard` с параметрами, как `enqueueIfStmt`:
   - удалить данные события;
   - удалить данные участника в событии;
   - перенести человека на другой аккаунт.
   Отличия действий задаются параметрами построителя, а не отдельными списками таблиц. `supportDeleteStmts` и
   `supportTransferStmts` (`src/db.js:333–358`) становятся частью построителей.
3. **Пять мест** вызывают построители. Тексты сообщений, записи журнала и ответы API не меняются.
4. **Тест схемы**: применить миграции, прочитать `PRAGMA table_info` всех таблиц; колонка с именем `event_id`,
   `user_id`, `tg_id`, `chat_id` или из перечня выше обязана быть в списке, и наоборот — каждая колонка списка
   существует в схеме.
5. **Дефект 1**: выход админа из участия идёт через построитель «удалить данные участника» с условием
   «жеребьёвка не проведена». Если удаление не выполнилось — тот же отказ, что и при проверке до записи:
   «После жеребьёвки так нельзя. Попроси владельца бота вписать тебя.»
6. **Дефект 2**: все операторы переноса получают условие «старая запись ещё существует»
   (`EXISTS (SELECT 1 FROM users WHERE tg_id = старый)`), удаление старой записи стоит последним — тот же приём,
   что в `deleteEvent`. Проигравший вызов получает существующий отказ «Старая запись не найдена.»
7. **Дефект 3**: уведомление удалённому и запись журнала при удалении до жеребьёвки выполняются, только если
   участник ещё в событии, и стоят в `batch` раньше удаления строки участника.

## Чего не делать

- Не менять схему и миграции. Внешние ключи не добавлять.
- Не переносить ссылки «кто сделал» при переносе участия.
- Не менять перестройку пар (`applyPairsChange`, `removeFromAssignment`) и версии пар (`pairsVersion`).
- Не добавлять захват в сброс, объявления, напоминания, роли — это решения владельца.

## Подводные камни

- `removeMember` находит оператор удаления участника по номеру в массиве (`removeAt`, `src/pairs.js:241`,
  `src/pairs.js:247`), `deleteEvent` — последний оператор (`src/events.js:101`). При перестройке `batch` не потерять, по
  какому оператору определяется исход.
- В переносе порядок операторов важен: сначала `UPDATE OR IGNORE` (перенос без конфликтов), потом `DELETE`
  остатков (`src/roles.js:184–198`).
- Сброс стирает письмо и адрес оставшегося владельца отдельными операторами (`src/events.js:116`, `:125`).
- Образец события копирует исключения, но не закреплённые пары (`src/events.js:37–40`) — это не каскад и в
  список не входит, но тест на это уже есть в e2e (`tests/e2e.test.mjs:1906–1927`).
- `outbox.chat_id` при переносе не меняется намеренно: сообщение старому аккаунту должно уйти старому аккаунту
  (`src/roles.js:210`).

## Приёмка

- Три теста с пометкой `todo` шага 3 (`tests/atomic.test.mjs`) зелёные без пометки.
- Тест схемы зелёный; проверка «от противного»: временная колонка `event_id` в тестовой базе роняет его.
- Остальные тесты шага 1 зелёные без правок ожиданий. `npm run test:e2e` зелёный без правок.
- Число запросов на действие (`tests/queries.test.mjs`) не выросло.
- Новый тест: после удаления события, сброса, удаления участника и переноса в базе не остаётся строк с этим
  событием или человеком, кроме описанных в таблице «что делает сейчас».
- В `src/` нет ни одного `DELETE FROM` или `UPDATE … SET user_id` по таблицам списка вне построителей и вне
  перестройки пар (проверить поиском).
- `CLAUDE.md` (структура, жёсткие правила), спецификации затронутых фич и план отмечены.
