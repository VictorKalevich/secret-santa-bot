# Шаг 6. `app.html` по частям

Фича Spec Kit: следующий свободный номер (ожидается `021`), короткое имя `app-parts`.
Нужен шаг 1. Сначала прочитай `docs/refactoring-roadmap.md`.

## Цель

Мини-приложение лежит в нескольких файлах по областям, а Worker отдаёт страницу, побайтно равную нынешней.
Код внутри частей не меняется.

## Зачем

`src/app.html` — 1872 строки, 127 062 байта, один `<script>` с одной функцией-обёрткой (строки 25–1869): 75
объявлений верхнего уровня, 60 мест вызова API, 59 действий. `renderAdmin` (строки 781–1433) — 653 строки, 40%
файла. Любая правка интерфейса идёт в одном файле; автопроверки — статические (дизайн-система, слова) и
скриншоты. Телефон владельца — iPhone, iOS локально не проверить: единственный способ не сломать его —
побайтное равенство страницы.

## Что уже проверено

- **Расширение частей.** Проверено сборкой `wrangler deploy --dry-run` (wrangler 4.160.1):
  - `.html` — текст, по существующему правилу `wrangler.toml:24–27`;
  - `.txt` — текст, по правилу wrangler по умолчанию (подходит имя вида `02-core.js.txt`);
  - своё расширение с добавлением в правило `Text` — текст;
  - **`.js` под правилом `Text` — не текст**: wrangler собирает такой файл как модуль. Части с расширением `.js`
    делать нельзя.
  Во всех рабочих вариантах файл попадает в сборку побайтно.
- **Контрольная сумма** `src/app.html` на коммите `24b85d3`: SHA-256
  `440b0db84c32e7dab6a4407854796ed2685aa5e83b43d6f614975b716b5f32ff`; только LF, без BOM, один завершающий перевод
  строки. `.gitattributes` задаёт `* text=auto eol=lf`.
- **Швы.** Разрез возможен только между объявлениями верхнего уровня. Перед каждым заголовком раздела
  `// ----------` стоит пустая строка: она закрывает предыдущую часть.

## Предлагаемые части

Склейка частей по порядку без разделителей равна исходнику. Номера строк — для коммита `24b85d3`; если
`src/app.html` с тех пор менялся, сверь по заголовкам разделов.

| № | Строки | Содержание |

| 2 | 26–217 | `'use strict'`, Telegram и подпись, `h`, `ui`, `api`, тост, подтверждение, `busy`, `bindToggle`, форматы, сравнение писем |

Заголовки разделов стоят в строках 36, 174, 218, 297, 514, 586, 674, 735, 780, 1435, 1514, 1546, 1577, 1664, 1840.

Где область разорвана и чистого разреза без перестановки кода нет — оставить как есть:

- навигация (`goHome`, `openEvent`, `syncBack`, строки 298–345) лежит под заголовком главного экрана;
- шторка (1546–1575) нужна всем экранам, но стоит в конце файла;
- `chatButton` и `finishedNotice` (564–584) общие, а лежат в разделе события;
- журнал (1514–1544) вызывается с главного экрана и из админки;
- внутри `renderAdmin` шва нет: блоки связаны общими локальными переменными (`d`, `s`, `users`, `byId`, `players`,
  `me`, `done`, `drafts`, `refresh`, `again`, `xapi`, `nodes`), `syncFixed` объявлена в строке 1160, а вызывается
  из блока жеребьёвки.

## Что сделать

1. Разрезать `src/app.html` на части в `src/app/` с номерами в именах (`01-…`, `02-…`). Первая и последняя —
   `.html`, части скрипта — `.js.txt` (или всё `.html`; решить в `research.md`, критерий — без правки
   `wrangler.toml`, если возможно).
2. Модуль сборки `src/app-page.js`: импортирует части по порядку и экспортирует их склейку. `src/index.js:3`
   импортирует склейку оттуда; вставка стилей (`src/index.js:17`) остаётся как есть — заменой через функцию.
3. Перевести тесты на собранный текст:
   - `tests/design-system.test.mjs:9` читает `src/app.html`; проверки `:40–46`, `:48–62`, `:87–91`, `:117–123`
     должны получать склейку. Иначе часть упадёт, а часть молча перестанет проверять скрипт.
   - `tests/wording.test.mjs:16–19` читает `src/*.js` без подпапок и `src/app.html`; проверка «＋» (`:31–35`) —
     только `src/app.html`. Обе должны получать склейку.
   - Склейку тесты берут импортом `src/app-page.js` через перехватчик из шага 1 (он уже понимает `.html`, `.css`,
     `.txt`), а не собственным списком файлов: порядок частей задан в одном месте.
4. `tests/screenshots.mjs` открывает страницу с работающего Worker — проверить, что работает без правок.
5. Обновить `CLAUDE.md` (структура, жёсткое правило о дизайн-системе: «в `src/app.html`» → «в частях
   приложения»), `design-system/README.md`, если там назван файл.

## Чего не делать

- Не менять ни одного символа внутри частей: никакого форматирования, переименований, перестановки функций.
  Проверки `tests/design-system.test.mjs:87–88`, `:119` привязаны к отступу в два пробела и точному тексту.
- Не делить скрипт на несколько тегов `<script>` и не делать модулей: код держится на общей области видимости,
  подъёме функций и одном `'use strict'`. Зависимости частей циклические (3↔4, 3↔5, 3↔7, 4↔7).
- Не исправлять найденные в интерфейсе недочёты — они перечислены ниже для отдельной фичи.
- Не добавлять сборщик и зависимости.

## Подводные камни

- Порядок частей фиксирован: при загрузке по порядку исполняются объявления `const` и `let` (строки 27–34, 54,
  103, 146, 224–233, 239, 242–243, 345, 1515, 1548–1550, 1690) и вызов `start()` в строке 1868 — он должен
  остаться последним. Блок `try/catch` в `syncBack` (339–343) молча проглотил бы ошибку неверного порядка.
- Редактор не должен менять завершающий перевод строки части. `.editorconfig` и форматтера в проекте нет — не
  добавлять.
- Если части скрипта когда-нибудь будут вставляться заменой плейсхолдера, замену задавать функцией: в скрипте
  54 строки с `${`.
- Перехватчик загрузки в тестах и правило `Text` в wrangler — два разных механизма. Совпадение страницы в
  настоящем Worker проверяется отдельно (см. приёмку).
- `tests/e2e.test.mjs` страницу `/app` не запрашивает; её открывают только скриншоты.

## Приёмка

- Склейка частей побайтно равна файлу до разреза:
  `git show main:src/app.html | sha256sum` и SHA-256 результата `src/app-page.js` совпадают (скрипт проверки —
  в `quickstart.md` фичи). Если `src/app.html` не менялся с `24b85d3`, это сумма из раздела «Что уже проверено».
- Страница настоящего Worker: `npm run dev`, `curl http://127.0.0.1:8787/app` — совпадает побайтно со страницей,
  снятой так же с `main` до разреза.
- Тест из шага 1 «`GET /app` = приложение со вставленными стилями» зелёный.
- `npm test` зелёный; проверки дизайн-системы и слов по-прежнему видят весь скрипт (проверка «от противного»:
  временно добавленный `style=` в части 5 роняет тест).
- `npm run test:e2e` и `npm run screenshots` проходят; снимки совпадают с прежними.
- Владелец открыл приложение на iPhone после выката — формальность при побайтном равенстве, но в отчёте попросить.

## Недочёты интерфейса для отдельной фичи

Найдены при составлении карты файла, поведение меняют — в этот шаг не входят:

- `busy(null, …)` без блокировки кнопки (строки 408, 476, 480, 894, 1117, 1181): двойное нажатие шлёт два запроса.
- Сохранение параметров события (1340–1349) не перерисовывает панель: старое название остаётся в текстах
  подтверждений до следующего обновления.
- В `renderAdmin` строка 1372 берёт `state.evId` вместо захваченного `evId`, строка 1426 — `finished()` вместо `done`.
- Заголовок шторки обращения ставится той шторке, что открыта сейчас (1777–1778); опрос раз в 6 секунд
  (1661, 1751, 1837) проверяет «открыта какая-то шторка», а не «эта».
- `closeSheet` (1572–1574) вызывает асинхронный `onClose` без ожидания; `render` (292) не ловит отказ
  `renderWard` и `renderAdmin` — возможен вечный загрузчик.
- `state.announcements` нет в начальном состоянии (224–228).
- `confirmBox` режет текст до 250 символов (117); худший случай — ровно 250 в строке 1008.
- Поле ответа в `openChat` (1581–1584, 1624–1630) дублирует `composerParts` (1666–1680); блоки исключений
  (1096–1130) и закреплённых пар (1163–1198) — две большие копии.
