# Шаг 5. Захваты и снимки жеребьёвки

Фича Spec Kit: следующий свободный номер (ожидается `020`), короткое имя `claims-snapshots`.
Нужны шаги 1 и 4. Сначала прочитай `docs/refactoring-roadmap.md`.

## Цель

- Атомарное действие «захват + операторы по условию» собирается одним помощником: условие и его параметры
  задаются один раз.
- Признак «захват сделал этот вызов» не зависит от совпадения часов.
- Формулы снимков жеребьёвки лежат в одном модуле парами «JS + SQL» и сверяются тестом.

## Зачем

**Пять способов узнать свой захват:**

| Способ | Где | Надёжность |
|---|---|---|
| Случайный `draw_token` | `runDraw`, `pairsVersion`, отмены — `src/pairs.js:101`, `162`, `323`, `353` | надёжно |
| Случайное число в поле `events.revealed` | `revealAll`, `src/events.js:170` | надёжно |
| `finished_at` и отсутствие записи журнала `finish` | `finishEvent`, `src/events.js:65–66` | надёжно, но инвариант держится на таблице журнала |
| `decided_by` и `decided_at` | `decideRequest`, `src/membership.js:167` | дубль, если один админ дважды в одну миллисекунду |
| Метка времени | `ward.received` (`src/api.js:217`); обращения: `taken_at`, `closed_at`, `created_at` сообщения (`src/support.js:107`, `143`, `237`, `321`, `354`) | дубль при совпадении миллисекунды |

Комментарии в коде сами отмечают, что часы Workers у одновременных запросов совпадают до миллисекунды
(`src/events.js:63`, `169`). Дубль воспроизведён для `ward.received`: два сообщения Санте (`baseline.md`,
раздел 4).

**Условие верно для обоих вызовов.** `admin.exclusion.add` ×2: исключение одно, записей журнала две — условие
журнала «жеребьёвка не проведена» (`src/api.js:589`) не отличает первый вызов от второго.

**Условия склеиваются из строк.** `THREAD` и `MINE_SENT` (`src/support.js:44–46`) — фрагменты с незакрытой
скобкой, закрывает её вызывающий; параметры позиционные. Ошибка в счёте `?` проявится только на том пути, где
сделана.

**Формулы снимков в двух модулях и двух видах:**

| Снимок | JS | SQL |
|---|---|---|
| Участники | `src/pairs.js:77` | `src/pairs.js:107–109` |
| Исключения | `src/pairs.js:78` | `src/pairs.js:110–111` |
| Семьи | `familySnapshot`, `src/db.js:215–227` | `FAMILY_SNAPSHOT_SQL`, `src/db.js:230–232` |
| Закреплённые пары | `fixedSnapshot`, `src/db.js:248–258` | `FIXED_SNAPSHOT_SQL`, `src/db.js:259–260` |

JS-функция семей проверена тестом (`tests/unit.test.mjs:128`), но с SQL-выражением нигде не сверяется;
`fixedSnapshot` не тестируется вовсе.

Снимок исключений `число:Σgiver:Σreceiver` не отличает {А→Б, В→Г} от {А→Г, В→Б}. У закреплённых пар это учтено
слагаемым-произведением (`src/db.js:255`). Чтобы ошибиться, админ должен успеть удалить два исключения и добавить
два других за миллисекунды между расчётом и записью пар — риск низкий.

## Что сделать

1. **Помощник захвата** (место — рядом с `enqueueIfStmt` в `src/db.js` или отдельный модуль): принимает оператор
   захвата и условие «захват мой» с параметрами, отдаёт построители `enqueue`, `audit` и произвольного оператора
   с этим условием и собранный `batch`. Фрагменты SQL — только с закрытыми скобками.
2. **Перевести на помощник** атомарные действия: `runDraw`, `cancelDraw`, `forceCancelDraw`, `applyPairsChange`
   с `pairsVersion`, `revealAll`, `finishEvent`, `deleteEvent`, `decideRequest`, действия обращений
   (`sendFromUser`, `closeByUser`, `take`, `sendFromAdmin`, `pass`, `closeByAdmin`), `ward.received`.
3. **`cancelDraw` и `forceCancelDraw`** (`src/pairs.js:317–376`) совпадают на четыре пятых: общая функция с
   параметрами «условие отмены», «удалять ли переписку», «текст сообщения», «код журнала». Тексты отказов и
   порядок проверок сохранить.
4. **Захваты без метки времени.** Там, где признак — время, перейти на условие по прежнему состоянию: в одном
   `batch` условные операторы стоят **перед** оператором изменения и проверяют состояние, которое это изменение
   отменяет. Второй вызов видит уже изменённое состояние и ничего не рассылает.
   - `ward.received`: сообщение Санте — пока `gift_received_at = 0`, затем отметка.
   - `admin.exclusion.add` и `.del`: запись журнала — пока хотя бы одной строки исключения нет (или она есть —
     для удаления), затем изменение.
   - Обращения (`take`, `pass`, закрытие): уведомления и журнал — по прежнему состоянию обращения, затем захват.
   Исход вызова по-прежнему определяется числом изменённых строк оператора захвата.
5. **Модуль снимков**: четыре снимка, у каждого функция JS и выражение SQL рядом; `checkDraw` и `runDraw` берут
   их оттуда.
6. **Тест паритета**: на случайных данных в тестовой базе JS и SQL дают одну строку — для всех четырёх снимков.
7. **Формула исключений** — добавить слагаемое-произведение, как у закреплённых пар. Это меняет поведение только
   в гонке: вместо записи пар по устаревшим исключениям — «попробуй ещё раз».

## Чего не делать

- Не менять схему. Новые колонки для признаков захвата не добавлять.
- Не менять надёжные захваты (`draw_token`, отметка раскрытия, завершение) — только способ сборки `batch`.
- Не добавлять захваты действиям, у которых их нет (объявления, напоминания, сброс, роли) — решение владельца.
- Не трогать `src/draw.js` и поиск пар.

## Подводные камни

- В `finishEvent` условие рассылки включает отсутствие записи журнала `finish`, и эта запись пишется последней
  (`src/events.js:66`, `73`). Порядок операторов сохранить.
- Числа в формулах снимков должны оставаться меньше 2^53: JS считает в `double`, SQLite — в целых. Идентификатор
  Telegram — до 52 значащих бит, поэтому произведения берутся по модулю (`FIXED_MOD`, `src/db.js:247`).
- `sendFromUser` создаёт обращение отдельным запросом до `batch` и при неудаче записи повторяет один раз
  (`src/support.js:95–103`, `131`). Пустое открытое обращение без сообщений возможно, если вызов оборвался между
  ними, — не чинить здесь, только не ухудшить.
- В `sendFromAdmin` номер оператора вставки зависит от того, берётся ли обращение этим ответом (`at`,
  `src/support.js:290`, `302`).
- Операторы «по прежнему состоянию» работают, потому что `batch` — одна транзакция и транзакции записи идут по
  очереди. Условный оператор, поставленный **после** захвата, прежнего состояния уже не увидит.
- Условие «по прежнему состоянию» обязано повторять все условия оператора захвата. Пример: заявку принимают,
  только пока регистрация открыта (`src/membership.js:170–173`) — то же условие нужно уведомлениям, иначе они
  уйдут при несостоявшемся захвате.
- `checkDraw` не должен получить дополнительных запросов и проходов по данным: снимки считаются по уже
  прочитанным строкам.

## Приёмка

- Два теста с пометкой `todo` шага 5 (`tests/atomic.test.mjs`) зелёные без пометки; добавлены проверки
  `together(…, { sameMoment: true })` для `take`, `pass`, закрытия обращения и `decideRequest`.
- Тест паритета снимков зелёный; проверка «от противного»: перестановка партнёров в исключениях меняет снимок.
- Остальные тесты шагов 1–4 зелёные без правок ожиданий. `npm run test:e2e` зелёный без правок.
- Число запросов на действие не выросло; `npm run bench:draw` — без ухудшения; эталон жеребьёвки не пересоздан.
- В `src/` нет фрагментов SQL с незакрытой скобкой (`THREAD`, `MINE_SENT` заменены).
- `CLAUDE.md` и спецификации отмечены; в спецификации шага формула исключений и захваты без метки времени
  записаны как исправления.
