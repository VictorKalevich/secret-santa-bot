# Компании: план

Запрос владельца (2026-11-23): «обёртка» над ботом — список компаний (семей, коллективов), который ведёт владелец бота.
Все уже зарегистрированные люди переходят в одну компанию и ничего не замечают. У компании может быть свой владелец с
нынешними правами владельца. Человек из нескольких компаний видит их список и даёт каждой своё название. Владелец бота
может зайти в любую компанию.

Этот файл — вход для того, кто реализует: что решено, в каком порядке делать, где риск. Подробности — в спецификациях
шагов. После выполнения обоих шагов файл удаляется (история — в git и в `specs/`), как план рефакторинга.

## Модель

```text
владелец бота (settings.owner_id) — один; владелец в любой компании
└── компания (companies): название владельца бота, назначенный владелец (0 — ведёт владелец бота)
    ├── люди компании (company_members): администратор?, своё название компании
    ├── события (events.company_id) → участники, письма, пары, переписка, обращения — как сейчас
    ├── семьи (families.company_id) — группы «не дарят друг другу», 008
    └── общий журнал (audit.company_id, event_id = 0)
человек (users) — один на бот: имя, уведомления, режим ответа в чате
```

- **Слова.** Новая сущность — «компания». «Семья» остаётся тем, что она значит с 008.
- **Роли.** Владелец бота ⊇ владелец компании ⊇ администратор компании ⊇ участник. Владелец компании получает всё, что
  сегодня может владелец, в пределах своей компании — включая служебный просмотр пар. Только владельцу бота остаются:
  компании (создать, назвать, удалить, назначить владельца), перенос участия на новый аккаунт, передача прав владельца
  бота, страница `/setup`.
- **Кто видит оболочку.** Экран «Компании» видит тот, у кого их две и больше, и владелец бота (у него с одной компанией —
  раздел внизу главного экрана). Остальным слово «компания» не показывается.
- **Главный приём реализации.** Контекст вызова привязан к компании (`ctx.in(companyId)`): `users()`, `ownerId()`,
  `isOwner()`, `me.is_admin` означают «в этой компании». Модули почти не меняются; непривязанный контекст на этих методах
  падает — пропущенное место ловят тесты.

## Что улучшено относительно запроса

1. **Два шага вместо одного** — самое опасное (миграция, границы) проверяется прежними тестами без правки эталонов и
   выкатывается отдельно, с безопасным откатом.
2. **Одноразовая ссылка владельца компании.** В новой компании людей ещё нет, выбрать владельца «из компании» не из
   кого. Ссылка `own_…` решает это: владелец бота создаёт компанию, отправляет ссылку — человек регистрируется и
   становится владельцем.
3. **Название по умолчанию и подсказка.** Пока человек не дал компании своё название, она показана как «Компания 1»,
   «Компания 2» с подписью «Владелец — Аня · событий: 2» — чтобы было понятно, где что.
4. **Владелец бота в чужой компании — «гость».** Он всё может, но не получает рассылок её организаторам и не появляется
   в её списках; его изменения видны в журнале компании под его именем. В README об этом честно сказано.
5. **Тексты.** В компании с назначенным владельцем бот говорит «владелец», а не «владелец бота» — иначе люди искали бы
   незнакомого им человека.
6. **Удаление пустой компании** и **журнал бота** — чтобы ошибочно созданная компания не оставалась навсегда, а
   создание, удаление и смена владельцев были записаны.

## Риски

| Риск | Что сделано |
|---|---|
| Утечка между компаниями (администратор одной видит людей, события, пары другой) | Шаг 1: контекст без компании падает; тест-таблица «каждое `admin.*` × чужой администратор»; списки и получатели сообщений проверяются на двух компаниях; чужое событие отвечает как несуществующее |
| Косвенная утечка через правила пар (семьи, прошлые пары другой компании влияют на жеребьёвку или предупреждение обмена) | Семьи и прошлые пары читаются только по компании события; снимок жеребьёвки — тоже; тесты |
| Миграция боевой базы (пересборка `family_members`) | Копия базы перед миграцией; тест миграции на базе с данными (число строк до и после); проверочный запрос после выката |
| Откат | Прежний код работает на схеме 17; общий признак `users.is_admin` поддерживается; сверка `tools/companies-reconcile.sql`. После появления второй компании откат кода — только с восстановлением базы из копии |
| Больше людей видят пары (владелец компании получает служебный просмотр) | Конституция 3.0.0 (шаг 2), журнал каждого открытия, README честно говорит участникам; владелец компании не видит ничего вне своей компании |
| Ссылка владельца компании даёт права тому, кто её открыл | Одноразовая, случайная (80 бит), действует до использования или отзыва; владелец бота получает сообщение, кто её использовал; запись в журнал; захват через `atomic` — из двух одновременных переходов права получает один |
| Перенос участия и переименование действуют на человека во всех компаниях | Перенос — только владелец бота; организатор не переименовывает человека, состоящего ещё где-то |
| Лимиты бесплатного тарифа | Роли и компании читаются в первом пакете вызова; таблица базовых чисел запросов не меняется |
| Объём: шаг 1 трогает ~14 модулей | Модули переводятся по одному, после каждого — зелёные тесты; эталоны запрещено править |

## Решения, принятые без владельца

**Утверждены владельцем 2026-11-23** («просмотрел, устраивают») — переспрашивать не нужно, реализовать как записано.

Спецификации заполнялись без уточняющих вопросов (правило владельца), поэтому решения были вынесены сюда на просмотр.

1. **Владелец компании видит пары своей компании** (служебный просмотр, закреплённые пары, вписывание, обмен,
   принудительная отмена). Основание: «существующий функционал владельца переходит на владельца семьи». Альтернатива —
   оставить всё, что касается пар, только владельцу бота.
2. **Владелец бота может всё в любой компании, включая служебный просмотр**, и не виден в её списках («гость»).
   Альтернатива — показывать его среди организаторов или запретить ему служебный просмотр в чужих компаниях.
3. **Имя человека одно во всех компаниях.** Альтернатива — своё имя в каждой компании (заметно дороже).
4. **Перенос участия на новый аккаунт — только владелец бота**, владелец компании просит его.
5. **Название «Основная»** у первой компании (видит только владелец бота, можно переименовать).
6. **Удалить можно только компанию без событий.**
7. **Передача прав владельца бота** переезжает из списка администраторов в раздел «Компании»; кнопка 👑 в списке
   администраторов теперь значит «сделать владельцем этой компании».

## Вне рамок

- Перевод события или человека из компании в компанию; объединение компаний.
- Лимиты на число компаний, оплата, самостоятельное создание компаний не владельцем бота.
- Удаление человека из компании целиком (сегодня человека из бота тоже не удалить).
- Свои имена людей в разных компаниях.
