# Research: Тексты — из словаря (060)

Замеры 2026-11-25 по `main` (`31ddb06`): строк с кириллицей вне комментариев — около 1300: приложение ≈ 650
(`06-admin` 211, `05-event` 148, `03-home` 78, `07-vault-audit` 70, `04-companies` 62, `08-sheet-chat` 57, `02-core` 24,
разметка 8), сервер ≈ 650 (`bot.js` 79, `pairs.js` 59, `events.js` 47, `api.js` 43, `support.js` 42, `looks.js` 38,
`companies.js` 34, `membership.js` 33, `roles.js` 32, `db.js` 29, `setup.js` 20, `participant.js` 18, `format.js` 15, …),
скрипт поля с крестиком `design-system/clearable-input.js.txt` — 1 (`aria-label`).

## R1. Где лежат словари и какого они вида

**Decision**: `src/i18n/<язык>/server.js` и `src/i18n/<язык>/app.js` — ES-модули `export default { 'ключ': значение }`,
плоские ключи с точками. Значение — строка с подстановками `{имя}`, набор форм числа `{ one, few, many, other }` или
список строк (месяцы, дни недели). Ключ начинается с области: на сервере — имя модуля (`pairs.drawDone` — текст
`src/pairs.js`), общие — `common.*`; в приложении — `app.<часть>.*` (`app.admin.drawConfirm` — текст `06-admin`),
набор до ответа сервера — `app.boot.*`. `src/i18n/index.js` — список языков и функции (R2). Ключ один на весь язык
(сервер и приложение не пересекаются); сервер может брать и ключи `app.*` (тексты, которые совпадают в API, боте и
приложении, — 034).

**Rationale**: модули JS — без сборщика (Wrangler собирает импорты), с комментариями и многострочными значениями; два
файла на язык — ровно граница «что уходит приложению»; в шаге 2 переводится файл целиком (22 файла на 11 языков, а не
сотни). Префикс области = место в коде — ключ находится поиском.

**Alternatives considered**: JSON — без комментариев и с экранированием; файл на модуль (≈ 35 на язык, 385 в шаге 2) —
много файлов при той же работе на новый текст; один файл на язык — приложению пришлось бы вычленять свои ключи по
префиксу при каждом запуске; ICU MessageFormat — нужен разборщик и на сервере, и в приложении, а формы числа целыми
строками проще и прозрачнее.

## R2. Как код берёт текст

**Decision**: `t(lang, key, params)` — строка на языке `lang`: значение по ключу (нет у языка — русское; нет и там —
сам ключ и `console.error('i18n: …')`), подстановки `{имя}` из `params` (нет подстановки или лишняя — `console.error`,
текст собирается как есть), набор форм — по `new Intl.PluralRules(lang).select(params.n)`, нет формы — `other`. В коде:
`ctx.t(key, params)` — язык вызывающего (контекст знает человека, R3); помощники без контекста получают переводчик
`t` параметром. `tl(lang, key)` — список (месяцы).

**Rationale**: модули и так получают `ctx` первым параметром — язык приходит без новых параметров; ошибка в словаре не
роняет вызов у людей, а в тестах `console.error('i18n: …')` — падение (R10).

**Alternatives considered**: глобальный «текущий язык» — неверен для сообщений другим людям и для одновременных
вызовов; исключение на нехватку ключа — у людей 500 вместо текста.

## R3. Язык вызывающего и язык получателя

**Decision**: колонка `users.lang` (миграция `0021_user_lang.sql`, `TEXT NOT NULL DEFAULT ''`, схема 21). `langOf(user)`
— `user.lang`, если такой язык есть в списке, иначе `DEFAULT_LANG = 'ru'`. Контекст вызова (`openContext`,
`makeContext`) знает `ctx.lang = langOf(me)` (строка пользователя уже читается `SELECT *` первым пакетом — запросов не
прибавляется), привязанный контекст наследует. Без человека (cron, `/setup`, отказ «не удалось проверить вход») —
русский. Шаг 2 расширит только `langOf` (язык Telegram) и выбор языка.

**Rationale**: без хранимого языка не проверить, что сообщение собирается на языке получателя (US3); колонка с пустым
значением ничего не меняет для людей, прежний код с ней работает (миграция до выката).

**Alternatives considered**: язык в шаге 1 только «по умолчанию» и подмена модуля в тестах — проверка не покрыла бы
очередь (язык получателя читает SQL); язык у события или комнаты — отвергнут владельцем ранее (язык у человека).

## R4. Сообщения в очереди — на языке получателя при отправке

**Decision**: в `outbox.payload` вместо готового текста — отложенный текст: `tx(key, params)` → `{ "$t": key, "$p":
params }`, где значение подстановки — строка, число или снова отложенный текст; дата — `tdate(iso)` → `{ "$d": iso }`
(и `tdate(ms, offset)` → `{ "$d": ms, "$o": offset }`); склейка частей — `tjoin(sep, parts)` → `{ "$j": parts, "$s":
sep }`. Кнопки — тоже `tx(...)` в `text`. `flushOutbox` берёт язык получателя тем же оператором захвата: `RETURNING *,
(SELECT lang FROM users u WHERE u.tg_id = outbox.chat_id) AS lang` (проверено на SQLite 3.53: подзапрос в `RETURNING`
работает, у неизвестного — `NULL`) и перед `sendMessage` собирает `render(payload, langOf({ lang }))`. Готовые строки
(сообщения, поставленные прежней версией) `render` не трогает.

**Rationale**: получателей много (рассылки, админы), язык каждого — в его строке; собирать при постановке значило бы
читать людей ради языка (больше запросов, тест `queries`). При отправке язык читается в том же запросе. Подставляемые
данные людей (название события, имя, текст письма) уже экранированы при постановке — как сейчас.

**Alternatives considered**: колонка языка в `outbox` с подзапросом в `INSERT` — лишняя схема и правка всех
`enqueue…Stmt`; отдельный запрос языков при отправке — +1 запрос на круг.

**Откат**: прежняя версия отправила бы отложенный текст объектом — Telegram ответит 400, сообщение удалится. Окно —
сообщения, поставленные новой версией и ещё не ушедшие (обычно секунды; cron — раз в минуту). Порядок — `quickstart.md`.

## R5. Подробности журнала

**Decision**: подробность записи журнала — тоже отложенный текст (`tx('audit.pairsChanged', { n: 2 })`); `auditStmt` и
`auditIfStmt` собирают его на `DEFAULT_LANG` перед записью — в базе прежний текст («пар изменено: 2»). В шаге 2 —
хранить ключ и собирать при показе: меняются только эти два построителя и чтение журнала.

**Rationale**: тесты читают подробности прямо из базы (`swap`) — формат хранения в шаге 1 прежний (SC-6002); места
вызова в шаге 2 не трогаются.

## R6. Словарь приложения

**Decision**: ответ `me` содержит `lang`, `texts_version` и — если запрос не прислал ту же версию (`texts`) — `texts`:
весь словарь `app.*` языка вызывающего. Приложение передаёт в `me` свою версию (`texts: state.textsVersion`), первый
вызов сеанса получает словарь, повторные (`reloadMe`) — нет. Версия — язык и FNV-1a 32 от JSON словаря (`ru:1a2b3c4d`),
JSON и версия готовятся один раз на экземпляр. До ответа сервера — набор `app.boot.*` (заголовок, «Загрузка…», «Открой
через Telegram», ошибка сети и сервера, «Повторить»…): сервер вставляет его в страницу вместо метки
`/*@boot-texts*/null` (как стили дизайн-системы — `/*@design-system*/`); отпечаток CSP считается по отдаваемой странице
(032) — правило прежнее. Разметка страницы (`01-shell.html`) текстов не содержит — скрипт ставит их первым делом.

**Rationale**: запрос `me` есть всегда при запуске — словарь не добавляет запросов к Worker (лимит 100 тыс. в сутки) и
не меняет CSP (`connect-src 'self'`); приложение получает только свой язык (≈ 40 КБ JSON, сжимается Cloudflare) один
раз за сеанс. В шаге 2 набор `app.boot.*` будет на всех языках (≈ 15 строк × 11), язык до ответа — по Telegram.

**Alternatives considered**: все словари в странице — +≈ 450 КБ при 11 языках на каждое открытие; страница на язык по
адресу (`/app?lang=`) — кнопка меню и прямые ссылки адрес без языка; отдельный файл словаря — лишний запрос к Worker или
статические ресурсы (настройка `assets`, против «без сборщика» нет, но сложнее); словарь в `localStorage` — на iOS
WebView ненадёжен, выигрыш мал.

## R7. Формы числа и даты

**Decision**: формы числа — `Intl.PluralRules(lang)` и на сервере, и в приложении (workerd, Node 22, WebKit iOS 13+ —
есть). Для русского на целых числах категории совпадают с нынешним `plural(n, one, few, many)` (проверено на 0–1000 в
тесте). Месяцы в родительном падеже (`formatDate`, `formatMs`, приложение — даты сообщений и календарь), дни недели
календаря — списки словаря (`common.monthsGen`, `app.core.monthsGen`, `app.core.weekdays`…); время — `toLocaleTimeString`
с локалью словаря (`common.locale`/`app.core.locale` = `ru-RU`).

**Rationale**: `Intl.DateTimeFormat('ru', { month: 'long' })` даёт те же слова, но точность «побайтно» и одинаковость
на сервере и в WebKit проще гарантировать списком; формы числа у 11 языков разные — правила `Intl` готовые.

## R8. Тексты в таблицах и семействах

**Decision**: в таблицах кода хранятся ключи, а не тексты: `ACTIONS` (`finished`, `confirm` — `[ключ слова, ключ
отказа]`, отказ не владельцу), `EVENT_PARAMS` (`beforeDraw`), правила обмена (`SWAP_RULES`), причины отказа жеребьёвки,
`POSTCARDS`/`MASKS` (`title` → ключ по `id`: `looks.card.<id>`, `looks.mask.<id>`), подписи журнала приложения
(`app.vault.audit.<код>`). Конвейер и обработчики собирают `ctx.t(ключ)`. Тексты по коду — семейства: проверка требует
ключ для каждого кода (коды журнала — из `docs/api.md`, открытки и маски — из `POSTCARDS`/`MASKS`, причины и правила —
из своих списков). Слово подтверждения сервер сверяет с `ctx.t(ключ слова)` — на языке вызывающего.

**Rationale**: таблицы остаются одним местом правил (019, 029); язык — только при сборке ответа.

## R9. Проверки словаря

**Decision**: новый тест `tests/i18n.test.mjs`:
1. **Кириллица вне словарей** — модули `src/**/*.js` кроме `src/i18n/`, склейка приложения, `clearable-input.js.txt`:
   вне комментариев (`//`, `/* */`, `<!-- -->`) кириллицы нет; исключения — аргументы `new Error(…)` и `console.*(…)`
   (для разработчика) и явный список с причинами. Место — файл (часть) и строка.
2. **Ключи** — каждый ключ в вызовах `t`/`ctx.t`/`c.t`/`tx` и в полях таблиц есть в словаре; каждый ключ словаря
   встречается в коде строкой или как член семейства; семейство (шаблон `` `looks.card.${id}` ``) объявлено в тесте со
   списком кодов, и у каждого кода есть ключ.
3. **Подстановки** — у вызова с литералом объекта (`{ a, b: x }`) имена = подстановкам текста (у набора форм — объединение,
   `n` обязателен); во время быстрых тестов `t` пишет `console.error('i18n: …')` на нехватку и лишнее — «мир» превращает
   его в исключение (R10).
4. **Формы числа** — у набора форм есть все категории языка для целых 0–1000; для русского итог совпадает с прежним
   `plural`.
5. **Файлы** — у каждого языка списка есть `server.js` и `app.js`; ключи `app.*` — только в `app.js`, остальные — только
   в `server.js`; префикс ключа — известная область; значения непустые.
6. **Одинаковая сборка** — `t` приложения (из склейки) и `t` сервера дают одно и то же на всех ключах `app.*` с
   подобранными подстановками.
7. **Слова** — правила 013/044/059/051 (`wording`) проверяют значения словарей; место нарушения — ключ.
Каждое правило — «от противного».

**Rationale**: (1) — полнота переноса (SC-6001), (2)–(5) — целостность словаря к шагу 2, (6) — одна логика в двух
местах (как паритет снимков 020).

## R10. Псевдоязык и строгость в тестах

**Decision**: «мир» (`tests/support/world.mjs`) по умолчанию строгий: `console.error`, начинающийся с `i18n:`, бросает
исключение (вызов падает с 500 — тест видит). Помощник `pseudoLanguage()` (`tests/support/pseudo.mjs`) добавляет в
`DICTIONARIES` служебный язык `xx`: каждая строка русского словаря транслитерируется в латиницу и берётся в `⟪…⟫`,
подстановки `{имя}` и HTML-теги не меняются, формы числа — по правилам русского (`Intl.PluralRules('xx')` → правила
языка по умолчанию; псевдоязык объявляет `plural: 'ru'`). Тест ставит человеку `users.lang = 'xx'` прямо в базе.
Проверка: сценарий бота и API (регистрация → жеребьёвка → переписка → обращение → раскрытие → завершение, отказы) с
людьми и названиями латиницей — всё, что получает человек `xx` (ответы API, сообщения и кнопки бота ему), не содержит
кириллицы и содержит `⟪`; всё, что получают остальные, не содержит `⟪`. В Chrome (`tests/screenshots.mjs`,
`checkPseudo`) — экраны приложения у человека `xx`: в тексте страницы нет кириллицы.

**Rationale**: статическая проверка (R9.1) ловит текст в коде, псевдоязык — неверный язык (текст вызывающего ушёл
получателю, словарь приложения не того языка) и пропуск при сборке (SC-6003, SC-6005).

## R11. Что из прежних тестов меняется

**Decision**: ожидаемые тексты поведения (эталон отказов, сообщения в сценариях, e2e, Chrome) не меняются. Меняются
только проверки, которые искали текст в исходном коде: `wording` (по словарю), `donate`, `app-companies`, `names`,
`mask`, `app-tweaks`, `looks`, `behavior` (034: совпадение текстов — один ключ), `api-table`/`api-doc` (поля
`finished`/`confirm` — ключи, сверка с документом — через русский словарь), `server-shape` (литерал отказа в модуле →
ключ), `swap` (тексты правил — по ключам), `app-csp` (метка `/*@boot-texts*/`), `world` (страница = склейка с
подстановками). Правило: проверка ищет ключ в коде и текст — в словаре; формулировки ожиданий прежние.

## R12. `/setup`, команды и описание бота

**Decision**: тексты страницы `/setup`, `setMyCommands`, `setMyDescription`, `setMyShortDescription`, подпись кнопки
меню (`🎁 Санта`) — ключи `setup.*`; язык — `DEFAULT_LANG`. В шаге 2 `/setup` поставит команды и описания на каждом
языке (`language_code`).

## R13. Объём и порядок работ

**Decision**: сначала основа (R1–R7, R10) и общие тексты (`format.js`, конвейер `api.js`, `bot.js` — открытие чата),
затем перенос по модулям сервера и частям приложения независимыми задачами (файлы не пересекаются: модуль → свой
раздел `server.js`, часть → свой раздел `app.js`), затем проверки (R9) и адаптация тестов (R11), в конце — псевдоязык,
Chrome и документы. Каждая задача переноса закрывается прогоном `npm test` — эталоны ловят расхождение побайтно.

## R14. Конституция и документы

**Decision**: Конституция 3.2.0 (MINOR): «Безопасность и данные» — хранится язык интерфейса человека (пока пустой —
русский). Принцип II «Весь интерфейс — на русском языке» меняет шаг 2. `CLAUDE.md` — жёсткое правило «тексты для людей —
только в словаре» и структура `src/i18n/`; `docs/api.md` — поля `me` (`lang`, `texts`, `texts_version`, запрос
`texts`) и правило «отказы — на языке вызывающего»; README — миграция `0021` в разделе обновления и строка в описании
данных.
