# Feature Specification: Журнал закреплённых пар — одна запись на одно изменение

**Feature Branch**: `023-fixed-pairs-audit`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Журнал закреплённых пар — одна запись на одно изменение. Сейчас `admin.fixed.add` и
`admin.fixed.del` пишут запись журнала при каждом вызове, даже если ничего не изменилось: двойное нажатие «закрепить»
(одновременно, в т.ч. в одну миллисекунду) — две записи при одной паре; повторное закрепление уже закреплённой пары и
удаление несуществующей — лишние записи; два одновременных закрепления с одним Сантой (или подопечным) — сохраняется
одна пара, а записей две. Нужно: запись `fixed.add`/`fixed.del` появляется, только если пара действительно добавлена
или убрана (как у исключений с фичи 020), через помощник атомарных действий `atomic`; ответы, тексты, схема и число
запросов не меняются. Источник: research R9 фичи 020 и «Решения владельца» плана рефакторинга."

## Контекст

Закреплённые пары (фича 014) — решение владельца бота до жеребьёвки «кто кому дарит». Журнал действий организаторов
видят и админы, поэтому запись о закреплении — без имён: «📌 Пара закреплена» / «✕ Закреплённая пара убрана». Сейчас
запись появляется при каждом вызове, а не при каждом изменении (проверено на текущем коде):

| Что сделал владелец | Пар в событии | Записей журнала сейчас | Должно быть |
|---|---|---|---|
| «Закрепить» дважды одновременно (и в одну миллисекунду) | 1 | 2 | 1 |
| «Закрепить» пару, которая уже закреплена | без изменений | +1 | +0 |
| «Убрать» дважды одновременно | 0 | 2 | 1 |
| «Убрать» пару, которой нет | без изменений | +1 | +0 |
| Одновременно «Аня → Боря» и «Аня → Вера» (один Санта) | 1 | 2 | 1 |

У исключений («кто кому не дарит») та же ошибка исправлена в фиче 020: запись пишется по прежнему состоянию — только
если строка действительно меняется. Закреплённые пары тогда в шаг не вошли (research R9 фичи 020).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Двойное нажатие даёт одну запись (Priority: P1)

Владелец нажимает «Закрепить» (или «Убрать») и, пока ответ не пришёл, нажимает ещё раз — или запрос уходит дважды из-за
сети. Пара закрепляется (убирается) один раз, и в журнале одна запись, как у любого другого действия.

**Why this priority**: это и есть найденный дефект; журнал должен совпадать с тем, что произошло.

**Independent Test**: два одновременных вызова с навязанным чередованием «оба читают, потом пишут» — и в одну
миллисекунду от одного человека; считаются пары и записи журнала.

**Acceptance Scenarios**:

1. **Given** событие до жеребьёвки, пара «Аня → Боря» не закреплена, **When** владелец дважды одновременно закрепляет
   её, **Then** пара одна, запись `fixed.add` одна, оба ответа — успех (как сейчас).
2. **Given** то же, **When** оба вызова приходят в одну миллисекунду, **Then** пара одна, запись одна.
3. **Given** пара «Аня → Боря» закреплена, **When** владелец дважды одновременно убирает её, **Then** пары нет, запись
   `fixed.del` одна, оба ответа — успех.
4. **Given** без кольцевой, **When** владелец дважды одновременно закрепляет взаимную пару «Аня ↔ Боря», **Then** две
   строки пары (в обе стороны), запись одна.

---

### User Story 2 — Вызов без изменений не пишет журнал (Priority: P1)

Владелец закрепляет пару, которая уже закреплена, или убирает пару, которой уже нет (например, вторая вкладка
приложения со старым экраном). Ничего не меняется — и в журнале ничего не появляется.

**Why this priority**: та же причина — запись о том, чего не было, вводит в заблуждение и админов, и владельца.

**Independent Test**: последовательные вызовы на одном событии; журнал до и после.

**Acceptance Scenarios**:

1. **Given** «Аня → Боря» закреплена, **When** владелец снова закрепляет «Аня → Боря», **Then** ответ — успех (как
   сейчас), новых записей журнала нет.
2. **Given** «Аня → Боря» не закреплена, **When** владелец убирает «Аня → Боря», **Then** ответ — успех, новых записей
   нет.
3. **Given** без кольцевой, закреплена «Аня → Боря», **When** владелец закрепляет взаимную «Аня ↔ Боря», **Then**
   добавляется «Боря → Аня», запись одна (изменение было).
4. **Given** закреплена только «Аня → Боря», **When** владелец убирает взаимную «Аня ↔ Боря», **Then** «Аня → Боря»
   убрана, запись одна.

---

### User Story 3 — Одновременные закрепления с одним Сантой или подопечным (Priority: P2)

Владелец с двух устройств одновременно закрепляет «Аня → Боря» и «Аня → Вера» (или «Аня → Боря» и «Вера → Боря»). У
Санты не больше одного закреплённого подопечного, у подопечного — не больше одного Санты, поэтому сохраняется одна пара.
В журнале — одна запись, у сохранённой.

**Why this priority**: случай редкий (нужны два одновременных вызова владельца), но запись без изменения — тот же дефект.

**Independent Test**: два вызова с навязанным чередованием «оба читают, потом пишут».

**Acceptance Scenarios**:

1. **Given** у Ани нет закреплённого подопечного, **When** одновременно закрепляются «Аня → Боря» и «Аня → Вера»,
   **Then** у Ани один закреплённый подопечный, запись `fixed.add` одна.
2. **Given** у Бори нет закреплённого Санты, **When** одновременно закрепляются «Аня → Боря» и «Вера → Боря», **Then**
   у Бори один закреплённый Санта, запись одна.

---

### Edge Cases

- **Жеребьёвка в ту же секунду.** Закрепление после записи жеребьёвки не сохраняется и не пишет журнал (как сейчас),
  ответ — прежний отказ «После жеребьёвки закреплённые пары не меняются…».
- **Ответы при одновременных закреплениях с одним Сантой.** Оба вызова отвечают успехом, как сейчас, хотя сохраняется
  одна пара (экран после обновления показывает, какая). Смена ответа — отдельное решение владельца (запись в плане
  рефакторинга), в эту фичу не входит.
- **Взаимная пара** — одна запись на вызов, если изменилась хотя бы одна из двух сторон; ноль — если не изменилась ни
  одна.
- **Админ** по-прежнему получает 403 на `admin.fixed.*` и журнала не пишет.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-2301**: Запись журнала `fixed.add` появляется, только если вызов действительно закрепил хотя бы одну сторону пары
  (взаимная пара — одна запись на вызов).
- **FR-2302**: Запись `fixed.del` появляется, только если вызов действительно убрал хотя бы одну сторону пары.
- **FR-2303**: Из двух одновременных вызовов (в том числе одного человека в одну миллисекунду) запись пишет только тот,
  чьё изменение сохранено. Признак — состояние пар до записи, а не время и не автор вызова (правило «одно действие — один
  результат», фича 020).
- **FR-2304**: Не меняются: ответы (коды и тексты), проверки перед записью, запрет менять пары после жеребьёвки (в том
  числе для жеребьёвки в ту же секунду), сами пары после вызова, схема базы, число запросов к базе и к Telegram на вызов.
- **FR-2305**: Запись журнала, как и раньше, — без имён и подробностей (её видят админы).
- **FR-2306**: Запись пар и журнала собирается общим помощником атомарных действий проекта, как у исключений; закреплённые
  пары перестают быть исключением из этого правила в описании проекта (`CLAUDE.md`).
- **FR-2307**: Тесты одновременных вызовов дополнены случаями историй 1 и 3, тест сквозного сценария закреплённых пар —
  ожиданием историй 2 (повторное закрепление записи не добавляет); описание журнала в `docs/api.md` — «только при
  изменении».
- **FR-2308**: В «Решения владельца» плана рефакторинга записан прежний ответ «успех» второму из одновременных
  закреплений с одним Сантой (подопечным); заметка о двойной записи `fixed.add` в памяти проекта снята.

### Key Entities

- **Закреплённая пара** — «Санта → подопечный» в событии; у Санты не больше одной, у подопечного не больше одной.
- **Запись журнала** — код (`fixed.add` / `fixed.del`), событие, кто сделал, время; подробностей нет.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-2301**: Двойное «Закрепить» и двойное «Убрать» (одновременно и в одну миллисекунду) — ровно одна запись журнала
  при одном изменении пар; проверяется тестом на 4 случаях.
- **SC-2302**: Повторное закрепление закреплённой пары и удаление отсутствующей — 0 новых записей журнала.
- **SC-2303**: Одновременные закрепления с одним Сантой или с одним подопечным — одна сохранённая пара и одна запись.
- **SC-2304**: Все прочие проверки не изменились и проходят: эталон 1125 отказов, таблица числа запросов (у
  `admin.fixed.add` — 6 запросов к базе, 0 к Telegram), тайна, права, сквозной сценарий (кроме намеренно изменённого
  ожидания числа записей).

## Assumptions

- Кольцевая жеребьёвка, проверки при закреплении (участники события, «уже есть закреплённый подопечный», «Санта уже
  закреплён», «только в одну сторону») и тексты — из фичи 014, не меняются.
- README не меняется: установка, команды и то, как пользоваться ботом, остаются прежними; журнал просто перестаёт
  показывать записи без изменений.
- Конституция не меняется: правило «одно действие — один результат» уже есть в `CLAUDE.md`, фича его выполняет.
