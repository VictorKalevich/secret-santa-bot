# 055. Чтения API по индексам: обычный вызов не читает таблицы целиком

**Feature Branch**: `055-api-indexed-reads`

**Created**: 2026-11-24

**Status**: Draft

**Input**: User description: "Сделать отдельной фичей: бот читает только людей своей компании, свои компании и свои
события — тогда потолок открытого бота поднимется до тысяч людей, а для людей ничего не изменится."

## Контекст

Бесплатный тариф D1 — 5 млн прочитанных строк в сутки на аккаунт; при превышении база до 00:00 UTC не отвечает. Аудит
планов всех запросов, которые выполняет код в тестах (386 разных запросов), нашёл полные просмотры на горячих путях:

- каждый вызов API, сообщение боту и нажатие кнопки читает **все компании** бота (первый пакет контекста);
- экран события, панель организатора и большинство действий в событии читают **всех людей бота** (список людей компании
  строится проходом по всей таблице людей);
- главный экран (`me`) читает **все события** бота, имена владельцев **всех компаний** и просматривает **все обращения**
  (счётчики непрочитанного);
- заявка на вступление, список семей компании, создание своей компании в открытом боте и переход по ссылке владельца
  компании просматривают всю таблицу заявок, семей или компаний;
- если запись владельца бота недействительна (владелец ещё не открыл ссылку `/setup`), поиск владельца бота на каждом
  вызове проходит по всем людям.

В открытом боте люди и компании прибавляются с каждым новым человеком, поэтому расход растёт примерно как квадрат числа
людей: потолок — порядка 400–700 активных людей в сутки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Обычный вызов читает только своё (Priority: P1)

Участник, организатор или владелец компании открывает главный экран, событие, панель, пишет письмо, отвечает в
переписке, пишет боту. Бот читает только его компании, его события, людей компании открытого события и обращения его
событий. Чужие люди, компании и события бота не читаются, сколько бы их ни было.

**Why this priority**: это и есть фича — расход чтений на человека перестаёт зависеть от размера бота.

**Independent Test**: мир открытого бота с «чужой историей» (другие компании с людьми, события с парами, обращения,
заявки, семьи) — каждый запрос вызовов обычных людей (не владельца бота) ищет по индексам; ни один не просматривает
целиком людей, компании, события, участников, пары, обращения, заявки и семьи.

**Acceptance Scenarios**:

1. **Given** в боте много чужих компаний, людей и событий, **When** участник, организатор или владелец компании
   открывает главный экран, **Then** читаются только его компании, события, где он участник, и события компаний, где он
   организатор; имена владельцев — только его компаний; непрочитанное обращений — по индексам.
2. **Given** то же, **When** человек открывает событие, панель или выполняет действие в событии, **Then** люди читаются
   только из его компании (и владелец бота как гость), а не все люди бота.
3. **Given** любой вызов API, сообщение боту или нажатие кнопки, **When** бот открывает контекст вызова, **Then**
   читаются только компании вызывающего; все компании — только когда вызывает владелец бота.
4. **Given** открытый бот, **When** человек отправляет заявку на вступление, организатор открывает «Семьи», человек
   создаёт свою компанию или переходит по ссылке владельца компании, **Then** заявки, семьи и компании ищутся по
   индексам.
5. **Given** запись владельца бота недействительна, **When** вызов ищет владельца бота, **Then** просматриваются только
   администраторы компаний, которые ведёт владелец бота, а не все люди.

### User Story 2 — Поведение прежнее (Priority: P1)

Ответы API, тексты и получатели сообщений, журнал, права и число запросов на действие — те же. Владелец бота видит все
компании и события, как раньше.

**Why this priority**: правка — только про то, как бот читает; любое изменение того, что видят люди, — ошибка.

**Independent Test**: прежние тесты (`npm run test:all`) без изменения ожиданий зелёные; число запросов на каждое
действие сценария `queries` — не больше базового; эталон отказов (`api-refusals`) не меняется.

**Acceptance Scenarios**:

1. **Given** любой сценарий прежних тестов, **When** он выполняется после правки, **Then** ответы, сообщения и журнал те
   же.
2. **Given** владелец бота, **When** он открывает главный экран, «Компании» или общее действие организатора, **Then**
   видит все компании и события, как раньше.

### Edge Cases

- Новые индексы ещё не созданы (код выкачен раньше миграции): бот работает как прежде, только читает больше — код от
  индексов не зависит, порядок «миграция ↔ выкат» и откат безопасны.
- Владелец бота: его вызовы по-прежнему читают все компании (и на главном экране — все события): его экраны показывают
  весь бот, а человек один. У остальных ветка «все компании» не читает ни строки — условие проверяется до чтения.
- Незнакомец открытого бота без компаний: компании не читаются.
- Событие чужой компании (переход по пригласительной ссылке, чужой номер события): компания читается одна, по номеру.
- Редкие действия владельца бота — перенос участия, передача прав владельца бота — по-прежнему просматривают таблицы
  целиком (несколько раз в год, один человек): вне фичи.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Первый пакет контекста вызова читает компании вызывающего через его строки компаний; все компании — только
  если вызывающий — владелец бота по настройке (условие не зависит от строк компаний и проверяется до чтения).
- **FR-002**: Компания, которой нет среди прочитанных, читается одна по номеру (не больше раза на компанию за вызов).
- **FR-003**: Люди компании читаются от строк этой компании (и запись владельца бота как гостя), а не проходом по всем
  людям; порядок и поля — прежние.
- **FR-004**: Главный экран: события — где человек участник и компаний, где он организатор (владельцу бота — все); имена
  владельцев — только его компаний (владельцу бота — всех); счётчики обращений — по индексам.
- **FR-005**: Запасной поиск владельца бота и список администраторов компаний, которые ведёт владелец бота, идут от этих
  компаний.
- **FR-006**: Миграция только с индексами (без строк и без версии схемы — как `0008`, `0017`): компании по владельцу,
  обращения по автору, открытые взятые обращения по ответственному, заявки по событию и человеку, семьи по компании;
  запросы создания компании и перехода по ссылке владельца компании используют индексы (в том числе существующий
  частичный по коду ссылки).
- **FR-007**: Ответы, тексты, получатели сообщений, журнал, права, отказы и число запросов на действие — без изменений.
- **FR-008**: Тест: сценарий открытого бота с чужой историей; все запросы вызовов обычных людей (API, бот, кнопки) —
  `EXPLAIN QUERY PLAN`: полный просмотр допустим только у служебных таблиц (настройки, очередь сообщений) и у ветки
  «все компании владельцу бота»; «от противного»: прежние запросы и база без новых индексов находятся.
- **FR-009**: README, `CLAUDE.md` и контракт контекста компании (`specs/050-company-scope/contracts/company-scope.md`)
  описывают новую миграцию и что читает контекст.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Число строк, которые читает вызов обычного человека, не растёт, когда в бот добавляются чужие люди,
  компании и события (в планах его запросов нет полного просмотра растущих таблиц).
- **SC-002**: Расход чтений API растёт линейно с числом активных людей (порядка тысячи строк в сутки на активного
  человека при размере компании в десятки), а не как квадрат: лимит API — несколько тысяч активных людей в сутки.
- **SC-003**: Все прежние тесты (`npm run test:all`) зелёные без изменения ожиданий; число запросов на действие — не
  больше базового.

## Assumptions

- Владелец бота видит весь бот, его вызовы читают все компании и события — это один человек.
- Перенос участия и передача прав владельца бота читают таблицы целиком — редкие действия одного человека, вне фичи.
- Минутная проверка по-прежнему перебирает пары идущих событий после жеребьёвки (054): ≈ 2 900 строк в сутки на
  человека в таком событии — после 055 это главный ограничитель (порядка 1 500 человек в идущих событиях одновременно).
  Сделать её пропорциональной числу правок — отдельная задача.
- Планы запросов D1 совпадают с планами SQLite в тестах (тот же движок); после выката планы проверяются на базе бота
  (`quickstart.md`).
