# Исследование 055: чтения API по индексам

## Как искали

Прогон всех быстрых тестов с перехватом `prepare` у `node:sqlite` (предзагрузка через `NODE_OPTIONS=--import`): каждый
SQL, подготовленный из `src/`, с местом вызова — 386 разных запросов. Для каждого — `EXPLAIN QUERY PLAN` на базе после
всех миграций. Полный просмотр (`SCAN таблица`, в том числе `SCAN … USING [COVERING] INDEX` — проход по всему индексу)
нашёлся у 56 запросов.

## R1. Что исправляем, а что нет

| Запрос | Где | Как часто | Решение |

## R2. Компании вызывающего — первый пакет

Решение: `companiesQuery(db, userId)` — `UNION` двух веток: компании по строкам `company_members` вызывающего (индекс
`company_members_user` → ключ компании) и все компании, если `?1 != 0 AND ?1 = owner_id` настройки. Условие второй
ветки не зависит от строк компаний — SQLite проверяет его до цикла: на 300 000 компаний «не владелец» — 3 мс, владелец
бота — 200 мс (замер прототипа). Число запросов прежнее: всё в том же первом пакете.

`ctx.companies()` — «компании, которые знает вызывающий»: свои; владельцу бота — все. Если владелец бота найден запасным
поиском (запись в настройках недействительна), первый пакет прочитал только свои — `companies()` дочитывает все одним
запросом (редкий случай). Без вызывающего (cron) — пустой набор без запроса.

Почему «свои» достаточно: компания видна человеку, только если у него есть строка в ней (`visibleCompanies` берёт
порядок из `mine()`); владелец компании — её администратор (I3), участник события — человек её компании (I5). Значит,
`menuCompanyTitles`, `companiesView`, `createView`, «я владелец компании» в меню бота, `setLabel` и удаление своей
компании получают те же ответы.

Компания не из прочитанных — `ctx.company(id)`: одна строка по номеру, не больше раза на компанию за вызов. Её берёт
`ctx.in(id)`. Чтобы вступление по ссылке не стоило лишнего запроса (новичок ещё не человек компании), пакет чтений
принимает `inCompany: id` — строку компании тем же пакетом (как `users`, `settings`); бот читает её вместе с записью
участника. Отвергнуто: оставить все компании в первом пакете (суть фичи), читать все компании лениво только владельцу
бота (+1 запрос в общих действиях владельца — `queries` ниже базового не держит).

## R3. Люди компании

`SELECT u.*, cm.is_admin AS company_admin, 0 AS guest FROM company_members cm JOIN users u … WHERE cm.company_id = ?1`
`UNION ALL` запись владельца бота как гостя (`… NOT EXISTS строки в компании`), `ORDER BY created_at, tg_id`. Поля и
порядок прежние, план — ключ компании в `company_members` → ключ `users`.

## R4. События главного экрана

Не владельцу бота: `UNION` событий, где он участник (`members_user`), и событий компаний, где у него `is_admin = 1`
(`company_members_user` → `events_company`), `ORDER BY created_at DESC, id`. Фильтр в `homeView` прежний (он отбирает
то же самое); владельцу бота — прежний `eventsQuery` (все события). При равном времени создания порядок — по номеру
(раньше — порядок просмотра таблицы, то есть тоже по номеру).

## R5. Обращения: частичный индекс взятых

`support_threads_taken ON support_threads (assignee) WHERE status = 'open' AND assignee != 0`. Часть 3 счётчика
(«взятые мной») получает условие `t.assignee != 0` — без него план не может взять частичный индекс. Индекс по
`assignee` без `!= 0` планировщик брал и для части 2 (`assignee = 0` — все ничьи открытые обращения бота) — хуже, чем
от событий компаний организатора (`support_threads_event`), как сейчас.

## R6. Передача прав владельца бота

`setOwner` писал журнал в каждую компанию, которую ведёт владелец бота или новый владелец, по `ctx.companies()` — у
нового владельца (ссылка `/setup`) это теперь только его компании. Замена — именованное чтение `SELECT id FROM companies
WHERE owner_id = 0 OR owner_id = ? ORDER BY id` (индекс `companies_owner`). Опция `companies: true` пакета чтений больше
никому не нужна — убирается.

## R7. Миграция

`0018_read_indexes.sql` — пять `CREATE INDEX IF NOT EXISTS`, без строк и без версии схемы (как `0008`, `0017`): код от
индексов не зависит, порядок «миграция ↔ выкат» и откат кода безопасны.

## R8. Проверка

`tests/api-reads.test.mjs`: мир открытого бота, чужая история (компании с людьми, завершённое событие с парами,
перепиской, обращением, отклонённой заявкой, семьёй), затем вызовы обычных людей — все операторы каждого вызова
(`EXPLAIN QUERY PLAN`): полный просмотр только у `settings`, `outbox` и у ветки «все компании» первого пакета. Общие
помощники разбора планов — `tests/support/plans.mjs` (их же берёт `cron-reads`). «От противного»: прежние запросы
компаний, людей, событий и база без индексов `0018` находятся.
