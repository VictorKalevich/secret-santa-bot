# Feature Specification: Быстрые тесты всего Worker

**Feature Branch**: `016-fast-tests`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Быстрые тесты всего Worker без wrangler. Разработчик запускает `npm test` и за секунды
получает проверку тайны пар (перестановка пар не меняет ни один ответ админу), прав ролей по всем действиям API,
атомарности при одновременных вызовах с навязанным чередованием, числа запросов к базе на действие и неизменности
результатов жеребьёвки при заданном зерне. Тесты работают на настоящем коде Worker и встроенном `node:sqlite`, без
новых зависимостей. Код приложения не меняется; e2e остаётся проверкой перед выкатом. Известные дефекты одновременных
вызовов фиксируются тестами с пометкой «будет исправлено». Автотест «владелец ⊇ админ» в e2e перестаёт пропускать
действия с «_» в имени. Основа — `docs/refactoring/step-1-fast-tests.md` и прототипы из `docs/refactoring/prototypes/`."

Шаг 1 плана рефакторинга (`docs/refactoring-roadmap.md`). Подробности, номера строк и прототипы —
`docs/refactoring/step-1-fast-tests.md`, базовые замеры — `docs/refactoring/baseline.md`.

## User Scenarios & Testing *(mandatory)*

Действующее лицо — разработчик (владелец проекта или агент), который меняет серверный код. Участники и организаторы
бота этой фичи не замечают: ни одна строка приложения не меняется.

### User Story 1 — Тайна пар и права ролей проверяются перед каждым коммитом (Priority: P1)

Сейчас тайну пар, права ролей и атомарность проверяет только сквозной тест: 194 секунды, восемь запусков локального
Worker, по правилам проекта — перед выкатом. Следующие шаги рефакторинга меняют именно этот код. Разработчик запускает
обычную проверку перед коммитом и за секунды узнаёт, не начал ли какой-нибудь ответ администратору зависеть от пар,
писем или адресов и не получил ли кто-то лишнее право или не потерял ли нужное.

**Why this priority**: тайна (принцип I) и «владелец ⊇ админ» (принцип VII) — жёсткие правила; без быстрой проверки
шаги 3–5 пришлось бы проверять только сквозным тестом в конце.

**Independent Test**: `npm test` — тесты тайны и прав зелёные; любая правка, из-за которой ответ администратору
меняется при перестановке пар, или любое действие, у которого меняется набор ролей с доступом, роняет проверку.

**Acceptance Scenarios**:

1. **Given** событие после жеребьёвки и снятые ответы администратору, **When** в базе подопечные переставлены между
   Сантами (статусы Санты остаются у Санты, статусы подопечного переезжают с подопечным), **Then** все ответы
   администратору совпадают с прежними побайтно.
2. **Given** событие с письмами и адресами, **When** тексты писем и адресов заменены другими непустыми, **Then** ответы
   администратору не меняются (кроме открытия письма, которое отдаёт письмо по замыслу).
3. **Given** список всех действий администратора из кода, **When** каждое вызывается на свежем событии участником,
   администратором и владельцем, **Then** участник получает отказ «Только для администратора.» на каждом, администратор —
   отказ по правам ровно на действиях владельца, владелец — ни одного отказа по правам.
4. **Given** любой сценарий с рассылками, **When** проверяются тексты всех сообщений, **Then** ни одно, кроме «Тайна
   раскрыта», не содержит имени подопечного получателя и текста чьего-либо письма.

### User Story 2 — Одновременные вызовы проверяются с навязанным чередованием (Priority: P1)

Проверки гонок в сквозном тесте не задают порядок выполнения и проходят, даже если два запроса выполнились по очереди.
С навязанным чередованием («оба прочитали, затем оба пишут») нашлись 11 случаев дубля или порчи данных. Разработчик
видит, какие действия защищены от двойного вызова, а известные дефекты помечены «будет исправлено в шаге N»: шаг,
который чинит дефект, снимает пометку, и тест начинает обязан проходить.

**Why this priority**: шаги 3 и 5 чинят пять дефектов; без воспроизводимой проверки не доказать ни поломку, ни починку.

**Independent Test**: `npm test` — 16 проверок «один результат» зелёные, 5 известных дефектов отмечены как
«будет исправлено» с номером шага и не роняют прогон.

**Acceptance Scenarios**:

1. **Given** два одинаковых вызова (жеребьёвка, раскрытие, завершение, удаление события, обе отмены, удаление и
   вписывание после жеребьёвки, заявки, обращения, ссылка владельца), **When** оба читают, затем оба пишут, **Then** у
   действия ровно один результат: одно сообщение, одна запись журнала, второй вызов получает отказ.
2. **Given** известный дефект (двойной перенос участия, выход админа из участия одновременно с жеребьёвкой, двойное
   удаление до жеребьёвки, двойное исключение, двойная отметка «получил» в одну миллисекунду), **When** прогон тестов,
   **Then** проверка помечена «будет исправлено» с номером шага и прогон не падает.
3. **Given** один и тот же код, **When** проверки атомарности запускаются несколько раз, **Then** результат одинаков.

### User Story 3 — Число запросов на действие не растёт (Priority: P2)

Бесплатный тариф даёт 50 внешних запросов на вызов. Шаг 4 должен сократить повторные чтения, остальные шаги — не
добавлять новые. Разработчик видит, если какое-то действие стало делать больше запросов к базе, чем в базовом замере.

**Why this priority**: лимит запросов — жёсткое правило (принцип V); шаг 4 опирается на эту проверку.

**Independent Test**: `npm test` — сценарий из 46 действий: каждое не тяжелее базового замера; жеребьёвка на 40 человек
вместе с отправкой очереди укладывается в 50 запросов.

**Acceptance Scenarios**:

1. **Given** сценарий из базового замера, **When** каждое действие выполнено, **Then** запросов к базе не больше, чем в
   `baseline.md` (раздел 3), а сообщений в Telegram — столько же.
2. **Given** событие на 40 человек, **When** жеребьёвка, **Then** запросов к базе и к Telegram за вызов — не больше 50,
   остальные сообщения ждут в очереди.

---

### User Story 4 — Результат жеребьёвки при том же зерне не меняется (Priority: P2)

Шаг 2 ускоряет жеребьёвку, шаги 4 и 5 трогают код вокруг неё. Требование «при том же зерне те же пары» сейчас
проверяется только разовым сравнением двух файлов. Разработчик получает постоянный эталон: несколько сотен случаев с
зерном, результат каждого записан заранее и сверяется побайтно.

**Why this priority**: пары, которые меняются при том же зерне, — незаметная смена поведения; эталон ловит её сразу.

**Independent Test**: `npm test` — тест эталона зелёный; правка порядка вызовов генератора случайных чисел роняет его.

**Acceptance Scenarios**:

1. **Given** эталон, снятый с текущей жеребьёвки, **When** тест сверяет жеребьёвку, поиск пар, удаление и вписывание
   после жеребьёвки, **Then** все результаты совпадают побайтно.
2. **Given** правка, меняющая порядок случайных выборов, **When** тест эталона, **Then** он падает и называет случай.

---

### User Story 5 — Автотест «владелец ⊇ админ» в сквозном тесте ничего не пропускает (Priority: P3)

Сквозной автотест прав находит действия регулярным выражением без «_» и пропускает два действия, а порог «не меньше
35» позволяет молча потерять ещё девять. После правки он находит ровно 46 действий.

**Why this priority**: сквозной тест остаётся проверкой настоящего Worker перед выкатом; дыра в нём мелкая, но
заметна только при чтении кода.

**Independent Test**: `npm run test:e2e` — автотест находит 46 действий, владелец не получает ни одного отказа по правам.

**Acceptance Scenarios**:

1. **Given** код API, **When** автотест собирает список действий, **Then** их ровно 46, включая действия с «_» в имени.

---

### Edge Cases

- Проверка «база не подготовлена» в общем процессе невоспроизводима (готовность схемы запоминается на весь процесс) —
  остаётся в сквозном тесте.
- Захваты, которые узнают «свой» вызов по метке времени, дают дубль только при совпадении времени до миллисекунды —
  такие проверки останавливают часы на время вызовов.
- Без навязанного чередования одновременные вызовы в одном процессе фактически идут по очереди — проверки гонок
  обязаны задавать порядок явно.
- Время прогона: существующие проверки времени жеребьёвки (`< 10 мс`) меряют настенное время; если новые тесты делают
  их нестабильными, прогон идёт без параллельных файлов, пороги не ослабляются.
- Поддельный Telegram в быстрых тестах отвечает так же, как имитация сквозного теста: отказ заблокировавшему, отказ при
  длине больше 4096 и при разорванном эмодзи.
- Перестановка пар не создаёт пары «сам себе» и не ломает уникальность подопечного.

## Requirements *(mandatory)*

### Functional Requirements

Инварианты — то, что фича обязана сохранить:

- **FR-1601**: Код приложения (`src/`) не меняется: ответы, тексты, коды ответов, запросы к базе — те же. Найденные
  дефекты только фиксируются тестами.
- **FR-1602**: Сценарии сквозного теста не сокращаются и не переписываются, кроме автотеста «владелец ⊇ админ»
  (FR-1614); сквозной тест остаётся проверкой настоящего Worker перед выкатом.
- **FR-1603**: Без новых зависимостей и без поддельных таймеров: «перемотка времени» — правкой полей в базе, как в
  сквозном тесте.

Что появляется:

- **FR-1604**: Обычная проверка перед коммитом запускает весь Worker (маршруты бота, приложения, API, настройки, cron)
  в одном процессе на встроенной базе с настоящими миграциями, без локального сервера Worker.
- **FR-1605**: Подмена базы повторяет поведение настоящей базы, на которое опирается код (первая строка или пусто,
  значение колонки, число изменённых строк именно этим оператором, пакет — одна транзакция с откатом, результаты
  операторов с возвратом строк, нумерованные параметры с повтором, привязка чисел, булевы как 0/1, ошибка на
  неопределённом значении); каждое свойство закреплено отдельной проверкой.
- **FR-1606**: Поддельный Telegram в быстрых тестах и HTTP-имитация сквозного теста пользуются одними правилами ответа
  (отказ заблокировавшему, отказ при длине больше 4096 видимых символов, отказ при разорванном эмодзи в тексте или
  кнопках).
- **FR-1607**: Тайна по значениям:
  - перестановка подопечных между Сантами не меняет ни одного ответа администратору (`admin.state`, `admin.audit`,
    `admin.users`, `admin.families`, `event.get`; `admin.draw.check` нового события, которое учитывает пары прошлого);
  - замена текстов писем и адресов другими непустыми не меняет ответы администратору, кроме открытия письма;
  - обычный администратор не получает поля закреплённых пар, действия закреплённых пар ему запрещены;
  - не-участник и администратор-неучастник получают отказ на действия участника (подопечный, переписка, отметки
    подарка, адрес, письмо, обращения);
  - тексты всех сообщений, кроме «Тайна раскрыта», не содержат имени подопечного получателя и текста письма;
  - взятое обращение: третьему администратору — отказ, владельцу — переписка.
- **FR-1608**: Права: список действий администратора собирается из кода и обязан содержать ровно 46; каждое действие
  на свежем событии — участнику отказ «Только для администратора.», администратору отказ по правам ровно на 12
  действиях владельца, владельцу — ни одного отказа по правам; незарегистрированному — отказ 403, неверная подпись —
  401, не-POST — 405.
- **FR-1609**: Атомарность: 16 проверок «один результат» — обычные проверки; 5 известных дефектов — проверки с
  пометкой «будет исправлено» и номером шага; 6 случаев «захвата нет, решение владельца» в тесты не входят.
- **FR-1610**: Число запросов: каждое действие сценария базового замера делает не больше запросов к базе, чем в
  `baseline.md`, и столько же запросов к Telegram; жеребьёвка на 40 человек вместе с отправкой очереди — не больше 50
  запросов за вызов; в журнале Worker нет «budget exceeded».
- **FR-1611**: Эталон жеребьёвки: результаты жеребьёвки, поиска пар, удаления и вписывания после жеребьёвки для
  нескольких сотен случаев с зерном записаны в файл отдельным скриптом от текущей жеребьёвки; тест сверяет побайтно.
  Эталон в шагах плана рефакторинга не пересоздаётся.
- **FR-1612**: Замер скорости жеребьёвки (холодный и прогретый вызов на 50–200 человек) запускается отдельной командой
  и в обычную проверку не входит.
- **FR-1613**: Страница приложения: ответ на `/app` — файл приложения со встроенной дизайн-системой (токены, перевод
  строки, компоненты) вместо метки, метки в ответе нет.
- **FR-1614**: Автотест «владелец ⊇ админ» в сквозном тесте находит действия с «_» в имени и требует ровно 46.
- **FR-1615**: Юнит-тесты очереди и счётчика запросов не узнают запросы по подстроке SQL там, где это можно сделать на
  подмене базы; проверка «в пакет уходят исходные операторы, а не обёртки» сохраняется по смыслу.
- **FR-1616**: Подпись `initData` и тестовые секреты лежат в общем файле без запуска процессов; его используют и
  быстрые тесты, и сквозной тест.
- **FR-1617**: Минимальная версия Node в проекте — та, где встроенная база доступна без флага и есть перехват загрузки
  модулей; подтверждена документацией Node.
- **FR-1618**: Документы: README (версия Node, раздел о тестах), `CLAUDE.md` (команды, структура, таблица фич), статус
  шага в плане рефакторинга, `baseline.md` (раздел 1 и команды раздела 7), папка прототипов — без перенесённых файлов.

### Key Entities

Данных приложения фича не добавляет. Новые артефакты тестов:

- **Мир**: весь Worker в одном процессе — база в памяти с миграциями, поддельный Telegram, помощники вызовов (API, бот,
  cron, SQL), счётчики запросов последнего вызова, одновременные вызовы с заданным порядком записи.
- **Эталон жеребьёвки**: файл с результатами для фиксированного набора случаев; создаётся один раз скриптом.
- **Базовые числа запросов**: таблица «действие → не больше N запросов к базе, ровно M к Telegram» из `baseline.md`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1601**: `npm test` зелёный; время прогона — не больше 5 секунд (было: 0,6 с без проверок тайны, прав и
  атомарности; сквозной тест — 194 с).
- **SC-1602**: Изменений в коде приложения нет: сравнение ветки с `main` по папке `src/` пусто.
- **SC-1603**: `npm run test:e2e` зелёный; автотест прав находит 46 действий из 46 (было 44).
- **SC-1604**: В выводе `npm test` ровно 5 тестов «будет исправлено», в имени каждого — номер шага плана.
- **SC-1605**: Проверки атомарности дают одинаковый результат в трёх прогонах подряд.
- **SC-1606**: В папке прототипов остались только правка жеребьёвки для шага 2, сверка двух вариантов жеребьёвки и
  обновлённое описание.
- **SC-1607**: Шаг 1 отмечен выполненным в плане рефакторинга; в `baseline.md` обновлены раздел 1 и команды раздела 7.

## Assumptions

- «Свежее событие» в проверке прав — отдельное событие на каждое действие и каждую роль: так завершение события одним
  действием не превращает отказ по правам у следующего в отказ «Событие завершено».
- Тело запроса в проверке прав — минимальное (событие, нулевые id людей, без слов подтверждения): опасные действия
  получают отказ по данным, а не по правам, как в сквозном автотесте.
- `admin.draw.check` после жеребьёвки всегда отвечает «Жеребьёвка уже проведена», поэтому в проверке перестановки он
  снимается на новом событии тех же людей, которое учитывает пары прошлого (так он и мог бы выдать чужие пары).
- В проверке перестановки администратор не участвует в событии: его собственная пара по замыслу видна ему в
  `ward.get`, а не в ответах администратора.
- Проверка «имя подопечного не в сообщениях» применяется к сообщениям участникам-неадминам: уведомления организаторам
  об обращениях и вступлениях называют автора по замыслу, и это имя не связано с парой.
- Число сообщений в Telegram на действие — поведение (не оптимизация), поэтому сравнивается на равенство; число
  запросов к базе — «не больше».
- Захваты по метке времени проверяются с остановленными часами — так выглядят одновременные запросы в Workers.
- Если прогон новых тестов вместе с проверками времени жеребьёвки окажется нестабильным, файлы запускаются по одному
  (без параллельных процессов), пороги не меняются.
- Минимальная версия Node — 22.15 по сведениям обзора; окончательно — по документации Node (в `research.md`).
