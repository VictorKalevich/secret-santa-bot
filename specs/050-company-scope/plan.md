# Implementation Plan: 050. Компании, шаг 1 — данные и права в пределах компании

**Branch**: `050-company-scope` | **Date**: 2026-11-23 | **Spec**: [spec.md](spec.md)

## Summary

Всё, что сегодня общее для бота, — администраторы (`users.is_admin`), список людей (`ctx.users()`), владелец
(`ctx.ownerId()`), семьи, общий журнал (`audit.event_id = 0`), «другие события», прошлые пары — начинает считаться в
пределах компании. Миграция `0015_companies.sql` (схема 17) создаёт `companies` и `company_members`, добавляет
`company_id` событиям, семьям, строкам семей и журналу и относит всё существующее к компании №1 «Основная».

Главный приём — **контекст вызова, привязанный к компании** (`ctx.in(companyId)`): у него `users()` — люди компании с
правами этой компании в поле `is_admin`, `ownerId()` — владелец компании (назначенный или владелец бота), `isOwner()`,
`me.is_admin` — «организатор здесь». Модули (`membership`, `support`, `events`, `pairs`, `panel`, `participant`, `roles`,
`vault`, `constraints`, `cron`, `bot`) получают привязанный контекст и почти не меняются: их `adminRecipients(users)`,
`u.is_admin`, `ctx.isOwner()` сами становятся «в пределах компании». Конвейер `handleApi` определяет компанию до
обработчика: у действия события — `ev.company_id`, у общего действия организатора — `body.company` или единственная
компания человека.

Экранов, действий и текстов не добавляется; с одной компанией ответы, сообщения, журнал, число запросов и страница
приложения — прежние (эталоны не трогаются). Изоляцию доказывает новый тест на двух компаниях, вторая создаётся прямо в
базе «мира».

## Technical Context

**Language/Version**: JavaScript ES2022, ES-модули (Cloudflare Workers, workerd)

**Primary Dependencies**: нет рантайм-зависимостей; Wrangler 4 для dev/deploy

**Storage**: Cloudflare D1 (SQLite); схема 16 → 17, миграция `0015_companies.sql` (2 новые таблицы, 4 колонки
`company_id`, пересборка `family_members` с ключом `(company_id, user_id)`)

**Testing**: `node:test` (Node 22.15+, «мир» `tests/support/world.mjs`: вторая компания — `w.sql`), e2e `wrangler dev`

**Target Platform**: Telegram Mini App + Worker на бесплатном тарифе

**Project Type**: веб-сервис (Worker) + мини-приложение без сборщика

**Performance Goals**: число обращений к базе на действие не больше базовых (`tests/queries.test.mjs`, таблица
`BASELINE` не меняется): роли и компании читаются в том же первом пакете, что пользователь и настройки

**Constraints**: тайна между компаниями (принцип I); ≤ 50 внешних запросов, ≤ 10 мс CPU; `atomic` для всех меняющих
действий; каскады — только построителями `REGISTRY`; прежний код работает на новой схеме (откат)

**Scale/Scope**: компаний — единицы, людей в компании — до сотен; 0 новых действий API (68), 0 новых кодов журнала,
~14 модулей `src/` с правками, `src/app/` не меняется

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Проверка | Итог |
|---|---|---|
| I. Тайна по умолчанию | Пары по-прежнему не отдаются никому, кроме Санты и служебного просмотра владельца. Новое: администратор одной компании не получает ничего о другой — события, люди, семьи, журнал, уведомления; действие над чужим событием — как над несуществующим. Правила пар (семьи, прошлые пары) не зависят от данных другой компании — иначе отказ или результат жеребьёвки косвенно выдавал бы чужие пары. Служебный просмотр, закреплённые пары, вписывание, обмен — по-прежнему только владелец бота (назначенного владельца компании в этом шаге нет). | ✅ |
| II. Проще некуда для участника | Для людей ничего не меняется; слова «компания» в интерфейсе нет. | ✅ |
| III. Спецификация до кода | spec → plan → tasks → implement в ветке `050-company-scope`; `docs/api.md`, README, `CLAUDE.md` — в той же ветке. | ✅ |
| IV. Только дизайн-система | `src/app/` и `design-system/` не меняются (страница побайтно прежняя). | ✅ |
| V. Бесплатно и без сервера | Первый пакет чтений вызова расширен (роли, компании, владелец бота) — запросов не больше; тест `queries` с прежней таблицей. | ✅ |
| VI. Проверено до выката | Прежние тесты без правки ожиданий + новый `companies` (изоляция, человек в двух компаниях, гость), `migrations` (0015 на базе с данными), `data-registry` (19 таблиц), `snapshots` (семьи компании), инварианты после сценариев; e2e. | ✅ |
| VII. Владелец — максимальные права | Владелец бота — владелец в любой компании (`isOwner()`), «владелец ⊇ админ» в каждой; e2e-автотест прежний. | ✅ |

## Порядок работ (сводно)

1. Схема: миграция, `REQUIRED_SCHEMA`, `REGISTRY`, `EVENT_SERVICE`, тесты схемы. Прежний код ещё читает по-старому —
   всё зелёное.
2. Контекст и конвейер: первый пакет, `ctx.in`, определение компании в `handleApi`. На время перехода непривязанный
   контекст ещё отдаёт общие `users()`/`ownerId()`.
3. Модули — по одному, после каждого `npm test` зелёный (прежние тесты — проверка US1).
4. Запрет общих `users()`/`ownerId()`/`isOwner()` у непривязанного контекста — пропущенные места падают в тестах.
5. Тесты двух компаний (US2, US3), инварианты, сверка, документы.
