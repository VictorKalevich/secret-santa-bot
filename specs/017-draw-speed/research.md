# Research: Жеребьёвка быстрее при том же результате

Основа — `docs/refactoring/step-2-draw-speed.md` и замеры `docs/refactoring/baseline.md` (раздел 2). Неизвестных в
Technical Context нет; ниже — решения и их обоснование.

## R1. Перестановка в `shuffle`

- **Decision**: `const t = a[i]; a[i] = a[j]; a[j] = t;` вместо `[a[i], a[j]] = [a[j], a[i]]`.
- **Rationale**: в непрогретом коде (интерпретатор и базовый компилятор V8, а холодный вызов в Worker идёт именно там)
  деструктуризация создаёт массив и итератор на каждую перестановку. Первое паросочетание делает `n` перемешиваний
  списков длиной до `n` — для 200 человек это ~40 000 перестановок, 3,8 мс из 5,8 холодного вызова. Вызовы `rng` и их
  порядок не меняются: тот же `Math.floor(rng() * (i + 1))` на каждом шаге цикла.
- **Alternatives considered**: перемешивание «на месте» без `slice` — меняет контракт (вызывающие передают свои
  массивы), выигрыш мал; отказ от перемешивания списков смежности — меняет результат.

## R2. Матрица допустимости по спискам (`fillMatrix`)

- **Decision**: функция правил из `pairRules` получает свойство `fillMatrix(ids, adj)`:
  1. индекс человека по id (`Map`);
  2. `adj.fill(1)`;
  3. каждый запрет `giver → receiver`, где оба в списке, — `0`;
  4. столбец каждого закреплённого подопечного (ключи `santaOf`), если он в списке, — `0`;
  5. строка каждого закреплённого Санты (`wardOf`), если он в списке, — `0`, затем его закреплённый подопечный, если
     он в списке, — `1`;
  6. диагональ — `0` («самому себе» нельзя).
- **Rationale**: значение `adj[i][j]` при переборе — `ids[i] !== ids[j] && rule(ids[i], ids[j])`, где `rule`:
  закреплённый Санта → только свой подопечный; иначе закреплённый подопечный → никто; иначе — нет запрета. Порядок
  шагов 3–6 даёт то же: шаг 5 перекрывает шаги 3–4 в строках закреплённых Сант (закреплённая пара важнее запрета и
  чужого закрепления), шаг 4 перекрывает «нет запрета» в столбцах закреплённых подопечных для остальных строк, шаг 6 —
  всё на диагонали. Люди не из списка пропускаются: запрет с ними ничего не меняет в матрице, строка Санты с
  подопечным не из списка — нули, столбец подопечного с Сантой не из списка — нули (как при переборе: `wardOf.get(a)
  === b` не выполняется ни для кого из списка; `santaOf.has(b)` — `false` для всех, кроме его Санты, которого нет).
  Дубли в списках закреплённых пар (в базе их нет — уникальные индексы, но функция их допускает) дают то же, что
  перебор: `wardOf` и `santaOf` строятся одинаково для обоих путей. Стоимость — один `fill` на `n²` байт плюс
  `O(|запретов| + n·|закреплённых|)` вместо `n²` вызовов замыкания с `Map.has`/`Set.has`: 1,4 мс из 5,8 на 200
  человек.
- **Предпосылка**: id в списке различны (это id участников события). Для одинаковых id перебор и `fillMatrix`
  разошлись бы на внедиагональных клетках с одинаковым id; в коде так не вызывается.
- **Alternatives considered**: строить матрицу в `pairRules` заранее — правилам неизвестен список `ids` и его порядок
  (каждая попытка `planDraw` строит свою матрицу по тем же `ids`); заменить функцию правил на объект — меняет интерфейс
  `findAssignment`, `removeFromAssignment`, `insertIntoAssignment`, на которые опираются `src/pairs.js` и тесты.

## R3. Как `findAssignment` узнаёт быструю часть

- **Decision**: `if (typeof isAllowed.fillMatrix === 'function') isAllowed.fillMatrix(ids, adj); else` прежний цикл.
- **Rationale**: интерфейс `findAssignment(ids, isAllowed, …)` не меняется: произвольная функция (тесты, обёртки)
  работает прежним перебором и даёт тот же результат. Свойство теряется при обёртке `(a, b) => rules(a, b)` — тогда
  просто медленнее, не иначе; эталон проверяет это равенство (`findFnSame`). Все вызовы из `src/` идут через
  `planDraw` (`run` передаёт `pairRules(…)` напрямую) — так и остаётся. `removeFromAssignment` и
  `insertIntoAssignment` матрицу не строят и не меняются.
- **Alternatives considered**: отдельный параметр `matrix` в опциях — два источника правды для одной матрицы.

## R4. Чего не делаем

- Один буфер `seen` на весь поиск в `findMatching` — выигрыш в пределах погрешности (`step-2-draw-speed.md`).
- «Быстрая попытка» — случайные круги до построения матрицы: меняет порядок вызовов `rng`, то есть пары при том же
  зерне; решение владельца (`docs/refactoring-roadmap.md`, «Решения владельца»).
- `DEFAULT_BUDGET`, 30 случайных кругов, 5 попыток перебора, 60 паросочетаний, деление бюджета в `planDraw`, `diagnose` —
  без изменений. Учёт шагов бюджета (`spend`) не трогается: матрица заполняется до поиска и в бюджет не входила.
- Комментарий «его закреплённый Санта — не a (иначе сработала бы строка выше)» в правиле сохраняется: в патче он удалён
  без причины.

## R5. Как доказать «тот же результат»

- **Decision**: три независимые проверки.
  1. Эталон шага 1 (`tests/draw-golden.test.mjs`, 400 случаев: `planDraw`, `findAssignment` с правилами и обёрткой,
     удаление и вписывание с рангом и без) — без пересоздания `tests/fixtures/draw-golden.json`.
  2. Сверка двух вариантов файла на 6000 случаях (`draw-equivalence.mjs`, исходник — `git show main:src/draw.js`) —
     один раз перед удалением прототипа; результат записывается в отчёт и `baseline.md`.
  3. Новый тест в `tests/draw.test.mjs`: на случайных правилах (запреты разной плотности, люди не из списка, закреплённые
     пары, в том числе с людьми не из списка, дубли и «самому себе») матрица `fillMatrix` поэлементно равна матрице
     перебора `a !== b && rule(a, b)`. Это закрепляет FR-1704 после удаления сверки.
- **Rationale**: эталон и сверка ловят расхождение результата, тест матрицы — расхождение причины (на случаях, где
  другая матрица случайно дала бы тот же итог).

## R6. Замер «до и после»

- **Decision**: `npm run bench:draw` дважды до правки и дважды после, на одной машине, от сети, в одной сессии;
  сравнивать медианы. До (2026-11-14, Node 24.21.0):

  | Человек | Холодный, мс (2 прогона) | Прогретый, мс (2 прогона) |
  |---|---|---|
  | 50 | 1,73 / 1,62 | 0,08 / 0,08 |
  | 100 | 3,14 / 2,99 | 0,29 / 0,29 |
  | 150 | 4,59 / 4,47 | 0,79 / 0,79 |
  | 200 | 6,08 / 5,69 | 1,40 / 1,37 |

- **Критерий** (FR-1707, SC-1701, SC-1702): холодная медиана на 200 — не больше 0,75 × нижней границы «до»
  (≤ 4,27 мс); ни одна медиана «после» не выше верхней границы «до» плюс разброс двух прогонов «до».
- Замер вариантом файла без копирования в `src/`: `npm run bench:draw -- <путь к draw.js>`.

## R7. Нестабильный тест числа запросов

- **Наблюдение**: на чистом `main` `tests/queries.test.mjs` падал 2 раза из 20 (и 1 раз в `npm test`):
  «`admin.remove (после жеребьёвки)`: к Telegram 3, было 2». Жеребьёвка (`runDraw`) и замена после удаления
  (`removeFromAssignment` в `src/pairs.js`) берут `Math.random`; если Санта удалённого не может дарить его подопечному
  (исключение или взаимная пара при кольцевой), меняются две пары и уведомлений три.
- **Decision**: `runQueriesScenario` подменяет `Math.random` генератором с зерном (`seeded` из
  `tests/support/draw-cases.mjs`) на время сценария и возвращает прежний в `finally`. Зерно 1 даёт базовую таблицу
  без изменений (проверено на зёрнах 1–8, 16, 17: только зерно 6 даёт «3»). `src/` не меняется, таблица `BASELINE` в
  `tests/queries.test.mjs` — тоже.
- **Rationale**: число сообщений — поведение, его нельзя проверять «в диапазоне»; сценарий должен быть одинаковым в
  каждом прогоне. Шаг 2 не меняет порядок вызовов `rng`, поэтому зерно 1 даёт ту же таблицу и после правки
  `src/draw.js`. Коды приглашений и метки `randomCode` идут через `crypto.getRandomValues` и подменой не затронуты.
- **Alternatives considered**: допускать 2–3 сообщения — ослабляет проверку; убирать из сценария исключения —
  меняет набор действий, который сверяется с базовой таблицей.
