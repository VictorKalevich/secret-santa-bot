# Feature Specification: Жеребьёвка быстрее при том же результате

**Feature Branch**: `017-draw-speed`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Жеребьёвка быстрее при том же результате. Организатор проводит жеребьёвку большой группы,
и расчёт укладывается в лимит CPU бесплатного тарифа с большим запасом: холодный вызов на 200 человек — не менее чем на

допустимости по спискам запретов вместо `n²` вызовов функции правил. Основа — `docs/refactoring/step-2-draw-speed.md` и
готовая правка `docs/refactoring/prototypes/draw-speedup.patch`."

Шаг 2 плана рефакторинга (`docs/refactoring-roadmap.md`). Подробности и замеры — `docs/refactoring/step-2-draw-speed.md`,

## User Scenarios & Testing *(mandatory)*

Действующие лица — организатор (владелец или админ), который проводит жеребьёвку, и разработчик, который проверяет, что
результат не изменился. Участники и организаторы видят прежние экраны, тексты и пары: меняется только скорость расчёта.

### User Story 1 — Жеребьёвка большой группы с запасом по лимиту CPU (Priority: P1)

Организатор нажимает «Провести жеребьёвку» в событии на 150–200 человек. Бесплатный тариф даёт 10 мс CPU на вызов, а
первый вызов обычно холодный. Сейчас холодный расчёт на 200 человек занимает 5,7–6,1 мс на машине владельца от сети и
9–12 мс от батареи, то есть на медленном экземпляре жеребьёвка может упереться в лимит. После фичи тот же расчёт
занимает заметно меньше времени, и жеребьёвка проходит с запасом; пары, сообщения и причины отказа — те же, что дала бы
прежняя версия при том же случайном зерне.

**Why this priority**: это единственная польза фичи для людей — запас по лимиту CPU (принцип V).

**Independent Test**: замер жеребьёвки (холодный и прогретый вызов на 50, 100, 150, 200 человек) до и после правки на
одной машине: холодная медиана на 200 человек ниже не менее чем на 25%, ни на одном размере медиана не выросла.

**Acceptance Scenarios**:

1. **Given** сценарий «семьи-пары + прошлый год, кольцевая» на 200 человек, **When** холодный расчёт жеребьёвки
   запускается 25 раз в свежих процессах, **Then** медиана не менее чем на 25% меньше медианы прежней версии.
2. **Given** тот же сценарий на 50, 100, 150 и 200 человек, **When** сняты холодные и прогретые медианы, **Then** ни
   одна не выросла больше разброса между двумя прогонами «до».
3. **Given** любое событие и любое зерно случайных чисел, **When** проводится жеребьёвка, **Then** пары, признак «один
   круг», признак «мешают семьи» и причины отказа совпадают с прежней версией побайтно.

### User Story 2 — Разработчик доказывает, что результат не изменился (Priority: P1)

Разработчик меняет расчёт ради скорости и должен доказать, что ни одна пара при том же зерне не поменялась: ни при
жеребьёвке, ни при удалении и вписывании после неё. Тест с эталонными результатами из шага 1 проходит без
пересоздания эталона; отдельная сверка на 6000 случайных случаях даёт 0 расхождений; новый тест сравнивает матрицу
«кто кому может дарить», построенную по спискам запретов, с матрицей прямого перебора правил — в том числе когда
запреты и закреплённые пары называют людей не из списка жеребьёвки.

**Why this priority**: без этого скорость нельзя принять — «пары при том же зерне не меняются» обязательно для всех
шагов плана.

**Independent Test**: `npm test` — эталон жеребьёвки и новый тест матрицы зелёные; сверка двух вариантов файла
жеребьёвки — 0 расхождений.

**Acceptance Scenarios**:

1. **Given** эталон из 400 случаев (шаг 1), **When** запускается `npm test`, **Then** все случаи совпадают побайтно,
   файл эталона не меняется.
2. **Given** случайные запреты, семьи и закреплённые пары, в том числе с людьми не из списка, **When** матрица
   строится по спискам запретов и прямым перебором правил, **Then** обе матрицы совпадают поэлементно.
3. **Given** произвольная функция правил (не созданная общим правилом «кто кому может дарить»), **When** по ней ищется
   распределение, **Then** результат тот же, что у прежней версии, — работает прежний перебор.
4. **Given** прежний файл жеребьёвки из `main` и новый, **When** запускается сверка на 6000 случайных случаях,
   **Then** расхождений 0.

### User Story 3 — Проверка перед коммитом не падает случайно (Priority: P2)

Разработчик запускает `npm test` перед каждым коммитом. Тест числа запросов из шага 1 иногда падает на неизменном коде:
жеребьёвка и замена пары в его сценарии берут случайные числа без зерна, и удаление участника после жеребьёвки меняет
то одну пару, то две (2 или 3 сообщения в Telegram при базовом числе 2). После фичи сценарий детерминирован: те же
числа запросов в каждом прогоне.

**Why this priority**: правило проекта — зелёный `npm test` перед каждым коммитом; случайное падение мешает и этому
шагу, и всем следующим. Код приложения для этого не меняется.

**Independent Test**: тест числа запросов 30 раз подряд — 0 падений; таблица базовых чисел не меняется.

**Acceptance Scenarios**:

1. **Given** неизменный код, **When** тест числа запросов запускается 30 раз подряд, **Then** все прогоны зелёные с
   прежней таблицей базовых чисел.

---

### Edge Cases

- Запреты события называют участника, который ещё не ввёл имя и в жеребьёвку не попал, — запрет с ним пропускается,
  матрица та же, что при переборе правил.
- Закреплённый Санта есть в списке, его закреплённый подопечный — нет (прямой вызов поиска): строка этого Санты —
  «никому», как при переборе правил.
- Закреплённый подопечный есть в списке, его закреплённый Санта — нет: столбец этого подопечного — «никто», как при
  переборе правил.
- Запрет и закреплённая пара на одного и того же Санту: закреплённая пара важнее запрета — Санта дарит только своему
  закреплённому подопечному, даже если на эту пару есть запрет.
- «Самому себе» запрещено всегда, в том числе если запрет или закреплённая пара указывают человека на самого себя.
- Функция правил обёрнута другой функцией: дополнительная быстрая часть теряется, работает прежний перебор с тем же
  результатом.
- Группа из 2–3 человек, исчерпание бюджета поиска, невозможная жеребьёвка — те же причины отказа.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1701**: Результат жеребьёвки при том же зерне не меняется побайтно: пары, признак «один круг», признак «мешают
  семьи», причины отказа (в том числе «мешают закреплённые пары», «слишком строго», «круг невозможен», «бюджет
  исчерпан»).
- **FR-1702**: Порядок и число вызовов генератора случайных чисел, порядок попыток, бюджет поиска (150 000 шагов и его
  деление между попытками), число случайных кругов (30) и попыток перебора — прежние.
- **FR-1703**: Удаление и вписывание после жеребьёвки дают прежний результат при том же зерне.
- **FR-1704**: Матрица «кто кому может дарить», построенная по спискам запретов и закреплённых пар, поэлементно равна
  матрице прямого перебора общего правила для любого списка людей, в том числе когда правила называют людей не из
  списка. Порядок применения повторяет правило: закреплённый Санта важнее запрета, «самому себе» — никогда.
- **FR-1705**: Функция правил без быстрой части (любая другая функция) обрабатывается прежним перебором.
- **FR-1706**: Меняется только файл чистых функций жеребьёвки. Чтение данных для жеребьёвки, запись результата, API,
  бот, тексты, приложение, схема базы — без изменений.
- **FR-1707**: Холодный расчёт жеребьёвки на 200 человек (сценарий замера) быстрее не менее чем на 25%; ни на одном
  размере (50, 100, 150, 200) холодная и прогретая медианы не растут.
- **FR-1708**: Тест с эталонными результатами (шаг 1) проходит без пересоздания эталона; добавлен тест равенства двух
  способов построения матрицы на случайных правилах.
- **FR-1709**: Сценарий теста числа запросов детерминирован: случайные числа в нём — с фиксированным зерном, таблица
  базовых чисел прежняя. Код приложения для этого не меняется.
- **FR-1710**: Готовая правка и сверка из папки прототипов удаляются после применения; в `baseline.md` (раздел 2)
  записаны замеры «после»; шаг 2 отмечен выполненным в плане рефакторинга; `CLAUDE.md` (таблица фич, строка про файл
  жеребьёвки) и память проекта обновлены.

### Key Entities

- **Матрица допустимости** — для каждой пары людей из списка жеребьёвки: может ли первый дарить второму. Строится один
  раз на попытку поиска; её значения определяют результат.
- **Правило «кто кому может дарить»** — запреты (исключения, семьи, прошлые пары) и закреплённые пары владельца;
  закреплённая пара важнее запретов.
- **Эталон жеребьёвки** — 400 случаев с результатами при заданных зернах (шаг 1); не пересоздаётся.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1701**: Холодная медиана расчёта на 200 человек снижается не менее чем на 25% (было 5,69–6,08 мс на машине
  владельца от сети).
- **SC-1702**: Ни одна из восьми медиан (холодная и прогретая на 50, 100, 150, 200 человек) не выросла больше разброса
  двух прогонов «до».
- **SC-1703**: Эталон жеребьёвки — 400 из 400 совпадений без пересоздания; сверка двух вариантов — 0 расхождений на
  6000 случаях.
- **SC-1704**: Изменения в `src/` — только файл жеребьёвки; сравнение ветки с `main` по остальным файлам `src/` пусто.
- **SC-1705**: `npm test` зелёный в 5 прогонах подряд, тест числа запросов — в 30 прогонах подряд; `npm run test:e2e`
  зелёный.
- **SC-1706**: В папке прототипов не осталось правки и сверки шага 2; шаг 2 отмечен в плане, `baseline.md` обновлён.

## Assumptions

- Правка берётся из `docs/refactoring/prototypes/draw-speedup.patch` как есть, кроме одного: поясняющий комментарий к
  проверке закреплённого подопечного в правиле сохраняется (в патче он удалён без причины), и добавляются пометки фичи
  в комментариях, как у правок 015.
- Третья проверенная правка (один буфер «уже посещённых» на весь поиск паросочетания) не делается: выигрыш в пределах
  погрешности (`step-2-draw-speed.md`).
- «Быстрая попытка» (случайные круги до построения матрицы) не входит: она меняет пары при том же зерне — отдельное
  решение владельца.
- Нестабильность теста числа запросов найдена при замерах «до» на чистом `main` (2–3 падения из 20 прогонов); это
  дефект теста шага 1, не кода. Исправление — только в сценарии теста (фиксированное зерно), отдельным коммитом. Если
  бы для стабильности понадобилось менять `src/` или базовые числа, это был бы вопрос владельцу.
- Замеры «до» и «после» сняты на одной машине (Windows 11, Node 24.21.0, от сети) в одной сессии; сравниваются медианы.
- README не меняется: установка, настройка, команды и роли те же. Задача на README в `tasks.md` — проверка этого.
- Тайна (принцип I) и права (принцип VII) не затрагиваются: файл жеребьёвки не отдаёт ничего наружу, а результат при
  том же зерне тот же.
