# Feature Specification: Адрес доставки, семьи и заявки на вступление

**Feature Branch**: `008-delivery-families-requests`

**Created**: 2026-11-12

**Status**: Draft

**Input**: User description: "(1) адрес/способ доставки подарка участника — виден только его Санте (и самому участнику),
не админам; (2) «семьи» — постоянные группы исключений на уровне бота (члены одной семьи не дарят друг другу в любом
эвенте), управляются админами; (3) заявки на вступление — эвент может требовать одобрения админом: человек по ссылке
подаёт заявку, админ одобряет/отклоняет, человек получает уведомление. Заполняй спецификацию самостоятельно."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Адрес доставки только для своего Санты (Priority: P1)

Компания разъехалась по разным городам, подарки отправляют почтой или курьером. Организатор включает в эвенте «Подарки
отправляют — спросить адрес». Каждый участник на вкладке «Письмо» заполняет «Как передать подарок» (город, отделение
почты, получатель, телефон или «заберу в офисе»). Санта видит это поле на вкладке «Подопечный» рядом с письмом.
Организатор адреса не видит — только отметку «📍 адрес указан / не указан».

**Why this priority**: Без адреса удалённый обмен невозможен, а пересылать адрес через организатора — утечка пар
и личных данных.

**Independent Test**: Эвент с включённым адресом: участник сохраняет адрес → его Санта видит адрес в «Подопечном»;
ни один ответ админу (статусы, «открыть письмо», журнал) не содержит текста адреса.

**Acceptance Scenarios**:

1. **Given** эвент с включённым адресом, **When** участник сохраняет «Как передать подарок» (до 500 символов),
   **Then** его Санта видит текст в «Подопечном», а админ — только «📍 адрес указан».
2. **Given** адрес выключен, **When** участник открывает «Письмо», **Then** поля адреса нет, а Санта его не видит.
3. **Given** участник уже указывал адрес в прошлом эвенте, **When** он вступает в новый эвент, **Then** поле
   предзаполнено прошлым адресом (его можно изменить).
4. **Given** подопечный изменил адрес после жеребьёвки, **When** проходит задержка уведомлений, **Then** Санта получает
   «Твой подопечный обновил письмо или адрес» — без имени и без текста.
5. **Given** эвент завершён, **When** участник открывает «Письмо», **Then** адрес только для чтения.

### User Story 2 — Семьи: постоянные исключения (Priority: P1)

Каждый год приходится заново вносить «Маша и Петя не дарят друг другу», «Аня, Олег и их сын — одна семья». Админ один
раз заводит «семью» на главном экране (раздел «Семьи»): название и состав. Во всех эвентах, где включено «Учитывать
семьи» (по умолчанию включено), члены одной семьи не дарят друг другу — в жеребьёвке и при заменах.

**Why this priority**: Главная ручная работа при повторе эвента; ошибка в исключениях портит праздник.

**Independent Test**: Семья {Маша, Петя} и эвент с 4 участниками: 20 жеребьёвок подряд — ни разу Маша→Петя или
Петя→Маша; при выключенном «Учитывать семьи» пара возможна.

**Acceptance Scenarios**:

1. **Given** семья из 2–10 человек, **When** проводится жеребьёвка эвента с включёнными семьями, **Then** ни один член
   семьи не дарит другому члену той же семьи.
2. **Given** семья делает жеребьёвку невозможной (например, эвент из 3 человек, двое — семья, кольцевая), **When** админ
   проверяет жеребьёвку, **Then** видит понятную причину со словом «семья» и советом выключить семьи или кольцевую.
3. **Given** после жеребьёвки кого-то удаляют или вписывают, **When** бот перестраивает пары, **Then** правила семей
   соблюдаются.
4. **Given** человек уже состоит в семье, **When** админ добавляет его в другую, **Then** отказ «уже в семье «…»» — один
   человек состоит не больше чем в одной семье.
5. **Given** участник переносится на новый аккаунт, **Then** членство в семье переходит вместе с ним.
6. **Given** панель эвента, **Then** в разделе «Исключения» перечислены семьи, члены которых участвуют (не меньше двух),
   и переключатель «Учитывать семьи».

### User Story 3 — Заявки на вступление (Priority: P2)

Ссылку переслали дальше, чем нужно. Организатор включает «Вступление по одобрению». Человек переходит по ссылке, пишет
имя и получает «Заявка отправлена организатору». Админы получают сообщение с кнопками «✅ Принять» / «❌ Отклонить» и видят
заявки в панели эвента. После решения человек получает уведомление: принят (кнопка «Открыть») или отклонён.

**Why this priority**: Защита закрытой компании; без неё приходится удалять случайных людей вручную.

**Independent Test**: Эвент с одобрением: человек по ссылке → заявка; до одобрения он не участник (нет письма, нет в
жеребьёвке); «Принять» → участник и уведомление; другой — «Отклонить» → уведомление, не участник.

**Acceptance Scenarios**:

1. **Given** эвент с одобрением и открытой регистрацией, **When** человек переходит по ссылке, **Then** он регистрирует
   имя (если новый) и получает «⏳ Заявка отправлена»; в эвенте он не участник.
2. **Given** заявка ждёт, **When** админ нажимает «✅ Принять» (в чате или в панели), **Then** человек становится
   участником и получает «🎉 Тебя приняли в эвент «…»» с кнопкой; остальные админы видят, что заявка решена.
3. **Given** заявка ждёт, **When** админ нажимает «❌ Отклонить», **Then** человек получает «Организатор не одобрил
   заявку…», в эвент не попадает.
4. **Given** заявка уже решена другим админом, **When** админ нажимает кнопку старого сообщения, **Then** «Заявка уже
   рассмотрена» — повторного действия нет.
5. **Given** у человека уже есть ожидающая заявка, **When** он снова переходит по ссылке, **Then** новой заявки нет —
   «Заявка уже отправлена, ждём решения организатора».
6. **Given** жеребьёвка проведена или регистрация закрыта, **When** админ принимает ожидающую заявку, **Then** человек
   становится участником как «вступивший после жеребьёвки» (админ впишет его) — как и при обычном позднем вступлении.
7. **Given** одобрение выключено, **Then** вступление работает как раньше.

### Edge Cases

- Адрес длиннее 500 символов — отказ с числом символов.
- Адрес видит только Санта этой пары; после замены подопечного новый Санта видит адрес, прежний — нет.
- «Открыть письмо» у админа показывает письмо без адреса.
- Семья из одного человека в эвенте не влияет ни на что; в списке эвента не показывается.
- Удаление семьи не меняет уже проведённых жеребьёвок.
- Админ, который сам участник, может принять собственную заявку? Админу заявка не нужна: админ вступает сам («Я
  участвую»).
- Отклонённый человек может подать заявку снова, если регистрация открыта (админ получит новое сообщение).
- Удаление эвента и полный сброс удаляют его заявки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-801**: Эвент MUST иметь параметр «спрашивать адрес доставки» (по умолчанию выключен).
- **FR-802**: При включённом параметре участник MUST указывать «Как передать подарок» (до 500 символов) до завершения
  эвента; новое участие MUST предзаполняться последним указанным адресом человека.
- **FR-803**: Адрес MUST видеть только сам участник и его Санта в этом эвенте; ни один ответ админу, журнал или
  уведомление MUST не содержать текста адреса; админ видит только «указан / не указан».
- **FR-804**: Изменение адреса после жеребьёвки MUST уведомлять Санту тем же отложенным уведомлением, что и письмо.
- **FR-805**: Админы MUST создавать, переименовывать и удалять семьи (2–20 человек, название до 40 символов) и менять их
  состав; человек MUST состоять не больше чем в одной семье.
- **FR-806**: Эвент MUST иметь параметр «учитывать семьи» (по умолчанию включён, меняется до жеребьёвки); при включённом
  жеребьёвка и замены MUST не давать члену семьи дарить другому члену той же семьи.
- **FR-807**: Невозможность жеребьёвки из-за семей MUST объясняться админу.
- **FR-808**: Перенос участия на новый аккаунт MUST переносить членство в семье.
- **FR-809**: Эвент MUST иметь параметр «вступление по одобрению» (по умолчанию выключен).
- **FR-810**: При одобрении переход по ссылке MUST создавать заявку (не больше одной ожидающей на человека и эвент) и
  уведомлять всех админов с кнопками «Принять» / «Отклонить»; панель эвента MUST показывать ожидающие заявки.
- **FR-811**: Решение по заявке MUST приниматься один раз (атомарно), уведомлять человека и попадать в журнал.
- **FR-812**: Журнал (007) MUST включать действия с семьями, параметры 008 и решения по заявкам — без адресов.

### Key Entities

- **Участие**: + «Как передать подарок» и время его изменения.
- **Эвент**: + «спрашивать адрес», «учитывать семьи», «вступление по одобрению».
- **Семья**: название, кто создал; **Член семьи**: семья, человек (человек — не больше чем в одной семье).
- **Заявка**: эвент, человек, статус (ждёт / принята / отклонена), кто и когда решил.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-801**: 0 ответов админу с текстом адреса во всех сценариях (проверка сквозным тестом).
- **SC-802**: Повторный эвент той же компании не требует ни одного ручного исключения для семей, заведённых один раз.
- **SC-803**: 100% жеребьёвок и замен соблюдают семьи при включённом параметре (20 жеребьёвок в тесте).
- **SC-804**: Посторонний по пересланной ссылке не становится участником эвента с одобрением без действия админа.
- **SC-805**: Решение по заявке доходит до человека за одно нажатие админа.

## Assumptions

- Адрес — свободный текст; формат (почта, курьер, «заберу сам») не проверяется. Хранится, пока хранится эвент.
- Адрес не участвует в «Открыть письмо» у админа: если нужен организатору для логистики — участник сообщит сам.
- Семьи общие для бота (как роли); видят и меняют их все админы; участники семьи не видят.
- Членство в семье влияет только на будущие жеребьёвки и замены, не на проведённые пары.
- Заявки — только для новых участников эвента; админы вступают сами.
- Уведомление о заявке получают все зарегистрированные админы; отправка — через очередь, как остальные сообщения.
