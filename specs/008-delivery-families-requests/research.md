# Research: 008-delivery-families-requests

## R1. Где хранить адрес

- **Decision**: поле `members.delivery` (участие в эвенте), а не `users`. Новое участие предзаполняется последним
  непустым адресом человека (подзапрос в `addMemberStmt`).
- **Rationale**: адрес меняется (переезд), а история эвента должна показывать, куда отправляли тогда. Предзаполнение
  убирает повторный ввод (принцип II).
- **Alternatives**: адрес в профиле человека — проще, но тогда Санта прошлого эвента продолжал бы видеть новый адрес.

## R2. Уведомление Санте об адресе

- **Decision**: `delivery_updated_at` и общий механизм cron: `upd = MAX(wishlist_updated_at, delivery_updated_at)`,
  текст «обновил письмо или адрес». Дифф письма (`seen_text`) адрес не затрагивает — адрес показывается целиком.

## R3. Семьи в жеребьёвке

- **Decision**: `familyExclusions(db, ev, ids)` — пары (a, b) для членов одной семьи среди участников, если
  `ev.families_on`. Они добавляются к исключениям в `checkDraw`, `removeMember`, `insertMember`.
- Объяснение причины (FR-807): если жеребьёвка невозможна, а без семей возможна — первой строкой «Мешают семьи: …
  Выключи «Учитывать семьи» или кольцевую». Второй поиск только при неудаче.
- `admin.state.families` — семьи с не меньше чем двумя участниками эвента (имена берутся из `users`).
- Один человек — одна семья: `family_members.user_id` — PRIMARY KEY.

## R4. Заявки: атомарное решение

- **Decision**:
  - Таблица `join_requests` с частичным уникальным индексом `(event_id, user_id) WHERE status = 'pending'` — не больше
    одной ожидающей заявки.
  - Решение — batch: `UPDATE join_requests SET status, decided_by, decided_at WHERE id = ? AND status = 'pending'`;
    добавление участника, уведомления и журнал — с условием `EXISTS (… status = ? AND decided_by = ? AND decided_at = ?)`.
    Повторное нажатие (или второй админ) ничего не меняет: «Заявка уже рассмотрена».
  - Новый человек: `/start inv_…` → ввод имени → заявка (админам уходит уже с именем). Зарегистрированный — заявка сразу.
  - Админы и владелец заявок не подают: вступают сразу.
- Сообщение админам: «🙋 <имя> просится в эвент «…»» с кнопками `req:<id>:a` / `req:<id>:r` и кнопкой приложения.
  Решивший получает ответ на нажатие, остальные — тихое «… принял(а)/отклонил(а) заявку».

## R5. Перенос, сброс, удаление

- Перенос: `UPDATE OR IGNORE family_members SET user_id` + удаление старой записи; заявки переходят на новый аккаунт.
- Полный сброс и удаление эвента удаляют его заявки; сброс возвращает `delivery_on = 0`, `families_on = 1`, `approval = 0`.
