# 063. Research — решения

## R1. Организаторы события — таблица `event_admins`, владелец — в ней же

- **Решение.** Новая таблица `event_admins (event_id, user_id, created_at)`, ключ `(event_id, user_id)`, индекс по
  `user_id`. Владелец события (`events.owner_id`) **всегда** есть в `event_admins` (инвариант E1). «Организатор события»
  в SQL — `EXISTS (SELECT 1 FROM event_admins …)`, «владелец» — `events.owner_id`.
- **Почему.** Организатор может не участвовать (флаг на `members` не подходит). Владелец в той же таблице упрощает все
  условия «организаторы события» (получатели сообщений, счётчики обращений, правило Г брошенных событий, «мои события»):
  одно `EXISTS` вместо «или владелец». Передача владения по спецификации оставляет прежнего владельца организатором —
  ровно то, что даёт «владелец в таблице»: меняется только `owner_id`.
- **Отклонено.** Флаг `members.is_admin` — организатор-неучастник невозможен. Отдельная колонка «роль» в таблице —
  избыточна при `owner_id`.

## R2. Владелец события — `events.owner_id`; 0 — «владелец бота» только для старых данных

- **Решение.** Колонка `events.owner_id INTEGER NOT NULL DEFAULT 0`. Новый код всегда пишет создателя. Миграция:
  назначенный владелец комнаты, иначе `settings.owner_id`, иначе 0. `ctx.at(ev).ownerId()` = `owner_id || владелец бота`
  (как `company.owner_id || botOwnerId` в 051) — только для бота без владельца на момент миграции.
- **Передача прав владельца бота** события не двигает: они принадлежат человеку (спецификация, крайние случаи).

## R3. Контекст события `ctx.at(ev)` вместо контекста компании `ctx.in(companyId)`

- **Решение.** Привязанный контекст (как 050) — к событию: `ctx.at(ev)` → `null` нет никогда (событие уже прочитано);
  `event`, `me.is_admin` (организатор этого события или владелец бота), `users()` — люди события (участники ∪
  организаторы; владелец бота без строки — гость, как в 050), `is_admin` у человека — организатор этого события,
  `ownerId()`, `isOwner()` (владелец события или владелец бота), `ownerWord()` (`owner_id = 0` → «владелец бота»),
  `read({ users })`. Один объект на событие за вызов.
- **Почему.** Модули уже написаны против привязанного контекста (`users()`, `adminRecipients`, `ownerId()`,
  `isOwner()`): смена «компания → событие» почти не трогает их код — меняются запросы людей и место привязки. У общего
  контекста по-прежнему нет людей и владельца (ошибка «контекст без события»).
- **Отклонено.** Хранить «комнату на событие» (`company_id` = своя компания каждого события): быстро, но оставило бы в
  коде всё про компании (названия, ссылки, `company_members`) и усложнило бы образцы и историю пар.

## R4. Общий признак `users.is_admin` остаётся: «организатор хотя бы одного события или владелец бота»

- **Решение.** `adminFlagStmt` считает его по `event_admins` и настройке `owner_id`; пересчёт — в пакетах создания
  события, назначения, снятия, передачи владения, удаления события, передачи прав владельца бота (как в 050 для
  компаний). Признак нужен там же, где сейчас: первая проверка конвейера `admin.*`, меню бота, запрет цели переноса
  участия.
- **Почему.** Меньше изменений конвейера и эталона отказов: участник без организаторства получает прежний 403 «Только
  для администратора.» до чтения события.
- **Новое в конвейере.** Организатор другого события, обращаясь к событию, где он не организатор: участник этого
  события — 403 «Только для администратора.», иначе — 404 «Событие не найдено.» (чужое событие — как несуществующее).

## R5. Лимит — таблица фактов создания `event_creations`

- **Решение.** `event_creations (event_id PRIMARY KEY, user_id, created_at)`, индекс `(user_id, created_at)`. Строка
  пишется в пакете создания события и не удаляется ни удалением события, ни сбросом (REGISTRY: `onEventDelete: 'keep'`);
  перенос участия переносит её (`ACTOR`). Лимит — `LIMIT_EVENTS = 10` за `LIMIT_MS = 365 суток`: вставка события с
  условием `(SELECT COUNT(*) FROM event_creations WHERE user_id = ? AND created_at > ?) < 10` (владельцу бота условие не
  ставится). Остальные операторы пакета — по коду приглашения нового события (как сейчас). Отказ — по свежему счёту.
- **Миграция и сверка** — `INSERT OR IGNORE … SELECT id, created_by, created_at FROM events WHERE created_by != 0`:
  идемпотентно (ключ — событие), так же работает сверка после выката.
- **Отклонено.** Считать по журналу бота: записи журнала — для показа; сверка «событие без записи журнала» потребовала
  бы совпадения времени; отдельная таблица проще и проверяема.
- **«Следующее можно создать»** — `MIN(created_at)` из окна + 365 суток (одним запросом со счётом).

## R6. Закрытый бот — `users.can_create`

- **Решение.** Колонка `users.can_create INTEGER NOT NULL DEFAULT 0`. В закрытом боте создать событие может владелец
  бота или человек с `can_create = 1` (условие — в пакете вставки, как лимит). Меняет только владелец бота
  (`bot.creator.set`, по прежнему состоянию, сообщение человеку, журнал бота `creator.grant`/`creator.revoke`).
  Миграция — 1 всем администраторам комнат и назначенным владельцам комнат (в обе базы: открытый бот колонку не читает).
  Перенос участия: `MAX` (как `is_admin`).

## R7. История «не повторять пары» — по владельцу

- **Решение.** `previousPairsQuery`: прошлые события с тем же `owner_id`, созданные не позже текущего, правило выбора
  прежнее (больше всего пар среди этих людей, при равенстве — новее). Индекс `events_owner (owner_id, created_at)`.
- **Почему.** Решение владельца (4). Тайна: владелец события и так может открыть пары своих прошлых событий служебным
  просмотром, поэтому предупреждения обмена (048) о прошлых парах не выдают ему чужого. Чужие владельцы — не влияют.
- **Следствие** (записано в спецификации): событие по образцу, который вёл другой человек, историю образца не
  учитывает.

## R8. Действия API: 73 → 69

| Было | Стало |

## R9. Журналы

- **Сфера записи** — событие (число) или `BOT_LOG`; `{ company }` убирается. Новые записи пишут `company_id = 0`.
- **Журнал бота** = все записи с `event_id = 0`: туда попадают и прежние общие записи комнат — история.
  `bot.audit` читает `WHERE event_id = 0` (063: по прежнему индексу `audit_event (event_id, id)` — отдельный `audit_bot` не понадобился).
- **Куда пишется**: `role.grant`, `role.revoke`, `event.owner` (новый код — передача владения) — журнал события;
  `event.create` — и журнал события, и журнал бота («<название>»); `event.delete`, `transfer`, `rename` (владелец бота),
  `owner.transfer`, `owner.link`, `creator.grant`, `creator.revoke` — журнал бота. `name.set` журнал не пишет.
- **Прежние коды** `company.create`, `company.owner`, `company.link`, `company.delete` — не пишутся, подписи остаются
  для истории (как семьи в 062).

## R10. «Мои события» и главный экран

- `myEventsQuery` = участник ∪ организатор (`event_admins`); владельцу бота — то же (решение 1а). Роль события —
  `owner` (`owner_id`), `admin` (строка организатора), иначе `member`.
- `me.create`: владельцу бота — `{ bot: true }`; можно создавать — `{ left, limit: 10, next }` (`next` — когда
  освободится место, только при `left = 0`); нельзя (закрытый бот без разрешения) — поля нет.
- `me.companies`, `event.company`, `events[].company` — убираются.

## R11. Владелец бота: «Все события»

- `bot.events { offset }` → `{ events: [{ id, title, status, event_date, owner_name, people }], more }` — страница 50,
  новые первыми (`ORDER BY id DESC LIMIT 51 OFFSET ?`), `people` — участники (подзапрос по `members` первичного ключа).
  Открытие — обычный `event.get`/`admin.state` (владелец бота — организатор любого события, гость).
- `bot.people` → `{ people: [{ id, name, username, can_create }] }`: закрытый бот — все зарегистрированные (бот
  маленький: регистрация только по ссылкам); открытый — люди событий владельца бота (участники и организаторы событий,
  где он организатор). Кандидаты передачи прав владельца бота и список «Кто может создавать события».
- `bot.owner.transfer`: цель — любой зарегистрированный (кроме себя); сообщения — новому владельцу бота; журнал бота.

## R12. Перенос участия (только владелец бота)

- Запрещён перенос записи владельца бота (`api.ownerNotTransferred`); владелец события и организаторы переносятся:
  `events.owner_id`, `event_admins`, `event_creations` — по REGISTRY (`ACTOR`/`dedupe`). Цель — не организатор нигде и
  не владелец бота (общий признак `is_admin`, как раньше). Сообщения — организаторам событий старой записи (участник или
  организатор), журнал бота — одна запись `transfer`.

## R13. Перенос данных и откат

- Миграция `0024_events_without_rooms.sql` (схема 24): колонки `events.owner_id`, `users.can_create`; таблицы
  `event_admins`, `event_creations`; заполнение по R1, R2, R5, R6; индексы. Прежний код (062) со схемой 24 работает
  (новые колонки — с умолчанием, новые таблицы он не читает).
- Сверка `tools/rooms-reconcile.sql` после выката: события, созданные прежним кодом между миграцией и выкатом
  (`owner_id = 0 AND company_id != 0`), получают организаторов и владельца по правилу миграции; факты создания —
  `INSERT OR IGNORE`. Повтор ничего не меняет. Назначения админов комнат, сделанные прежним кодом в этом окне для уже
  перенесённых событий, не переносятся (окно — минуты; описано в `quickstart.md`).
- Новый код пишет `events.company_id = 0` и `audit.company_id = 0`: после отката на 062 новые события не видны и не
  попадают в комнату №1 (иначе их увидели бы её администраторы). Откат безопасен сразу; позже — новые события и
  назначения прежний код не видит (возврат на 063 их возвращает).

## R14. Бот

- `/start own_<код>` — «Эта ссылка больше не действует. Попроси у организатора пригласительную ссылку на событие.» и
  меню (или просьба имени незнакомцу открытого бота); ожидание `name_own:…` после имени — обычная регистрация с тем же
  текстом. `companyByOwnerCode`, `claimCompanyOwner` убираются.
- Меню: без названий комнат; строка роли — только «владелец бота»; текст без событий: можно создавать — «Создай своё
  событие в приложении или попроси пригласительную ссылку», нельзя — прежний.
- Вступление по ссылке больше не пишет `company_members` (`joinCompanyStmt` убирается).

## R15. Приложение

- Корень — `view: 'home'` (список); `view: 'settings'` — экран «Настройки»; `view: 'event'`. Экран и часть «Компании»
  (`04-companies`) заменяются частью `04-settings` (настройки, раздел владельца бота, «Все события», «Кто может
  создавать»). `withList`, `listFirst`, `capi`, `enterCompany`, `companyTitle`, `goCompanies` убираются; права события —
  `enterEvent(role)` из `event.get` (`event.role`: `owner` | `admin` | `member` | `guest`; владелец бота — права
  владельца везде).
- Кнопка «Создать» — новый компонент дизайн-системы `ds-bottom-bar` (закреплён внизу, отступ под «домашнюю полосу»
  `env(safe-area-inset-bottom)`, у страницы — `ds-page--bar`, чтобы список не уходил под кнопку). Шапка — кнопка
  «⚙️» справа (`ds-hero__action`). «Завершённые · N» — существующий `ds-details`.
- «Организаторы» — секция панели события `adminOrganizers(p)` (`06-admin`), данные — из `admin.state` (`organizers`,
  кандидаты — участники). Переименование участника в панели — только владельцу бота.
