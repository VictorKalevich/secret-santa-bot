# Research: Исправление багов и рефакторинг (009)

Все решения — без изменения схемы базы (`REQUIRED_SCHEMA` остаётся 8). Лимиты бесплатного тарифа уточнены по
документации Cloudflare: 50 внешних запросов на вызов (запросы к D1 входят; `db.batch()` — один запрос независимо от
числа операторов), 10 мс CPU на HTTP-запрос и на вызов cron, не больше 100 параметров в одном SQL-запросе.

## R1. Счётчик внешних запросов на вызов

- **Decision**: `src/budget.js` оборачивает `env` в начале каждого вызова (`fetch` и `scheduled`): привязка `DB`
  заменяется тонкой обёрткой, которая считает `first/all/run/raw` и `batch` (по одному на вызов), а `tgApi` считает
  каждый `fetch`. Счётчик живёт в `env.meter = { used, enqueued }`. `flushOutbox` перед каждым кругом берёт из очереди не
  больше, чем осталось в бюджете с запасом на завершающий `batch`. Если вызов всё же превысил лимит (можно только в
  `wrangler dev`, где лимит не применяется), в журнал Worker пишется `budget exceeded` — e2e проверяет, что таких строк нет.
- **Rationale**: Расчёт «на бумаге» ломается при каждом новом пути (ревью нашло три). Счётчик делает отправку очереди
  самоограничивающейся и даёт проверяемую метрику (SC-903).
- **Alternatives**: статические лимиты отправки по каждому пути (хрупко); отдельный тестовый эндпоинт со счётчиком
  (тестовый код в проде); оборачивать `fetch` глобально (затрагивает чужие вызовы).

## R2. Единая точка отправки очереди

- **Decision**: отправка запускается один раз в `index.js` после обработчика: `/tg` и `/api/*` — если обработчик что-то
  поставил в очередь (`meter.enqueued`, флаг ставят `enqueueStmt`/`enqueueIfStmt`), через `ctx.waitUntil`; cron — в
  конце `runScheduled`. Все `ctx.waitUntil(flushOutbox(...))` внутри бота, API и игровой логики удаляются.
- **Rationale**: раньше отправка стартовала в середине обработки и шла параллельно с остальными запросами вызова —
  бюджет нельзя было посчитать; теперь к моменту отправки остальная работа закончена.
- **Alternatives**: всегда запускать отправку (лишний запрос на каждый опрос переписки раз в 6 секунд).

## R3. Плановый запуск: изоляция шагов и «одно тяжёлое действие»

- **Decision**: `runScheduled` выполняет шаги `notify` → `daily` → отправка, каждый в `try/catch` с записью в журнал
  Worker. Шаг `daily` (после часа напоминаний) собирает кандидатов: эвенты с наступившим автодействием и эвенты, которым
  сегодня нужна рассылка напоминаний (ещё не отмеченные `last_daily`). Эвенты без рассылки отмечаются `last_daily` одним
  `UPDATE … WHERE id IN (…)`. Из кандидатов выполняется один: по кругу по номеру минуты (`minuteOfDay % N`, автодействия
  в списке первыми) — так постоянно падающий кандидат не блокирует остальные. Напоминание пишет `last_daily` в том же
  `batch`, что и рассылку: либо всё, либо ничего (без потерь и дублей при сбое).
- **Rationale**: тяжёлое действие ≤ ~10 запросов; основа запуска ≤ 6; остальное — очереди. Утренние напоминания при
  многих эвентах растягиваются на минуты — приемлемо.
- **Alternatives**: считать бюджет и делать столько эвентов, сколько влезет (сложнее, а выигрыш — минуты).

## R4. Режим ответа в переписку

- **Decision**: формат `users.pending` для ответа: `msg_ward:<eid>:<id собеседника>:<ms нажатия>` (и `msg_santa:…`).
  Любая команда (`/…`) при активном режиме ответа сбрасывает его до обработки самой команды. Отказ при нажатии
  «↩️ Ответить» сбрасывает прежний режим. При тексте: старый формат или прошло больше 60 минут → «время истекло»;
  собеседник по текущей паре ≠ сохранённому → «пара изменилась». `sendChatMessage` получает необязательное ожидаемое
  `other` и проверяет его.
- **Rationale**: id собеседника хранится только на сервере (поле не отдаётся ни в одном ответе) — тайна не страдает.
- **Alternatives**: отдельная колонка с временем (миграция ради одного поля); отправка по старой паре (тайна и логика
  переписки сломаются).

## R5. Вход по ссылке — одна функция для ссылки и ввода имени

- **Decision**: `joinByInvite(env, ev, user)` в `src/membership.js` возвращает исход: `already` | `joined` | `closed` |
  `request_sent` | `request_pending` | `request_rejected` и сама ставит в очередь уведомление админам о вступлении (в
  одном `batch` с добавлением участника). Бот только выбирает текст. Режим регистрации хранит и код приглашения:
  `name:<eid>:<invite_code>`; если ссылку за это время сменили — после имени бот отвечает «ссылка устарела» (иначе смена
  ссылки не останавливала бы удалённого «чужого»). Человек, добавленный в эвент при открытии ссылки (до ввода имени),
  после имени получает приветствие, а админы — «присоединяется».
- **Rationale**: два пути с разными правилами и были источником бага.
- **Alternatives**: проверять только членство после имени (остаётся расхождение с правилами ссылки).

## R6. Пауза после отклонённой заявки

- **Decision**: перед созданием заявки — `SELECT 1 FROM join_requests WHERE event_id=? AND user_id=? AND
  status='rejected' AND decided_at > now − 24 ч`; если есть — исход `request_rejected`, админам ничего.
- **Alternatives**: запретить навсегда (человек не сможет вступить после ошибочного отказа).

## R7. Атомарность раскрытия и завершения

- **Decision**: как жеребьёвка 006 — первый оператор `batch` «занимает» действие уникальным значением, остальные
  выполняются только при нём. Раскрытие: `UPDATE events SET revealed = <now> WHERE id=? AND revealed = 0 AND
  draw_done = 1`, рассылка и журнал — `enqueueIfStmt`/`auditIfStmt` с условием `revealed = <now>`. Завершение:
  `UPDATE … SET status='finished', finished_at=<now> … WHERE status='active'`, условие `status='finished' AND
  finished_at=<now>`. Проигравший запрос: `changes = 0` → «Тайна уже раскрыта» / «Эвент уже завершён».
- **Rationale**: поле `revealed` везде читается как логическое (`!!`, `!ev.revealed`), момент раскрытия совместим.

## R8. Версия пар и снимок состава при жеребьёвке

- **Decision**:
  - удаление и вписывание после жеребьёвки: первый оператор `UPDATE events SET draw_token = <новый> WHERE id=? AND
    draw_token = <прочитанный> AND draw_done = 1`, все остальные (включая удаление участника, переписки, уведомления,
    журнал) — с условием `draw_token = <новый>`; при `changes = 0` → «Пары изменились одновременно с этим действием —
    попробуй ещё раз». Отмена жеребьёвки уже сверяет `draw_token` — совместимо.
  - жеребьёвка: условие захвата дополняется снимком того, на чём строился расчёт: число и сумма id зарегистрированных
    участников, число исключений эвента, `ring` и `families_on`. Не совпало → «Состав эвента изменился — попробуй ещё раз».
- **Rationale**: без новых полей; сумма id + число — достаточно для гонки «удалили во время жеребьёвки»; параметры в
  `IN (…)` не нужны (лимит 100 параметров).
- **Alternatives**: счётчик версии в отдельной колонке (миграция); `IN (список id)` (упирается в лимит параметров).

## R9. Тайна: заморозка ограничений после жеребьёвки

- **Decision**:
  - `admin.exclusion.add/del` при `draw_done` → 400 «После жеребьёвки исключения не меняются…»; интерфейс показывает
    исключения только для чтения.
  - `admin.family.save/delete` → 400, если кто-то из людей, чьё членство меняется (добавленные и удалённые; при
    удалении семьи — все её члены), участвует в эвенте `status='active' AND draw_done=1 AND families_on=1`; текст
    называет эвент. Переименование семьи без смены состава разрешено.
  - `admin.insert` с `id = me` → 400 «Вписать себя нельзя — попроси другого администратора».
  - `admin.draw.check` и `admin.draw` не возвращают `history_used`/`history_ignored`.
- **Rationale**: замены используют текущие ограничения; если их можно менять после жеребьёвки, отказ/успех замены —
  ответ «да/нет» на вопрос о паре. Семьи глобальны, поэтому блокируются точечно.
- **Alternatives**: снимок ограничений на момент жеребьёвки (новая таблица); игнорировать семьи при заменах (нарушит
  правило семей).

## R10. Адрес доставки при вступлении

- **Decision**: `addMemberStmt(db, ev, userId, guard?)` копирует последний адрес только при `ev.delivery_on`; принимает
  необязательное условие (для решения по заявке) — одна функция вместо двух копий SQL.

## R11. Жеребьёвка: общий бюджет и честные причины

- **Decision**: логика попыток переезжает в чистую функцию `planDraw` в `src/draw.js` (тестируется в Node): бюджет
  `B = DEFAULT_BUDGET` делится так: объяснение «мешают семьи» — `B/4` (если семьи есть), остальное — основной поиск; при
  прошлых парах основной делится пополам между попыткой «с историей» и «без истории». Текст `ring_impossible` смягчается:
  «Похоже, без взаимных пар не обойтись… Попробуй ещё раз; если не выйдет — …» (это результат поиска, а не доказательство).
- **Rationale**: замер в Node: три полных поиска — 6–7,5 мс против ~2 мс одного; с общим бюджетом — в пределах одного.

## R12. Telegram: таймаут и разрыв символов

- **Decision**: `fetch` к Bot API с `AbortSignal.timeout(10000)` (поддерживается Workers). Обрезка текстов кнопок —
  `shortTitle` (по кодовым точкам). Имитация Telegram в тестах отвечает 400 на строки с одиночными суррогатами — так e2e
  ловит такие ошибки.

## R13. Меню бота одним запросом

- **Decision**: один `SELECT` по `members` + `events` с `EXISTS` по `pairs` (как Санта и как подопечный).

## R14. Мини-приложение

- **Decision**:
  - счётчик навигации `state.nav`: каждый экран при построении берёт номер; после `await` и перед перерисовкой по итогам
    действия сверяет его и молча выходит, если пользователь ушёл; экраны эвента вызывают API с `evId`, сохранённым при
    построении;
  - `showError(e, retry)` — кнопка повторяет переданную загрузку; при ошибке открытия эвента — ещё «К списку эвентов»;
  - переписка: `lastId` двигается только по ответам `chat.get`; после отправки — `load()`; пузырьки вставляются по id;
  - журнал — обычная шторка (у неё уже есть прокрутка);
  - помощник `bindToggle(input, fn)`: блокировка на время запроса, откат при ошибке;
  - письмо: сохраняется снимок текста до запроса; `reloadEvent` обновляет `state.member` на месте (`Object.assign`);
    адрес участвует в «несохранённом»; закрытие чата с черновиком — подтверждение; черновики объявления и параметров
    хранятся в `state.drafts[evId]`;
  - админ по умолчанию открывает «Письмо» (участник) или «Админ» (не участник), не «Подопечный»;
  - после `busy` кнопки пересчитывают доступность (`update()`);
  - кэш последнего `ward.get` по эвенту — после закрытия чата вкладка «Подопечный» перерисовывается из него;
  - подтверждение жеребьёвки: сначала важное, вместо списка имён — число; ≤ 250 символов;
  - системная кнопка «Назад»: один обработчик — закрыть шторку или вернуться к списку (с проверкой несохранённого);
  - `aria-label` переключателя = подпись строки.
- **Rationale**: всё — в рамках существующих компонентов дизайн-системы; новых токенов и компонентов нет.

## R15. Модули вместо `src/game.js`

- **Decision** (поведение не меняется; первым шагом — перенос без правок, затем исправления):

  | Модуль | Что внутри |
  |---|---|
  | `src/format.js` | `escapeHtml`, `msg`, `q`, `shortTitle`, даты (`formatDate`, `formatMs`, `addDays`, `ISO_DATE`, `localDate`), `displayName`, `cleanText`, `appUrl`, `openAppButton`, `inviteLink`, `randomCode` |
  | `src/budget.js` | счётчик запросов (R1) |
  | `src/outbox.js` | `flushOutbox` |
  | `src/pairs.js` | проверка/проведение/отмена жеребьёвки, удаление и вписывание с перестройкой пар |
  | `src/events.js` | жизненный цикл эвента, раскрытие, напоминания, объявления, автодействия, `isFinished`/`chatWritable` |
  | `src/chat.js` | переписка, непрочитанные, `MAX_CHARS` |
  | `src/roles.js` | владелец и админы, адресаты-админы (`adminRecipients`), перенос участия |
  | `src/membership.js` | вступление по ссылке (R5), заявки, семьи |
  | `src/bot.js` | + `menuMessage` (раньше в game.js) |

  `api.js` больше не импортирует `bot.js` (`sendAnonymous` заменён прямым `sendChatMessage`). Ни один модуль логики не
  длиннее ~400 строк.
- **Alternatives**: оставить один файл (растёт с каждой фичей); дробить мельче (лишние импорты без выигрыша).
