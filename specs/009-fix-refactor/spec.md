# Feature Specification: Исправление багов и рефакторинг перед первым выкатом

**Feature Branch**: `009-fix-refactor`

**Created**: 2026-11-12

**Status**: Draft

**Input**: User description: "Бот ещё ни разу не выкатывался. Проанализировать функционал и архитектуру, найти и исправить баги,
сделать рефакторинг кода. Новых функций не добавлять." Источники находок: собственный анализ кода и два независимых
ревью (серверная часть; мини-приложение). Решения, принятые без уточняющих вопросов, — в разделе Assumptions.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Админ не может вычислить пары (Priority: P1)

Принцип I конституции: администратор не видит пар. Ревью нашло обходные пути через инструменты организатора:

- **Исключения и семьи после жеребьёвки как «оракул».** После жеребьёвки админ может добавить исключения (или собрать
  семью) так, чтобы опоздавшего участника X можно было вписать только в связку «S → W», и нажать «Вписать в жеребьёвку».
  Отказ ничего не меняет и доказывает, что S не дарит W; повторяя, админ находит подопечного S. Так же через
  «Вписать» самого себя админ выбирает себе Санту и узнаёт чужие пары.
- **Прошлые пары через проверку жеребьёвки.** Ответ проверки сообщает, удалось ли учесть пары прошлого эвента. Подбирая
  исключения и повторяя проверку, админ восстанавливает пары прошлого (нераскрытого) эвента.
- **Адрес доставки в эвенте, который его не спрашивал.** При вступлении в любой эвент адрес молча копируется из прошлого
  участия; если организатор позже включит «спрашивать адрес», Санта увидит адрес, который человек в этом эвенте не давал.

После исправления после жеребьёвки исключения эвента не меняются, семьи её участников не меняются, пока эвент идёт,
вписать себя нельзя, проверка жеребьёвки не говорит о прошлых парах, а адрес предзаполняется только в эвенте,
который его спрашивает.

**Why this priority**: Нарушение NON-NEGOTIABLE принципа «Тайна по умолчанию».

**Independent Test**: После жеребьёвки добавить исключение → отказ; изменить семью участника идущего эвента с
жеребьёвкой → отказ; админ вписывает себя → отказ; ответ проверки жеребьёвки не содержит признаков прошлых пар;
человек с адресом в эвенте A вступает в эвент B без адреса → адрес в B пуст.

**Acceptance Scenarios**:

1. **Given** жеребьёвка проведена, **When** админ добавляет или удаляет исключение, **Then** отказ «После жеребьёвки
   исключения не меняются», исключения прежние.
2. **Given** человек из семьи участвует в идущем эвенте с проведённой жеребьёвкой и включённым правилом семей,
   **When** админ меняет или удаляет эту семью (или добавляет в неё этого человека), **Then** отказ с названием эвента;
   после завершения эвента изменение проходит.
3. **Given** админ вступил в эвент после жеребьёвки, **When** он нажимает «Вписать в жеребьёвку» для себя, **Then** отказ
   «Вписать себя нельзя — попроси другого администратора».
4. **Given** «не повторять пары прошлого эвента» включено, **When** админ проверяет или проводит жеребьёвку, **Then**
   ответ не сообщает, удалось ли учесть прошлые пары.
5. **Given** человек указал адрес в эвенте A, **When** он вступает в эвент B, который адрес не спрашивает, **Then** в B
   адрес пуст; **When** вступает в эвент C, который адрес спрашивает, **Then** адрес предзаполнен (как в 008).

### User Story 2 — Рассылка не останавливается, не дублируется и укладывается в лимит (Priority: P1)

Бот раз в минуту отправляет очередь, уведомления об изменении писем, напоминания и автодействия расписания. Сейчас
ошибка в любом шаге обрывает весь плановый запуск — очередь перестаёт уходить. При двух-трёх эвентах с напоминаниями в
один день (обычная ситуация: «семья» и «работа») или с автодействием плановый запуск превышает лимит 50 внешних
запросов бесплатного тарифа: последний шаг отправки падает, уже отправленные сообщения через минуту уходят повторно —
дубли у десятков человек. То же возможно в чате бота: владелец по ссылке /setup или участник по приглашению с
несколькими эвентами. Зависший запрос к Telegram держит пачку дольше времени захвата — дубли и нарушение порядка.

После исправления шаги независимы, каждый вызов знает, сколько запросов уже потратил, и отправляет из очереди ровно
столько, сколько помещается в лимит; тяжёлые действия по эвентам выполняются по одному за запуск, остальные — в
следующие минуты; запрос к Telegram ограничен по времени.

**Why this priority**: Очередь — единственный путь любых сообщений другим людям.

**Independent Test**: Три эвента с напоминаниями в один день → каждый адресат получил ровно одно напоминание; ни один
вызов не превысил 50 запросов (по счётчику вызова). Ошибка в шаге автодействия → очередь в том же запуске отправлена.

**Acceptance Scenarios**:

1. **Given** в трёх идущих эвентах сегодня напоминания, **When** наступает час напоминаний, **Then** каждый участник без
   письма получает ровно одно напоминание по каждому своему эвенту, и ни один плановый запуск не превышает 50 запросов.
2. **Given** в одном шаге планового запуска ошибка, **When** запуск продолжается, **Then** остальные шаги и отправка
   очереди выполняются, ошибка записана в журнал Worker.
3. **Given** автодействие и напоминания в один час, **When** плановые запуски, **Then** сначала автодействие, напоминания
   — в следующих запусках, без потерь и дублей.
4. **Given** владелец открывает ссылку /setup, участник с пятью эвентами открывает приглашение, **When** бот отвечает,
   **Then** ответ и отправка очереди укладываются в 50 запросов.

### User Story 3 — Случайный текст не уходит в переписку (Priority: P1)

Участник нажимает «↩️ Ответить» (Санте или подопечному) и передумывает. Сейчас режим ответа живёт бессрочно, не
сбрасывается ни /start, ни отказом при следующем нажатии; любой текст боту через день уйдёт анонимно. Кроме того, если
за это время пара сменилась (удаление, вписывание, отмена и новая жеребьёвка), текст «про Аню» уйдёт новому собеседнику.

После исправления режим ответа отменяется любой командой, сбрасывается при отказе, истекает через час и привязан к
конкретному собеседнику: если пара сменилась, текст не отправляется.

**Why this priority**: Сообщение, ушедшее не тому адресату, нельзя вернуть.

**Independent Test**: «Ответить» → /start → текст: никому не доставлен. «Ответить», прошло 2 часа → текст не
доставлен, бот объясняет. «Ответить», затем пара сменилась → текст не доставлен.

**Acceptance Scenarios**:

1. **Given** участник нажал «↩️ Ответить», **When** он отправляет /start или другую команду, **Then** режим отменён,
   следующий текст никому не пересылается.
2. **Given** прошло больше часа, **When** участник пишет текст, **Then** текст не пересылается, бот отвечает «Время
   ответа истекло — нажми «↩️ Ответить» ещё раз».
3. **Given** нажатие «↩️ Ответить» отклонено («нет подопечного», «переписка закрыта», «эвент не найден»), **When**
   участник пишет текст, **Then** текст не уходит прежнему собеседнику.
4. **Given** после нажатия «↩️ Ответить» собеседник сменился, **When** участник пишет текст, **Then** текст не
   пересылается, бот просит нажать «Ответить» заново.
5. **Given** участник нажал «↩️ Ответить» и в течение часа пишет текст, **When** пара та же, **Then** доставлено как раньше.

### User Story 4 — Вход по ссылке и меню бота работают всегда (Priority: P2)

- Участник повторно открывает приглашение после жеребьёвки (регистрация закрыта) — сейчас «Регистрация закрыта», после
  исправления — «Ты уже участвуешь».
- Человека удалили из эвента до ввода имени — сейчас после ввода имени он получает «напиши письмо», а админы —
  «присоединяется». После исправления вход проверяется заново теми же правилами, что и по ссылке.
- Отклонённый по заявке человек каждым /start создаёт новую заявку и снова пишет всем админам. После исправления новая
  заявка после отклонения — не раньше чем через сутки.
- Название эвента с эмодзи: обрезка в кнопке меню может разорвать эмодзи — Telegram отклоняет всё меню.

**Why this priority**: Первые минуты знакомства с ботом; тупик или молчание стоят участника.

**Independent Test**: Участник после жеребьёвки открывает ссылку → «уже участвуешь». Эвент с эмодзи в названии → меню
приходит. Отклонённый повторно открывает ссылку → «заявка отклонена», админам ничего.

**Acceptance Scenarios**:

1. **Given** участник эвента, регистрация закрыта или эвент завершён, **When** он открывает приглашение, **Then** «Ты уже
   участвуешь в эвенте …» и меню.
2. **Given** человек начал регистрацию по ссылке и был удалён из эвента, **When** он вводит имя, **Then** регистрация
   завершена; в эвент он вступает, только если вступление по ссылке сейчас разрешено (или подаёт заявку); «присоединяется»
   админы получают только при фактическом вступлении.
3. **Given** заявку отклонили меньше суток назад, **When** человек снова открывает приглашение, **Then** ответ «Заявку
   отклонили…», новой заявки и сообщений админам нет.
4. **Given** название эвента из 80 символов с эмодзи, **When** участник с подопечным открывает меню, **Then** меню
   доставлено, эмодзи не разорваны.

### User Story 5 — Одно действие — один результат (Priority: P2)

- Раскрытие тайны и завершение эвента могут прийти одновременно вручную и по расписанию: сейчас участники получают
  «твой Санта — …» или «эвент завершён» дважды.
- Два админа одновременно удаляют (или вписывают) участников после жеребьёвки: пары считаются по устаревшему снимку,
  в итоге у кого-то нет подопечного или подопечный — удалённый человек, без ошибки.
- Жеребьёвка во время удаления участника: удалённый человек попадает в пары.

После исправления каждое такое действие выполняется целиком или не выполняется вовсе; проигравший запрос получает
понятный отказ «уже …» или «состав изменился — попробуй ещё раз».

**Why this priority**: Редкие гонки, но последствия — дубли в праздничный момент или сломанная цепочка подарков.

**Independent Test**: Два одновременных раскрытия → одно сообщение каждому подопечному. Два одновременных удаления после
жеребьёвки → у каждого оставшегося ровно один подопечный и один Санта.

**Acceptance Scenarios**:

1. **Given** жеребьёвка проведена, **When** два раскрытия одновременно, **Then** по одному сообщению, второй — «Тайна уже
   раскрыта».
2. **Given** идущий эвент, **When** два завершения одновременно, **Then** по одному сообщению, второй — «Эвент уже
   завершён».
3. **Given** жеребьёвка проведена, **When** два изменения пар одновременно, **Then** одно применено, второе отклонено
   «Пары изменились одновременно с этим действием — попробуй ещё раз»; распределение корректно.
4. **Given** жеребьёвка запущена, **When** параллельно удалён участник, **Then** либо жеребьёвка без него, либо отказ
   «Состав эвента изменился — попробуй ещё раз».

### User Story 6 — Жеребьёвка укладывается в лимит CPU и честно объясняет отказ (Priority: P2)

С 008 проверка жеребьёвки может трижды подряд тратить полный бюджет поиска (с прошлыми парами, без них, для объяснения
«мешают семьи»). После исправления все попытки вместе укладываются в один бюджет. Кроме того, если кольцевое
распределение не нашлось за отведённые попытки, бот говорит «не удалось подобрать, попробуй ещё раз», а не «невозможно».

**Why this priority**: Ошибка сервера в момент жеребьёвки; вероятна только на сложных наборах.

**Independent Test**: 50 участников, кольцевая, семьи и прошлые пары → проверка в пределах одного бюджета.

**Acceptance Scenarios**:

1. **Given** все три попытки нужны, **When** проверка, **Then** суммарные вычисления — в пределах одного бюджета.
2. **Given** обычные ограничения, **When** жеребьёвка, **Then** проходит, как раньше.

### User Story 7 — Мини-приложение не путает эвенты и не теряет ввод (Priority: P2)

- **Чужой экран.** Ответ сервера, пришедший после перехода в другой эвент или на другую вкладку, рисуется поверх нового
  экрана; его кнопки (сохранить параметры, удалить эвент, удалить участника, «подарок готов») действуют на текущий эвент.
- **Тупик после ошибки.** «Попробовать снова» после ошибки первой загрузки или открытия эвента падает.
- **Переписка.** После своей отправки пропадает ответ собеседника, пришедший в те же секунды.
- **Журнал** показывает только первый экран записей.
- **Переключатели** после ошибки сервера остаются в новом положении; быстрые двойные переключения расходятся с сервером.
- **Потеря ввода.** Текст, допечатанный во время сохранения письма, считается сохранённым; после закрытия чата
  «Сохранить» может записать письмо поверх более новой версии; адрес, черновик сообщения, объявление и параметры эвента
  пропадают без предупреждения при перерисовке или закрытии.
- **Отмена жеребьёвки** становится невозможной, если админ-участник просто открыл эвент: по умолчанию открывается вкладка
  «Подопечный», и подопечный считается просмотренным.
- **Мелочи.** Кнопки «Сохранить»/«Отправить» снова активны после действия при пустом/неизменном поле; подсветка изменений
  письма подопечного пропадает после закрытия чата; длинное подтверждение жеребьёвки обрезается и прячет важное;
  системная кнопка «Назад» Telegram закрывает приложение вместо возврата к списку; переключатели без подписи для
  экранного диктора.

**Why this priority**: Часть пунктов (чужой экран) ведёт к действиям не над тем эвентом; остальные сбивают с толку людей
без технического опыта (принцип II).

**Independent Test**: Открыть эвент A, не дожидаясь загрузки панели перейти в эвент B → на экране только B, кнопки
действуют на B. Ошибка сети при открытии эвента → «Попробовать снова» открывает эвент.

**Acceptance Scenarios**:

1. **Given** загрузка экрана эвента A не завершилась, **When** пользователь перешёл в эвент B или на другую вкладку,
   **Then** ответ для A не отображается, действия выполняются только над видимым эвентом.
2. **Given** ошибка загрузки, **When** «Попробовать снова», **Then** повторяется именно неудавшаяся загрузка.
3. **Given** собеседник написал, пока участник отправлял своё сообщение, **When** открыта переписка, **Then** видны оба.
4. **Given** в журнале 100 записей, **When** журнал открыт, **Then** все записи доступны прокруткой.
5. **Given** сервер отклонил изменение переключателя, **Then** переключатель в прежнем положении; пока запрос идёт,
   переключатель недоступен.
6. **Given** несохранённый адрес или черновик сообщения, **When** пользователь уходит с экрана или закрывает чат,
   **Then** приложение предупреждает; черновики объявления и параметров переживают перерисовку панели.
7. **Given** админ-участник после жеребьёвки открывает эвент, **Then** открывается не вкладка «Подопечный», и отмена
   жеребьёвки остаётся доступной, пока он сам не откроет подопечного.
8. **Given** эвент открыт, **When** системная кнопка «Назад» Telegram, **Then** возврат к списку эвентов (или закрытие
   шторки, если она открыта).

### User Story 8 — Тексты говорят правду (Priority: P3)

- «Письмо увидит только твой Санта» — но организатор может открыть письмо (с подтверждением и записью в журнал).
- Подтверждение жеребьёвки: «Отменить её будет нельзя» — с 007 отмена возможна, пока никто не открыл подопечного.
- Удаление после жеребьёвки: «новый подопечный появится только у его Санты» — может измениться до трёх пар.
- Подсказка напоминаний: «за 2 дня до срока» — на деле за 2 дня, за день и в день срока.
- «Санта получит уведомление» — уведомление приходит через несколько минут и только если у Санты уведомления включены.
- Авто-раскрытие и автозавершение без даты вручения молча не срабатывают — нет предупреждения.
- «📋 Копировать» без ссылки (бот не настроен) говорит «Ссылка скопирована».
- Исключения после жеребьёвки: нет пояснения, почему их нельзя менять.

**Why this priority**: Не ломает игру, но обещания интерфейса должны совпадать с поведением.

**Independent Test**: Пройти по экранам — каждый текст соответствует поведению из спецификаций 001–009.

**Acceptance Scenarios**:

1. **Given** любой из перечисленных экранов, **When** пользователь читает подсказку, **Then** она соответствует поведению.

### User Story 9 — Перенос участия ничего не теряет (Priority: P3)

При слиянии старого участия с новым аккаунтом в одном эвенте письмо берётся «новое, если не пустое», а адрес — всегда
старый: свежий адрес теряется. После исправления адрес выбирается по тому же правилу, что и письмо.

**Why this priority**: Редкий сценарий, но потерянный адрес — подарок, ушедший не туда.

**Independent Test**: Старый аккаунт с адресом A, новый в том же эвенте с адресом B → после переноса адрес B.

**Acceptance Scenarios**:

1. **Given** новый аккаунт уже в эвенте с непустым адресом, **When** перенос, **Then** сохраняется адрес нового аккаунта.
2. **Given** у нового аккаунта адрес пустой, **When** перенос, **Then** сохраняется адрес старого.

### User Story 10 — Код проще поддерживать (Priority: P3)

Вся игровая логика — один файл на тысячу строк; одни и те же правила (имя человека, кому из админов писать, нормализация
текста, даты, добавление участника с адресом) повторяются; API мини-приложения зависит от модуля чата бота; отправка
очереди запускается из разных мест в середине обработки. После рефакторинга логика разбита на модули по зонам
ответственности, повторы сведены в одно место, отправка очереди — одна точка в конце обработки запроса.

**Why this priority**: Не видно пользователям, но снижает риск новых багов в следующих фичах.

**Independent Test**: Все тесты, проходившие до фичи, проходят без изменения ожиданий (кроме ожиданий, которые меняет
сама эта спецификация); ни один модуль логики не длиннее ~400 строк.

**Acceptance Scenarios**:

1. **Given** набор тестов до рефакторинга, **When** рефакторинг завершён, **Then** все тесты проходят.

### Edge Cases

- Плановый запуск оборвался посреди отправки: неотправленные сообщения уходят позже (как в 006); дубли — только при обрыве.
- Эвентов с напоминаниями больше, чем помещается в один запуск: остальные — в следующие минуты того же часа.
- Участник нажал «↩️ Ответить» в одном эвенте, потом в другом: действует последний выбор.
- Режим ответа истёк, а человек прислал длинный текст: текст остаётся в чате у самого человека, бот просит переслать.
- Удалённый из эвента человек по той же ссылке при открытой регистрации вступает снова (как раньше).
- Опоздавшая пара супругов после жеребьёвки: исключение между ними задать уже нельзя; работают семьи, заданные заранее,
  либо отмена жеребьёвки, пока никто не открыл подопечного.
- Человек из семьи участвует в двух эвентах: семья заблокирована, пока хоть один из них идёт после жеребьёвки с
  включёнными семьями.
- Изменение пар отклонено из-за одновременного действия: ничего не изменено, никто не уведомлён.

## Requirements *(mandatory)*

### Functional Requirements

**Тайна (US1)**

- **FR-901**: После жеребьёвки эвента добавление и удаление его исключений MUST отклоняться; интерфейс показывает
  исключения только для чтения с пояснением.
- **FR-902**: Создание, изменение и удаление семьи MUST отклоняться, если кто-то из людей, чьё членство меняется (прежние
  и новые члены), участвует в идущем эвенте с проведённой жеребьёвкой и включённым правилом семей; отказ называет эвент.
- **FR-903**: Администратор MUST NOT вписывать в жеребьёвку самого себя.
- **FR-904**: Ответы проверки и проведения жеребьёвки MUST NOT сообщать, удалось ли учесть пары прошлых эвентов.
- **FR-905**: Адрес доставки MUST предзаполняться при вступлении только в эвент, который спрашивает адрес.

**Рассылка и лимиты (US2)**

- **FR-906**: Сбой одного шага планового запуска MUST NOT останавливать остальные шаги, включая отправку очереди;
  сбой пишется в журнал Worker.
- **FR-907**: Каждый вызов (плановый, webhook бота, API) MUST учитывать уже сделанные внешние запросы и отправлять из
  очереди не больше, чем помещается в лимит 50 с запасом.
- **FR-908**: За плановый запуск MUST выполняться не больше одного тяжёлого действия по эвентам (автодействие или
  рассылка напоминаний одного эвента); отметка «проверено сегодня» для эвентов без рассылки — одним запросом.
- **FR-909**: Отправка очереди MUST запускаться один раз в конце обработки вызова, после всех остальных запросов.
- **FR-910**: Запрос к Telegram MUST ограничиваться по времени (не дольше 10 секунд).

**Режим ответа (US3)**

- **FR-911**: Режим ответа в переписку MUST отменяться любой командой и сбрасываться при отказе нажатия «Ответить».
- **FR-912**: Режим ответа MUST истекать через 60 минут; текст после истечения не пересылается, бот объясняет, что делать.
- **FR-913**: Режим ответа MUST быть привязан к собеседнику на момент нажатия; если пара сменилась, текст не пересылается.

**Вход и меню (US4)**

- **FR-914**: Участник, открывший приглашение своего эвента, MUST получать «уже участвуешь» независимо от открытости
  регистрации и статуса эвента.
- **FR-915**: При вводе имени вход в эвент MUST проверяться заново по правилам приглашения; «присоединяется» — только при
  фактическом вступлении.
- **FR-916**: После отклонения заявки новая заявка того же человека в тот же эвент MUST NOT создаваться в течение суток.
- **FR-917**: Тексты кнопок и сообщений MUST сокращаться без разрыва символов; меню MUST доставляться при любом названии
  эвента до 80 символов.
- **FR-918**: Меню бота MUST собираться за постоянное число запросов к базе.

**Атомарность (US5)**

- **FR-919**: Раскрытие тайны MUST выполняться не более одного раза при одновременных запросах; второй — «Тайна уже раскрыта».
- **FR-920**: Завершение эвента MUST выполняться не более одного раза; второй запрос — «Эвент уже завершён».
- **FR-921**: Удаление и вписывание участника после жеребьёвки MUST применяться, только если пары эвента не менялись с
  момента их чтения; иначе — отказ без изменений и уведомлений.
- **FR-922**: Жеребьёвка MUST записываться, только если состав участников не менялся с момента расчёта; иначе — отказ
  «Состав эвента изменился — попробуй ещё раз».

**Жеребьёвка (US6)**

- **FR-923**: Все попытки поиска в одной проверке/жеребьёвке MUST вместе укладываться в один бюджет вычислений.
- **FR-924**: Если кольцевое распределение не найдено за отведённые попытки, причина MUST быть «не удалось подобрать —
  попробуй ещё раз…», а не «невозможно».

**Мини-приложение (US7)**

- **FR-925**: Ответ, пришедший для экрана, который пользователь уже покинул, MUST NOT отображаться; действия экрана MUST
  выполняться над эвентом, для которого экран построен.
- **FR-926**: «Попробовать снова» MUST повторять неудавшуюся загрузку.
- **FR-927**: Переписка MUST показывать все сообщения собеседника, включая пришедшие во время своей отправки.
- **FR-928**: Журнал действий MUST прокручиваться целиком.
- **FR-929**: Переключатель MUST блокироваться на время запроса и возвращаться в прежнее положение при ошибке.
- **FR-930**: Сохранение письма MUST считать сохранённым только отправленный текст; правки, сделанные в других экранах,
  MUST NOT теряться; несохранённые адрес и черновик сообщения MUST защищаться предупреждением; черновики объявления и
  параметров эвента MUST переживать перерисовку панели.
- **FR-931**: Для администратора эвент по умолчанию MUST NOT открываться на вкладке «Подопечный».
- **FR-932**: Кнопки действий MUST после выполнения отражать актуальное состояние полей (пустое/неизменное — недоступно).
- **FR-933**: Подсветка изменений письма подопечного MUST сохраняться после закрытия переписки.
- **FR-934**: Подтверждение жеребьёвки MUST помещаться в лимит окна подтверждения Telegram; важное — в начале.
- **FR-935**: Системная кнопка «Назад» Telegram MUST закрывать шторку, а на экране эвента — возвращать к списку.
- **FR-936**: Переключатели MUST иметь доступное имя (подпись строки).

**Тексты (US8), перенос (US9)**

- **FR-937**: Все тексты из US8 MUST соответствовать поведению; при включённых авто-раскрытии/автозавершении без даты
  вручения интерфейс MUST предупреждать.
- **FR-938**: При переносе участия адрес доставки MUST выбираться по правилу письма (новый, если не пустой).

**Рефакторинг (US10) и документация**

- **FR-939**: Игровая логика MUST быть разбита на модули по зонам ответственности; повторяющиеся правила MUST жить в одном
  месте; API мини-приложения MUST NOT зависеть от модуля чата бота.
- **FR-940**: Рефакторинг MUST NOT менять поведение, кроме перечисленного в этой спецификации.
- **FR-941**: README, CLAUDE.md и контракты MUST отражать новую структуру и изменённое поведение.

### Key Entities *(include if feature involves data)*

- **Режим ввода (users.pending)**: для ответа в переписку дополнительно хранит собеседника и момент нажатия «Ответить»
  (в той же строке; схема базы не меняется).
- **Эвент (events)**: отметка раскрытия хранит момент раскрытия (раньше — 1), смысл «раскрыто / нет» прежний; токен
  жеребьёвки дополнительно служит версией пар (меняется при каждом изменении пар).
- **Заявка (join_requests)**: время решения используется для паузы после отклонения.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-901**: 0 способов для администратора изменить исключения или семьи участников после жеребьёвки идущего эвента,
  вписать себя или узнать из ответа проверки жеребьёвки о прошлых парах (сквозной тест).
- **SC-902**: 0 дублей и 0 потерь напоминаний при трёх эвентах с напоминаниями в один день (сквозной тест).
- **SC-903**: Ни один вызов не превышает 50 внешних запросов по собственному счётчику на сценариях: 10 идущих эвентов
  в час напоминаний, /setup-ссылка владельца, приглашение у участника с 5 эвентами.
- **SC-904**: 0 сообщений, пересланных в переписку после команды, отказа, истечения часа или смены пары.
- **SC-905**: Меню доставляется в 100% случаев для названий до 80 символов, включая эмодзи.
- **SC-906**: При двух одновременных раскрытиях/завершениях — ровно одно сообщение каждому адресату; при двух
  одновременных изменениях пар — корректное распределение.
- **SC-907**: Проверка жеребьёвки для 50 участников с невыполнимыми ограничениями при истории и семьях — до 10 мс на
  эталонном замере.
- **SC-908**: Все тесты, проходившие до фичи, проходят (с ожиданиями, обновлёнными по этой спецификации); ни один модуль
  логики не длиннее ~400 строк.

## Assumptions

- Новых функций нет: всё перечисленное — исправление поведения, расходящегося со спецификациями 001–008, конституцией или
  ожиданиями пользователей, и рефакторинг.
- Схема базы не меняется: собеседник и момент нажатия «Ответить» — в строке режима ввода; момент раскрытия — в поле
  `revealed`; версия пар — в существующем токене жеребьёвки; пауза после отклонения — по времени решения заявки.
- Запрет менять исключения после жеребьёвки — цена тайны: иначе успех или отказ «Вписать» отвечает на вопрос «дарит ли S
  подопечному W». Для опоздавших пар остаются семьи (заданные заранее) и отмена жеребьёвки, пока никто не открыл
  подопечного. Семьи блокируются точечно — только для людей из идущих эвентов с проведённой жеребьёвкой.
- Сведения «удалось ли учесть прошлые пары» убираются из ответов целиком (и из проверки, и из проведения): с отменой
  жеребьёвки результат проведения тоже можно было бы использовать как «оракул». Бот по-прежнему старается не повторять
  пары; интерфейс говорит «если получится».
- Перенос участия на «второй» аккаунт администратора остаётся остаточным риском 006 (защита — уведомления прежнему аккаунту
  и всем админам). Сделать перенос только владельцу — смена политики ролей; это вынесено на обсуждение с владельцем, а не
  исправляется здесь.
- Удаление эвента (только владелец, ввод слова УДАЛИТЬ) не делается атомарным против двойного запуска: двух владельцев не
  бывает, двойное нажатие уже блокируется.
- Срок режима ответа — 60 минут, пауза после отклонения заявки — 24 часа.
- Лимит внешних запросов считается по документации Cloudflare: 50 на вызов на бесплатном тарифе, запросы к D1 входят,
  `batch` — один запрос; не больше 100 параметров в одном запросе.
