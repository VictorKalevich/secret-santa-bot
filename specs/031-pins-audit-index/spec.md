## User Scenarios & Testing *(mandatory)*

### User Story 1 — Второе из одновременных закреплений получает честный отказ (Priority: P1)

Владелец бота закрепляет пары с двух устройств (или с двух вкладок) почти одновременно, и закрепления спорят: у одного
Санты два подопечных, у одного подопечного два Санты, или при кольцевой — встречные пары. Сохраняется одно закрепление,
и только его вызов отвечает «успех». Второй получает тот же отказ, который получил бы, если бы нажал на секунду позже, —
с именем человека, у которого уже есть пара.

**Why this priority**: ответ «успех» на несохранённое действие вводит владельца в заблуждение; встречные пары при
кольцевой нарушают правило проекта «кольцевая — без взаимных пар» и потом мешают жеребьёвке.

**Independent Test**: два вызова с навязанным чередованием «оба читают, потом пишут» (и в одну миллисекунду); проверяются
ответы, сохранённые пары и записи журнала.

**Acceptance Scenarios**:

1. **Given** у Ани нет закреплённого подопечного, **When** одновременно закрепляются «Аня → Боря» и «Аня → Вера»,
   **Then** у Ани один закреплённый подопечный; вызов, чья пара сохранена, — успех; другой — отказ «У «Аня» уже есть
   закреплённый подопечный — сначала убери ту пару.»; запись `fixed.add` одна.
2. **Given** у Бори нет закреплённого Санты, **When** одновременно закрепляются «Аня → Боря» и «Вера → Боря», **Then**
   одна пара; второй — отказ «Санта для «Боря» уже закреплён — сначала убери ту пару.»; запись одна.
3. **Given** кольцевая включена, пар нет, **When** одновременно закрепляются «Аня → Боря» и «Боря → Аня», **Then**
   сохраняется одна; второй — отказ «При кольцевой жеребьёвке пару можно закрепить только в одну сторону: «…» уже
   дарит «…».»; запись одна.
4. **Given** без кольцевой, пар нет, **When** одновременно закрепляются взаимная «Аня ↔ Боря» и «Аня → Вера», **Then**
   сохраняется либо взаимная пара целиком (обе стороны), либо «Аня → Вера» — никогда одна сторона взаимной; проигравший
   вызов — отказ; запись одна.
5. **Given** пар нет, **When** владелец дважды одновременно закрепляет одну и ту же пару (в том числе взаимную), **Then**
   оба ответа — успех, пара одна, запись одна (как в 023: повтор — не спор).

### User Story 2 — В журнале видно каждый ответ организатора в обращение (Priority: P2)

Организатор отвечает участнику в обращении — из приложения или из чата бота («↩️ Ответить»). В журнале события
появляется запись «💬 Ответ в обращение» с именем автора обращения: видно, кто из организаторов и когда отвечал. Текста
ответа в журнале нет.

**Why this priority**: решение владельца — журнал отражает работу организаторов с обращениями полностью, а не только
взятие, передачу и закрытие.

**Independent Test**: ответы организатора в ничьё и во взятое обращение, из приложения и из бота; записи журнала до и
после; одновременные и отклонённые ответы.

**Acceptance Scenarios**:

1. **Given** обращение уже ведёт админ, **When** он отвечает из приложения, **Then** в журнале события новая запись
   `support.reply`: автор — админ, подробности — имя автора обращения.
2. **Given** обращение ничьё, **When** админ отвечает (ответ берёт обращение), **Then** две записи: `support.take` и
   `support.reply`.
3. **Given** обращение ведёт админ, **When** он отвечает из чата бота («↩️ Ответить»), **Then** запись `support.reply`,
   как из приложения.
4. **Given** обращение ведёт другой админ (или закрыто, или своё), **When** организатор пытается ответить, **Then**
   отказ прежний, записи нет.
5. **Given** обращение ничьё, **When** два админа одновременно отвечают, **Then** сохраняется ответ взявшего; записей
   `support.take` и `support.reply` — по одной.
6. **Given** журнал события, **When** его открывает админ, **Then** запись видна с подписью «💬 Ответ в обращение» и
   без текста ответа.

### User Story 3 — Приложение открывается без просмотра всей переписки (Priority: P3)

Участник открывает мини-приложение («мои события»). Число непрочитанных сообщений от Санты и подопечного считается по
его собственным непрочитанным сообщениям, а не просмотром всех сообщений всех событий. Для пользователя ничего не
меняется: те же числа, тот же экран; растёт только запас по времени, когда сообщений станут тысячи.

**Why this priority**: сейчас для группы владельца это доли миллисекунды — это запас на будущее; при этом изменение
схемы должно быть безопасным для боевой базы.

**Independent Test**: план запроса непрочитанных после всех миграций — поиск по индексам, без просмотра таблицы;
числа непрочитанных прежние; миграция применяется к базе с данными и не меняет ни одной строки.

**Acceptance Scenarios**:

1. **Given** база со всеми миграциями, **When** считаются непрочитанные для «мои события», **Then** запрос ищет по
   индексам Санты и подопечного, без просмотра всей таблицы сообщений.
2. **Given** боевая база с данными, **When** применяется новая миграция, **Then** ни одна строка ни одной таблицы не
   меняется, добавляются только индексы.
3. **Given** новая миграция ещё не применена, **When** выкачен новый код (или наоборот — миграция применена, а работает
   прежний код), **Then** бот работает как раньше, без сообщения «База не подготовлена».
4. **Given** новая версия выкачена и миграция применена, **When** владелец откатывает код на прежнюю версию, **Then**
   прежний код работает с базой без изменений.

---

### Edge Cases

- **Жеребьёвка в ту же секунду, что и закрепление.** Как раньше: закрепление не сохраняется, ответ — «После жеребьёвки
  закреплённые пары не меняются…».
- **Причина не определяется.** Состояние пар для текста отказа читается в той же транзакции, что и запись, поэтому
  мешающая пара в нём есть; если причины всё же нет (жеребьёвку провели и отменили в ту же секунду), ответ — отказ
  «Закреплённые пары только что изменились — обнови экран и попробуй ещё раз.»; ничего не сохранено.
- **Повтор того же закрепления** (двойное нажатие, вторая вкладка) — не спор: ответ «успех», без записи журнала (023).
- **Удаление закреплённой пары** не меняется: удаление отсутствующей — «успех» без записи (023).
- **Админ** по-прежнему получает 403 на `admin.fixed.*`.
- **Ответ организатора, который не сохранился** (обращение закрыли, передали или взял другой в ту же секунду), записи
  `support.reply` не оставляет.
- **Ответ участника** в своё обращение журнал не пишет (как раньше: журнал — действия организаторов).
- **Ответ владельца** в обращение, переданное себе, пишет `support.reply`, как ответ любого организатора.
- **Миграция на пустой базе** (новая установка по README) применяется вместе с остальными, ничего не ломая.
- **Индексы и запись сообщений.** Каждое новое сообщение переписки обновляет два индекса — на запись это не влияет
  заметно (одна строка).

## Requirements *(mandatory)*

### Functional Requirements

**Закреплённые пары**

- **FR-3101**: Закрепление сохраняется, только если в момент записи у каждого его Санты нет другого закреплённого
  подопечного, у каждого подопечного — другого закреплённого Санты, а при кольцевой — нет встречной пары. Иначе не
  сохраняется ни одна его сторона (взаимная пара — целиком или никак).
- **FR-3102**: Вызов, чьё закрепление не сохранено из-за другого закрепления, получает тот же отказ (код и текст), что дала
  бы обычная проверка перед записью при новом состоянии пар: «У «X» уже есть закреплённый подопечный — сначала убери ту
  пару.», «Санта для «Y» уже закреплён — сначала убери ту пару.», «При кольцевой жеребьёвке пару можно закрепить только в
  одну сторону: «…» уже дарит «…».».
- **FR-3103**: Если закрепление не сохранено, а обычная проверка по состоянию пар причины не находит (страховка: например,
  жеребьёвку в ту же секунду провели и сразу отменили), ответ — отказ «Закреплённые пары только что изменились — обнови
  экран и попробуй ещё раз.» (код 400); «успеха» без сохранённой пары не бывает.
- **FR-3104**: Повтор уже сохранённого закрепления — успех без записи журнала; запись `fixed.add` — только при
  настоящем изменении (как в 023). Отказ — без записи.
- **FR-3105**: Порядок проверок, отказ после жеребьёвки, права (только владелец), удаление закреплённой пары — без
  изменений. Число запросов к базе — прежнее, в том числе у проигравшего спор.

**Журнал ответов организатора**

- **FR-3106**: Каждый сохранённый ответ организатора в обращение (приложение — `admin.support.send`, бот — ответ в режиме
  `sup_a`) пишет запись журнала события `support.reply`: автор — организатор, подробности — имя автора обращения; текста
  ответа в записи нет.
- **FR-3107**: Ответ, который берёт ничьё обращение, пишет две записи: `support.take` (как раньше) и `support.reply`.
- **FR-3108**: Запись `support.reply` появляется тогда и только тогда, когда сохранён сам ответ (одно действие — один
  результат): отказ или проигрыш одновременному взятию, передаче или закрытию записи не оставляет.
- **FR-3109**: Журнал в приложении подписывает запись «💬 Ответ в обращение»; `docs/api.md` (раздел действия, таблица
  кодов журнала и список «не пишут») описывает новый код; число запросов к базе и Telegram на ответ — прежнее.

**Индекс непрочитанных**

- **FR-3110**: Новая миграция только добавляет индексы сообщений переписки по Санте и по подопечному (с признаком
  «прочитано»); она не создаёт и не удаляет таблиц и не меняет ни одной строки, повторное применение безопасно.
- **FR-3111**: Подсчёт непрочитанных для «мои события» ищет по этим индексам, без просмотра всей таблицы сообщений;
  числа непрочитанных — прежние.
- **FR-3112**: Код от новых индексов не зависит: требуемая версия схемы не поднимается, бот работает и до применения
  миграции, и после; откат кода на прежнюю версию безопасен для базы.
- **FR-3113**: README («Обновление бота») и описание проекта (`CLAUDE.md`) называют новую миграцию; порядок «копия базы →
  миграции → выкат» прежний.

**Общее**

- **FR-3114**: Ответы, тексты и число запросов остальных действий не меняются; эталон отказов, таблица запросов, тайна,
  права и сквозной сценарий проходят (изменения — только перечисленные выше и точечно в тестах).
- **FR-3115**: Сделанные пункты убраны из `docs/todo.md` (в нём остаётся «быстрая попытка» жеребьёвки — «не делаем» — и
  CSP до фичи 032).

### Key Entities

- **Закреплённая пара** — «Санта → подопечный» в событии до жеребьёвки; у Санты не больше одной, у подопечного не больше
  одной; при кольцевой — без встречной.
- **Запись журнала `support.reply`** — событие, кто ответил, время, имя автора обращения; без текста.
- **Индексы непрочитанных** — служебная часть схемы, данных не содержит и не меняет.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-3101**: В тестах одновременных вызовов (с навязанным чередованием и в одну миллисекунду) на 4 видах спора — один
  Санта, один подопечный, встречные при кольцевой, взаимная против одиночной — ровно один ответ «успех», у другого
  отказ с текстом обычной проверки; ни разу не сохраняется одна сторона взаимной пары или встречная пара при кольцевой.
- **SC-3102**: Каждый сохранённый ответ организатора даёт ровно одну запись `support.reply` (ответ в ничьё — плюс одна
  `support.take`); отклонённые и проигравшие ответы — ноль записей; проверено для приложения и бота.
- **SC-3103**: План запроса непрочитанных для «мои события» не содержит просмотра всей таблицы сообщений.
- **SC-3104**: Миграция, применённая к базе с данными всех таблиц, не меняет ни одной строки (сравнение до и после).
- **SC-3105**: Число запросов к базе и Telegram у всех действий — не больше базового (таблица запросов), эталон 1125
  отказов не меняется, `npm run test:all` зелёный.

## Assumptions

- Признак «закрепление сохранено» и отказ проигравшему определяются по состоянию пар в момент записи (в той же
  транзакции), а не по времени или автору вызова — правило «одно действие — один результат» (020).
- Отказ проигравшему строится по закреплённым парам, прочитанным в той же транзакции сразу после записи, — тем же
  правилом, что обычная проверка, поэтому тексты одинаковые; отдельного запроса к базе нет.
- Отказ «Закреплённые пары только что изменились…» — новый текст; слово «событие» в нём не нужно.
- Подробности `support.reply` — имя автора обращения, как у `support.take`: журнал видят все админы, а кто автор
  обращения, им и так видно в списке обращений; текста ответа нет (Конституция, обращения 2.2.0).
- Ответ участника в своё обращение журнал не пишет: журнал — действия организаторов и бота (принцип проекта).
- Требуемая версия схемы (`REQUIRED_SCHEMA`) не поднимается и номер схемы в базе не меняется: индексы — ускорение, код
  от них не зависит. Это отступление от обычного правила «новая схема → новая версия» записано в `CLAUDE.md`, чтобы
  порядок «миграция ↔ выкат» не мог уронить бота.
- Индексы — по (Санта, «прочитано») и (подопечный, «прочитано»): на SQLite подсчёт для «мои события» идёт двумя
  поисками по индексам; подсчёт для одного события и так ищет по индексу пары (`messages_pair`) и не меняется.
- Конституция не меняется: правила тайны, ролей и журнала (без текстов) выполняются.
- «Быстрая попытка» жеребьёвки остаётся в `docs/todo.md` как «не делаем»; CSP — фича 032.
