# Research: 031 — честный отказ при одновременных закреплениях, журнал ответов в обращения, индекс непрочитанных

Проверено на коде `main` `d1b3633` (2026-11-16).

## R1. Закрепление: условие «можно закрепить» в пакете записи

**Сейчас** (`changeFixed`, `src/constraints.js`): проверки «у Санты уже есть подопечный», «у подопечного уже есть Санта»,
«кольцевая — в одну сторону» идут по чтению до записи. Запись — `INSERT OR IGNORE` под условием «жеребьёвки нет», журнал
— по прежнему состоянию (023). Два одновременных закрепления читают одно и то же, оба проходят проверки:

- один Санта / один подопечный — второй `INSERT` молча отбрасывается первичным ключом или уникальным индексом, ответ
  «успех»;
- встречные пары при кольцевой (`А → Б` и `Б → А`) — ограничения схемы их не ловят, **сохраняются обе**: взаимная пара
  в кольцевой, которую обычная проверка не пускает (потом жеребьёвка отказывает `fixed_block`);
- взаимная `А ↔ Б` против `А → В` — `INSERT` идут по сторонам, одна сторона взаимной может сохраниться, другая нет.

**Decision**: у добавления — дополнительное условие пакета «закрепление возможно» (`FREE`), по каждой стороне `(a, b)`:

```text
( пара (a, b) уже есть
  OR ( у a нет закреплённого подопечного AND у b нет закреплённого Санты ) )
[ AND встречной (b, a) нет ]            -- только при кольцевой (ev.ring на момент вызова)
```

Стороны соединяются `AND`: все или ни одной. Условие истинно и после собственных вставок пакета (сторона уже есть),
поэтому вставки взаимной пары не мешают друг другу. Операторы пакета (через `atomic`, `src/claim.js`):

1. `claim`: `SELECT 1 WHERE <жеребьёвки нет> AND <FREE>` — оператор исхода по прежнему состоянию (строка есть — можно);
2. `audit fixed.add` — `<…> AND <FREE> AND <хотя бы одна сторона изменится>` (как в 023);
3. `INSERT OR IGNORE` сторон — `<…> AND <FREE>`;
4. `SELECT giver, receiver FROM fixed_pairs WHERE event_id = ?` — состояние после записи для текста отказа.

Удаление (`admin.fixed.del`) не меняется: исхода у него нет (удаление отсутствующей — успех без записи, 023).

**Rationale**: признак «закрепление моё» — состояние пар в той же транзакции, а не время и автор (правило 020: у двух
нажатий одного человека в одну миллисекунду они совпадают). Повтор того же закрепления — `FREE` истинно (сторона уже
есть), ответ «успех» без записи — как в 023. `claim` с `SELECT` — оператор исхода: `run()` считает исход выигранным,
если оператор вернул строку (`claim.results.length`), как у `INSERT … RETURNING`.

**Alternatives considered**:

- Отдельное чтение пар после проигрыша — лишний запрос на редком пути; чтение в том же пакете бесплатно (один batch —
  один запрос), а состояние то же, что видела запись.
- Различать исход по `meta.changes` каждого `INSERT` — не работает для повтора (0 изменений, но это успех) и не делает
  взаимную пару «целиком или никак».
- Уникальный индекс «встречная пара» в схеме — невозможен простым индексом и мешал бы взаимным парам без кольцевой.

## R2. Текст отказа проигравшему

**Decision**: проверки «перед записью» вынесены в одну функцию `fixedRefusal(ev, fixed, links, name)` (порядок прежний:
кольцевая — встречная; по сторонам — уже есть подопечный, уже есть Санта). Обычный путь вызывает её по чтению до записи,
проигравший — по строкам оператора 4. Эти строки — состояние той же транзакции, а вставок у проигравшего не было,
поэтому ложное `FREE` всегда даёт причину: сторона не «уже есть» и занят Санта или подопечный, либо есть встречная при
кольцевой. Исход ложен и без спора, если ложно условие «жеребьёвки нет» — это ловит повторное чтение события; остаётся
только «жеребьёвку провели и сразу отменили» между пакетом и чтением события — тогда отказ-страховка `FIXED_CHANGED`
«Закреплённые пары только что изменились — обнови экран и попробуй ещё раз.» (400), но не ложный «успех».

Порядок проверок после пакета: сначала прежнее повторное чтение события (жеребьёвка в ту же секунду → «После жеребьёвки
закреплённые пары не меняются…»), затем исход. Имена — из того же списка участников, что прочитан до записи.

**Rationale**: один текст на одну причину — тот же, что увидел бы владелец, нажав секундой позже; правило проверки не
дублируется.

## R3. Журнал ответа организатора `support.reply`

**Сейчас** (`sendFromAdmin`, `src/support.js`): пакет `open` («обращение открыто»), для ничьего — `free` (взятие:
уведомления, `support.take`, `UPDATE … assignee`), затем `mine` («открыто и ведёт отвечающий»): уведомление участнику,
«прочитано», захват — `INSERT … RETURNING` ответа. Бот (`onSupportReply`, режим `sup_a`) вызывает тот же
`sendFromAdmin`.

**Decision**: `mine.audit(ev.id, me.tg_id, 'support.reply', displayName(author))` — перед захватом, под тем же условием
`mine`. Между записью журнала и вставкой ответа условие не меняется (оператор «прочитано» его не трогает), поэтому запись
есть тогда и только тогда, когда ответ сохранён. Ответ в ничьё — `support.take` (из `takeInto`) и `support.reply`.
Подробности — имя автора обращения (как у `support.take`); текста нет.

**Rationale**: одно место для приложения и бота; число запросов прежнее (оператор в том же пакете). Два админа
одновременно отвечают в ничьё: у второго ложны и `free`, и `mine` — ни взятия, ни ответа, ни записей.

**Alternatives considered**: писать запись только для ответов во взятое (без `support.reply` при взятии ответом) —
журнал зависел бы от того, было ли обращение ничьим; правило «каждый ответ — запись» проще проверить и прочитать.

Подпись в приложении (`AUDIT_LABELS`, `src/app/06-vault-audit.js.txt`): `'support.reply': '💬 Ответ в обращение'`.

## R4. Индексы непрочитанных

**Сейчас**: «мои события» (`homeView` → `unreadByEventQuery`, `src/chat.js`) — `WHERE m.read_at = 0 AND (m.santa = ?1 OR
m.ward = ?1)` по всей таблице `messages`; единственный индекс — `messages_pair (event_id, santa, ward, id)`. План SQLite:
`SCAN m USING INDEX messages_pair` — просмотр всех сообщений.

**Decision**: миграция `migrations/0008_unread_index.sql`:

```sql
CREATE INDEX IF NOT EXISTS messages_unread_santa ON messages (santa, read_at);
CREATE INDEX IF NOT EXISTS messages_unread_ward ON messages (ward, read_at);
```

План после миграции (SQLite 3.53, с `ANALYZE` и без): `MULTI-INDEX OR` — `SEARCH m USING INDEX messages_unread_santa
(santa=? AND read_at=?)` и `… messages_unread_ward (ward=? AND read_at=?)`. Подсчёт для одного события
(`unreadQuery`) и так ищет по `messages_pair (event_id=?)` — без изменений. Запрос и код не меняются.

**Alternatives considered** (проверено на 20 000 сообщений):

- Частичные индексы `(santa) WHERE read_at = 0` — без статистики `ANALYZE` (D1 её не собирает сам) планировщик их не
  берёт: `SCAN … messages_pair`.
- Индексы `(read_at, santa)` — тот же план, но порядок колонок `(santa, read_at)` полезен и для поиска по одному
  человеку без условия «прочитано».
- `(santa, read_at, event_id)` — тот же план; лишняя колонка не нужна.
- Переписать запрос как `UNION ALL` двух половин — лишняя правка кода при том же результате.

## R5. Версия схемы не поднимается

**Decision**: `0008` не меняет `settings.schema` (остаётся `11`), `REQUIRED_SCHEMA` в `src/db.js` — `11`. Код от
индексов не зависит: результат запросов тот же, меняется только скорость.

**Rationale** (стабильность — главное условие владельца):

- код 031 до применения миграции — работает (поднятая версия дала бы «База не подготовлена» на всё, пока миграция не
  применена);
- прежний код (откат на `bc273a7a`, `34c924ce`) после миграции — работает: `checkSchema` требует `>= 11`, индексы ему
  не мешают;
- миграция только создаёт индексы `IF NOT EXISTS` — ни одна строка не меняется, повтор безопасен; Wrangler записывает
  применённую миграцию в `d1_migrations`, так что «есть ли новые миграции» по-прежнему видно в `migrations list`.

Правило проекта «новая схема → новая версия» уточняется в `CLAUDE.md` и README: индексы, от которых код не зависит, —
без подъёма версии.

**Alternatives considered**: поднять версию до 12 по обычному правилу — порядок «миграция → выкат» стал бы обязательным,
а ошибка в нём роняла бы бота целиком.
