## R2. Помощник захвата — отдельный модуль `src/claim.js`

**Decision**: функция `atomic(db, cond, ...args)` возвращает построитель пакета. Условие — выражение с закрытыми
скобками, проверяется при создании (иначе — `Error`); хранится в скобках, параметры — один раз. Методы добавляют
операторы в общий список **в порядке вызовов** (порядок операторов = порядок строк кода): `enqueue(chatId, payload)`,
`audit(eventId, actor, action, details)`, `where(sql, ...params)` (текст оканчивается условием WHERE — добавляется
`AND (cond)`), `select(sql, ...params)` (`INSERT … SELECT …` без WHERE — добавляется `WHERE (cond)`), `add(...stmts)`
(свои условия, построители `REGISTRY`), `and(more, ...moreArgs)` (тот же список, условие `(cond) AND (more)`), `claim(stmt)`
(отметить оператор захвата; если его нет в списке — добавить), `run()` → `{ won, claim, results }`. Поле `guard` —
`[sql, ...args]` для построителей с параметрами `(guard, ...args)` (`addMemberStmt`, `markRemovedStmt`,
`clearRemovedStmt`, `eventDataDeleteStmts`, `memberDataDeleteStmts`, `personTransferStmts`).

**Rationale**: файл шага: «принимает оператор захвата и условие „захват мой“ с параметрами, отдаёт построители enqueue,
audit и произвольного оператора с этим условием и собранный batch». Порядок вызовов = порядок операторов делает видимым
главное: стоит ли оператор до захвата («по прежнему состоянию») или после («захват мой»). `and()` нужен трём случаям:
удаление участника (версия пар + «ещё участник»), обращения (открыто + кто ведёт), заявка (ждёт + регистрация открыта).
Отдельный модуль, а не `src/db.js`: тот уже смешивает схему, запросы и `REGISTRY` (обзор, пункт 11); помощник зависит
только от `enqueueIfStmt`/`auditIfStmt`.

**Alternatives considered**: (а) функция `claimBatch({ before, claim, after })` — три списка скрывают порядок внутри
списков и не решают «два условия в одном пакете»; (б) случайный токен для каждого захвата — нужна колонка (схема не
меняется, FR-2002); (в) проверка скобок только тестом по исходникам — не ловит условие, собранное во время выполнения
(`insertMember` строит условие захвата из частей).

## R3. «По прежнему состоянию» вместо метки времени

**Decision**: где признак — время (или автор и время), уведомления и журнал стоят в пакете **перед** изменением с
условием, которое изменение отменяет; исход — по оператору захвата, как прежде:

| Действие | Условие (перед захватом) | Захват — исход |
|---|---|---|
| «подарок получен» | у пары подопечного `gift_received_at = 0` | `UPDATE pairs …` (исход не нужен — ответ всегда успех) |
| исключение: добавить / убрать | прежнее «жеребьёвка не проведена» (владельцу — без него) **и** хотя бы одной добавляемой строки нет / хотя бы одна удаляемая есть | нет (ответ — по повторному чтению события, как прежде) |
| взять | обращение открыто и ничьё | `UPDATE … WHERE status = 'open' AND assignee = 0` |
| передать | открыто и ведёт прежний ответственный | `UPDATE … WHERE … assignee = <прежний>` |
| закрыть админом | открыто | `UPDATE … WHERE status = 'open'` |
| закрыть участником | открыто (уведомление админу — ещё и «ничьё или его») | то же |
| ответ организатора | взятие: открыто и ничьё; ответ, уведомление, «прочитано»: открыто и ведёт отвечающий | вставка ответа (строка `RETURNING`) |
| сообщение участника | открыто (уведомления: ничьё — всем, взятое — ответственному); журнал `support.open` — открыто | вставка сообщения (строка `RETURNING`) |
| решение по заявке | заявка ждёт решения; «принять» — и регистрация открыта, событие идёт | `UPDATE join_requests … status = 'pending'` |

**Rationale**: `batch` D1 — одна транзакция, транзакции записи одной базы выполняются по очереди (D1 — один экземпляр
SQLite на базу). Второй вызов начинает транзакцию после фиксации первой и видит уже изменённое состояние: его условия
ложны, захват не меняет строк. Условие перед захватом обязано повторять все условия захвата (подводный камень файла
шага: заявка принимается, только пока регистрация открыта — то же условие у уведомлений). Оператор, поставленный
**после** захвата, прежнего состояния уже не видит — поэтому порядок, а не только условие.

**Alternatives considered**: условие «после захвата» с проверкой «значение моё» — значение у двух вызовов одного
человека в одну мс одинаковое (`now`, `me`); различить их можно только случайным значением в новой колонке (схема).

**Следствие для исключений**: при последовательном повторе (добавить существующее, убрать отсутствующее) записи журнала
больше нет — журнал отражает изменение. Файл шага предписывает именно это условие; e2e на число записей журнала
исключений не опирается (проверено: `tests/e2e.test.mjs` проверяет наличие `exclusion.add`, а не число).

**«Подарок получен»**: условие — по паре этого подопечного, без «Санта тот же»: так и прежний код (сообщение — Санте,
прочитанному до записи). Сужение — изменение поведения вне гонки, в шаг не входит.

## R4. Надёжные захваты — только сборка

**Decision**: жеребьёвка, отмены, удаление/вписывание (версия пар), раскрытие, завершение, удаление события, перенос,
выход админа собираются помощником с прежними условиями и прежним порядком операторов. `pairsVersion` возвращает
построитель (`atomic` с условием версии или «жеребьёвка не проведена») и оператор версии (уже в списке); `insertMember`
отмечает его захватом, `removeMember` — строку участника (последний оператор, как прежде). `applyPairsChange` пишет в
построитель. Завершение: захват — первым, рассылка и запись `finish` — после, запись — последней (подводный камень).

## R5. Отмена и принудительная отмена — одна функция

**Decision**: `undoDraw(ctx, ev, actor, opts)`: общие проверки (завершено → не проведена → раскрыта, тексты прежние),
чтение пар и настроек одним пакетом, токен `<префикс><12 символов>`, захват `UPDATE events … revealed = 0 AND status =
'active'` + `opts.cond` (обычная — `CANCEL_COND`: никто не открыл подопечного, переписки нет), удаление пар, при
`opts.chats` — удаление переписки, рассылка `opts.text`, журнал `opts.action`, отказ при несостоявшемся захвате —
`opts.lost()` (обычная — постоянный текст; принудительная — по повторному чтению события). `cancelDraw` и
`forceCancelDraw` — однострочные обёртки с прежними именами и сигнатурами.

## R6. Снимки жеребьёвки — модуль `src/snapshots.js`

**Decision**: `SNAPSHOTS = { members, exclusions, families, fixed }`; у каждого `js(data)` по уже прочитанным строкам
(`data = { ids, exclusions, families, fixed }` — те же, что читает `checkDraw`) и `sql` — выражение с одним параметром
(id события). `drawSnapshot(ev, data)` — четыре строки (семьи — `''`, если правило выключено); `snapshotGuard(eventId,
snap)` — `{ sql, args }` для условия захвата жеребьёвки (`(? = '' OR <семьи> = ?)` — как прежде). Формулы:

| Снимок | Строка |
|---|---|
| участники (зарегистрированные) | `число : Σ id` |
| исключения (все события) | `число : Σ дарящий : Σ получатель : Σ (дарящий mod M)(получатель mod M)` — **новое слагаемое** |
| семьи (строки людей-участников) | `число : Σ (человек mod M)(семья mod M) : Σ семья` |
| закреплённые пары | `число : Σ дарящий : Σ получатель : Σ (дарящий mod M)(получатель mod M)` — как прежде |

Все суммы — по модулю 2^52 (в JS — на каждом шаге, в SQL — `SUM(…) % 2^52`), M = 1000003.

**Rationale**: числа меньше 2^53 по построению (подводный камень): идентификатор Telegram < 2^52, накопленная сумма
< 2^52, слагаемое < 2^52 → промежуточное < 2^53, точно в `double`; в SQL `SUM` целых точна, пока < 2^63 (≥ 2048 строк
с максимальными идентификаторами; сейчас идентификаторы ~2^33). Для нынешних данных (суммы < 2^52) строки участников,
исключений (первые три числа) и закреплённых пар совпадают с прежними побайтно; у семей произведение теперь по модулю —
прежняя формула `Σ человек × семья` при идентификаторах до 2^52 и числе семей до тысяч переполняла бы и `double`, и
целые SQLite (ошибка «integer overflow» в условии захвата → 500 на жеребьёвке). Снимок нигде не хранится: строка
считается и сравнивается в одном вызове, смена формулы не требует миграции. Одна функция «связи» для исключений и
закреплённых пар (одинаковая формула, разные таблицы). Перестановка {А→Б, В→Г} → {А→Г, В→Б} меняет
`Σ(a mod M)(b mod M)`, если А ≢ В и Б ≢ Г (mod M) — вероятность совпадения у случайных идентификаторов ~10⁻⁶.

**CPU**: `checkDraw` проходит каждый список один раз (было: исключения — 4 прохода, `map`×2 + `reduce`×2); новых
запросов нет — снимки из уже прочитанных строк.

**Alternatives considered**: сравнивать отсортированный список пар строкой — длина строки ∝ числу исключений в условии
SQL (`group_concat`), разбор и сравнение дороже; хэш (FNV) в SQL недоступен без функций.

## R7. Статическая проверка «нет SQL с незакрытой скобкой»

**Decision**: тест `tests/claims.test.mjs` разбирает каждый `src/*.js` на строковые литералы (`'…'`, `"…"`, шаблоны с
вложенными `${…}`; комментарии и литералы регулярных выражений пропускаются) и для литералов со словами SQL (`SELECT`,
`INSERT`, `UPDATE`, `DELETE`, `EXISTS`, `WHERE`) проверяет баланс скобок по статической части (вставки `${…}` — не в
счёт; строки SQL в одинарных кавычках внутри литерала — не в счёт). «От противного»: на коде до фичи тест находит
`THREAD` и `MINE_SENT` (и только их).

**Rationale**: приёмка «в `src/` нет фрагментов SQL с незакрытой скобкой» — проверяемо только по исходникам; проверка в
`atomic()` ловит лишь то, что дошло до помощника.

## R10. Запросы и скорость

Число пакетов и запросов на действие не меняется: операторы переставляются внутри тех же пакетов, чтения те же.
Замер жеребьёвки (`planDraw`) не затрагивается (`src/draw.js` не меняется); «до» (2026-11-14, `main` на `7c5e774`, два
прогона): холодный — 0,90–0,92 / 1,83–1,88 / 2,76–2,81 / 3,46–3,51 мс, прогретый — 0,05 / 0,17–0,18 / 0,42 / 0,68 мс
(50 / 100 / 150 / 200 человек).
