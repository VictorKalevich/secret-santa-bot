# Research: 051. Компании, шаг 2

Решения по основе — `specs/050-company-scope/research.md`.

## Решения владельца (2026-11-23)

Общий план обоих шагов был в `docs/companies-roadmap.md` (удалён после 051, история — git). Спецификации заполнялись без
уточняющих вопросов; семь решений владелец просмотрел и утвердил 2026-11-23:

1. Владелец компании видит пары своей компании (служебный просмотр, закреплённые пары, вписывание, обмен, принудительная
   отмена). Альтернатива — всё, что касается пар, только владельцу бота.
2. Владелец бота может всё в любой компании, включая служебный просмотр, и не виден в её списках («гость»).
3. Имя человека одно во всех компаниях.
4. Перенос участия на новый аккаунт — только владелец бота; владелец компании просит его.
5. Первая компания называется «Основная» (видит только владелец бота, можно переименовать).
6. Удалить можно только компанию без событий.
7. Передача прав владельца бота — в разделе «Компании»; кнопка 👑 в «Владелец и администраторы» — «сделать владельцем
   этой компании».

Вне рамок: перевод события или человека между компаниями и объединение компаний; лимиты на число компаний, оплата,
создание компаний не владельцем бота; удаление человека из компании целиком; свои имена людей в разных компаниях.

## R1. Владелец компании получает всё «про пары» в своей компании

**Решение.** Все действия с ролью `OWNER` (служебный просмотр, закреплённые пары, вписывание, обмен, принудительная
отмена, сброс и удаление события, администраторы) доступны владельцу компании в его компании. Конституция — 3.0.0.

**Почему.** Запрос: «существующий функционал владельца переходит на функционал владельца семьи». Компания без этого не
самостоятельна: её люди не знают владельца бота, а вписать опоздавшего или поменять подопечных мог бы только он.

**Отвергнуто.** Служебный просмотр только владельцу бота: меньше людей видят пары, но владелец бота становится
диспетчером чужих компаний. Владелец выбрал первый вариант («Решения владельца», п. 1).

## R2. Одно действие для назначения, передачи и возврата

**Решение.** `admin.owner.transfer { company, id }` — «владельцем компании становится `id`». Вызывает владелец компании
или владелец бота. Если `id` — владелец бота, в `companies.owner_id` пишется 0 («ведёт владелец бота») — это и есть
«Вести самому». Прежний назначенный владелец остаётся администратором. Захват — `UPDATE companies SET owner_id = ?
WHERE id = ? AND owner_id = ?` по прежнему значению.

**Почему.** Три кнопки интерфейса — одно правило на сервере и один набор проверок одновременности. Прежние тексты отказов
действия подходят без изменений.

## R3. Передача прав владельца бота — отдельное действие

**Решение.** `bot.owner.transfer { id }` — прежняя `transferOwnership`/`setOwner(via: 'transfer')`. Кнопка — в разделе
«Компании». Получатель — зарегистрированный человек компании, которую ведёт владелец бота.

**Почему.** С несколькими компаниями кнопка 👑 в списке администраторов одной компании не должна отдавать весь бот.

## R4. Ссылка владельца компании

**Решение.** `companies.owner_code` — случайный код (16 символов алфавита `randomCode`, 80 бит) или пусто. Ссылка
`https://t.me/<бот>?start=own_<код>`. Создаёт и отзывает владелец бота (`bot.company.link`); новая ссылка заменяет
прежнюю. Переход:

- зарегистрированный человек — права сразу;
- новый — запись пользователя с ожиданием `name_own:<компания>:<код>`, вопрос об имени (как после пригласительной
  ссылки), права — после имени, если код ещё тот же.

Права выдаются одним пакетом `atomic` по прежнему состоянию «код компании всё ещё этот»: строка человека компании с
`is_admin = 1`, сообщения, журнал, последним — `UPDATE companies SET owner_id = ?, owner_code = '' WHERE id = ? AND
owner_code = ?`.

**Почему.** В новой компании людей нет — выбрать владельца не из кого (запрос говорит «кому-либо из семьи», но при
создании семья пуста). Ссылка — тот же приём, что ссылка владельца бота и пригласительная ссылка события.

**Безопасность.** Ссылка даёт доступ к парам будущих событий компании, поэтому: одноразовая; видна только владельцу бота;
в журнал и ответы другим людям не попадает; после использования владелец бота получает сообщение с именем и @username;
отзыв в одно нажатие. В отличие от ссылки владельца бота, код случайный и хранится в базе — он не даёт ничего вне одной
компании.

**Отвергнуто.** Выбор владельца из всех людей бота — владелец компании появлялся бы без своего согласия, а новому
человеку всё равно нужна ссылка.

## R5. Названия

**Решение.** Название владельца бота — `companies.name` (переходит к следующему владельцу бота). Своё название —
`company_members.label`. Одно действие `company.label.set`: вызывающий — владелец бота → пишется название компании
(1–40 символов, пустое нельзя); иначе — своё название (0–40, пустое — сброс). В журнал не пишется.

**Почему.** Для человека это одно и то же: «как я называю эту компанию». Владельцу бота нужна строка у компании, а не у
себя: в чужой компании у него нет строки человека компании.

## R6. Какие компании видны и как названы по умолчанию

**Решение.** Видна компания, где человек владелец или администратор либо участник хотя бы одного существующего события.
Владельцу бота — все. Название по умолчанию — «Компания N», N — порядковый номер компании среди всех строк человека по
`joined_at` (номер не меняется, когда другая компания пропала из видимых). Рядом — «Владелец — <имя> · событий: K».

**Почему.** Строка человека компании остаётся и после выхода из события (050, R3), но пустая компания в списке — шум: из-за
неё человек с одной живой компанией получил бы экран выбора. Настоящее название показать нельзя — оно личное у владельца
бота.

## R7. Когда появляется экран «Компании»

**Решение.** Корневой экран — «Компании», если видимых компаний две и больше; иначе — главный экран единственной
компании. Владелец бота с одной компанией получает раздел «Компании» внизу главного экрана (создать, настройки, журнал
бота, передача прав владельца бота).

**Почему.** Правило «оболочку видит тот, кому есть из чего выбирать» одно для всех. Бот с одной компанией выглядит как
раньше — в том числе у тех, кто развернул бота по README и компаниями не пользуется.

## R8. «Владелец» вместо «владелец бота»

**Решение.** `ownerWord(botRun)` в `src/format.js` и такой же помощник в `02-core`: формы «владелец бота / владельца
бота / владельцу бота / владельцем бота» при `botRun` и «владелец / владельца / владельцу / владельцем» иначе. Все
тексты для людей, говорящие, кто может действие владельца в событии или компании, строятся через помощника. Действия
только владельца бота (перенос участия, компании, страница настройки) всегда говорят «владелец бота».

**Почему.** Людям компании с назначенным владельцем «владелец бота» — незнакомый человек; обращаться им надо к своему
владельцу. В компании, которую ведёт владелец бота, тексты побайтно прежние — эталон отказов не меняется.

## R9. Гость на экране

**Решение.** В компании, где у владельца бота роль `guest`, главный экран компании показывает плашку: «Ты здесь как
владелец бота: в списках компании тебя нет, уведомления её организаторам тебе не приходят. Твои изменения записываются в
журнал компании.» Чтение без записей в журнал (как у любого организатора), служебный просмотр — с записью, как всегда.

## R10. Что остаётся только владельцу бота

**Решение.** Перенос участия (`admin.transfer`) и переименование человека из нескольких компаний.

**Почему.** Оба действия меняют человека во всех компаниях. Перенос — ещё и путь к чужим парам: владелец компании мог бы
перенести участие человека на свой второй аккаунт и увидеть его пары в другой компании.

## R11. Удаление — только пустой компании

**Решение.** `bot.company.delete` с условием «событий нет» в самом пакете. Удаление — построителем
`companyDataDeleteStmts` из `REGISTRY` (новое обязательное решение `onCompanyDelete: 'delete' | 'block'` у таблиц с
ключом `company`; `events` — `block`). Перед удалением строк людей — пересчёт общего признака `users.is_admin` тем, кто
был в ней администратором. Создание события проверяет в самой вставке, что компания существует.

**Почему.** Удаление событий — действие со своими подтверждениями и рассылками участникам; повторять его каскадом из
компании — много операторов в одном пакете и риск стереть лишнее одной кнопкой.

## R12. Журнал бота

**Решение.** Записи с `company_id = 0, event_id = 0`: `company.create`, `company.delete`, `company.link` (создана /
отозвана — без кода), `company.owner` (и в журнал компании), а также `owner.link`, `owner.transfer` (дополнительно к
записям в компаниях, которые ведёт владелец бота, 050). Читает `bot.audit`.

## R13. Роли в приложении

**Решение.** Сервер в `me.companies[]` отдаёт `role`, `organizer`, `owner`, `bot_run`. Приложение при входе в компанию
(`enterCompany`) выставляет `state.me.is_admin = organizer`, `state.me.is_owner = owner` — существующий код экранов читает
эти поля как раньше. Общие действия организатора вызываются только через `capi` (добавляет `company`).

**Почему.** В частях приложения ~27 чтений `is_admin`/`is_owner`; их смысл — «в этом месте» — совпадает с ролью в
компании открытого экрана.

## R14. Имена и роль новых действий

**Решение.** Действия только владельца бота — с приставкой `bot.` и ролью `BOT` (отказ 403 «Только для владельца
бота.»); `company.label.set` — роль «зарегистрированный».

**Почему.** Приставка `admin.` включает проверку «администратор» и попадает в таблицы прав (48 действий × роли);
действия владельца бота не относятся ни к событию, ни к правам администратора.

## Уточнения при реализации

Записаны по ходу `/speckit-implement` (2026-11-23/24). Решения владельца не менялись; здесь — то, чего план и контракт не
определяли, и одно изменение ожидания прежнего теста.

### R15. Строка владельца бота, когда компания уходит назначенному владельцу

**Решение.** При смене `owner_id` с 0 на человека строка владельца бота в компании удаляется, если он не участник её
событий и не в её семьях (дальше он в ней гость, как в quickstart, шаг 6); иначе остаётся с `is_admin = 0` (человек
компании без прав — I5, I6 держатся). «Вести самому» (`owner_id` → 0) возвращает строку с `is_admin = 1` (I2). Всё — в том
же пакете `atomic` по прежнему владельцу (`ownerChange`, `src/companies.js`).

**Почему.** Контракт говорит «новому владельцу — строка `is_admin = 1`», но не говорит, что становится с правами владельца
бота: оставлять ему `is_admin = 1` значило бы держать его администратором чужой компании (он получал бы её уведомления и
был бы в её списках), а гость по R9 — без строки.

### R16. Тексты отказа владельца в конвейере

**Решение.** Строки `ACTIONS` хранят текст отказа владельца в прежнем виде («… может только владелец бота.» — так его
сверяют `docs/api.md`, эталон и тест `api-table`); конвейер при отказе строит его заново через `ctx.ownerWord()` компании
вызова (`byOwner`/`ownerRefusal` в `src/api.js`). `admin.transfer` — `onlyBotOwner` (всегда «владелец бота») и признак `bot`.

**Почему.** Один текст на строку таблицы, а в компании с назначенным владельцем нужен «владелец» (R8).

### R17. «Создать ссылку» проиграло переходу по прежней ссылке

**Решение.** `bot.company.link { on: true }` пишет новый код по прежнему коду. Проиграл одновременному «создать» —
отдаёт действующую ссылку победителя; проиграл переходу по прежней ссылке (код стёрт) — создаёт код ещё раз (не больше
двух попыток), чтобы владелец бота получил действующую ссылку, а не пустую. Тест — `atomic`, оба порядка.

### R18. Журнал бота: `owner.transfer` — две записи

**Решение.** По R12 `owner.transfer` пишется и в журнал бота, поэтому прежняя проверка `atomic` «admin.owner.transfer ×2 —
одна передача» (теперь `bot.owner.transfer`, план — «Точечные изменения», п. 1) считает 2 записи с этим кодом: одну в
журнале компании и одну в журнале бота (проверено отдельно). Остальные ожидания прежние.

### R19. Подробности записи `company.owner`

**Решение.** В журнале компании — «→ <имя>», «→ владелец бота» («Вести самому») или «по ссылке: <имя>», без названия
компании; в журнале бота — то же с ««<название>»: » впереди. Автор — кто сменил (по ссылке — сам новый владелец).

### R20. Порядок компаний и номер «Компания N»

**Решение.** Номер N — место строки человека среди всех его строк `company_members` по `joined_at`, затем `company_id`;
компания, которая перестала быть видимой (он вышел из её событий), номер не освобождает — названия остальных не «прыгают».
Список у владельца бота — по id компании (data-model, «Видимость»).

### R21. Номер новой части приложения — `04-companies`

**Решение.** План называл часть `03b-companies`; правило частей (021, `contracts/app-parts.md`) — имена `NN-слово` с
номерами подряд, новая часть — «на своём месте, части после неё перенумеровать». Часть — `04-companies.js.txt`, прежние
`04-event` … `08-start` стали `05-event` … `09-start` (`git mv`, содержимое прежнее); ссылки на них в тестах, `CLAUDE.md`,
`docs/api.md` и спецификации 051 исправлены. Тесты, которые выбирали часть по номеру (`mask`), — по новым номерам.

### R22. Плашка гостя — «администраторам»

**Решение.** Контракт (раздел 5) давал текст «уведомления её организаторам тебе не приходят»; правило слов 044 (тест
`wording`) запрещает «организатор» в текстах для людей. Текст — «уведомления её администраторам тебе не приходят»;
контракт исправлен.

### R23. «Профиль» и «Уведомления» — общая функция корневого экрана

**Решение.** Разделы нужны и на главном экране (одна компания), и на «Компаниях» (FR-5125), поэтому они вынесены из
`renderHome` в `personalSections(nav, greet, people)` (`03-home`) без изменения поведения. Тест `names` (039), который
искал обновление после смены имени в теле `renderHome`, смотрит в `personalSections` и проверяет, что `renderHome` её
вызывает.

### R24. Причина отказа жеребьёвки «Мешают закреплённые пары»

**Решение.** Текст «Владелец бота может убрать часть закреплённых пар» (`describeProblem`, `src/pairs.js`) — о действии
владельца в событии, поэтому строится через `ctx.ownerWord()` компании события; в компании владельца бота — прежний
(эталон e2e не меняется), с назначенным владельцем — «Владелец может убрать…» (тест `companies-manage`). Найдено
правилом T020.
