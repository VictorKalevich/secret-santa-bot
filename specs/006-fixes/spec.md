# Feature Specification: Исправления по ревью и миграции базы

**Feature Branch**: `006-fixes`

**Created**: 2026-11-12

**Status**: Implemented

**Input**: User description: "Исправление найденных при ревью багов и переход на миграции D1 до первого выката.
(1) Перенос участия не должен позволять админу/владельцу получить чужие пары. (2) Уведомление о сообщении в переписке
не должно превышать лимит Telegram при длинном названии эвента. (3) Жеребьёвка укладывается в лимит CPU бесплатного
тарифа даже при невыполнимых ограничениях. (4) Одновременная жеребьёвка двумя админами не перезаписывает пары.
(5) Админ видит, кто заблокировал бота. Мелочи: повторное раскрытие, уведомление об удалении, исключения только между
участниками, переименование админов, порядок очереди сообщений. (6) Схема базы — через миграции, README описывает
миграции и резервную копию."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Перенос участия не раскрывает пары (Priority: P1)

Админ переносит участие человека на его новый аккаунт Telegram (004/005). Сейчас админ может «перенести» любого участника
на собственный аккаунт и так узнать его подопечного, его Санту и прочитать переписку — это нарушает принцип «Тайна по
умолчанию». После исправления перенос на аккаунт администратора (в том числе на свой) запрещён, а прежний аккаунт и все
администраторы получают уведомление о переносе — тайно сделать подмену нельзя.

**Why this priority**: Единственное найденное нарушение тайны пар — главного правила проекта.

**Independent Test**: Админ, не участвующий в жеребьёвке эвента, пытается перенести участника этого эвента на свой
аккаунт → отказ; перенос на обычный новый аккаунт проходит, старый аккаунт и другие админы получают уведомление.

**Acceptance Scenarios**:

1. **Given** админ и участник X с назначенным подопечным, **When** админ переносит X на свой аккаунт, **Then** отказ
   «Переносить участие на аккаунт администратора нельзя», пары и переписка не меняются.
2. **Given** владелец, **When** он переносит участника на аккаунт другого администратора, **Then** такой же отказ.
3. **Given** админ и участник X, **When** админ переносит X на зарегистрированный аккаунт без прав администратора,
   **Then** перенос выполняется, прежний аккаунт X получает сообщение «Твоё участие перенесено на другой аккаунт: <имя>.
   Если это не ты — напиши организатору», а все остальные администраторы — «<админ> перенёс участие <X> на <новый
   аккаунт>».
4. **Given** перенос администратора на его новый аккаунт (делает владелец), **When** новый аккаунт ещё не админ,
   **Then** перенос проходит и права переходят вместе с участием (как раньше).

### User Story 2 — Сообщения переписки доходят всегда (Priority: P1)

Санта или подопечный пишет сообщение максимальной длины (4000 символов) в эвенте с длинным названием (до 80 символов).
Сейчас уведомление получателю не помещается в одно сообщение Telegram, Telegram его отклоняет, а отправитель видит
«Отправлено». После исправления название эвента в заголовке уведомления сокращается так, что сообщение всегда помещается.

**Why this priority**: Тихая потеря сообщения — самая неприятная ошибка переписки: никто не узнает, что она случилась.

**Independent Test**: Эвент с названием из 80 символов, сообщение из 4000 символов → получатель получает уведомление
целиком; название в заголовке сокращено с многоточием.

**Acceptance Scenarios**:

1. **Given** название эвента 80 символов, **When** Санта отправляет 4000 символов, **Then** подопечный получает
   уведомление, длина которого не превышает лимит одного сообщения Telegram.
2. **Given** короткое название, **When** отправлено любое сообщение, **Then** название в заголовке показано полностью.
3. **Given** Telegram отклонил сообщение из очереди как некорректное, **When** очередь обрабатывается, **Then** в журнале
   Worker остаётся запись с кодом и описанием ошибки (без текста сообщения).

### User Story 3 — Жеребьёвка не падает на сложных ограничениях (Priority: P1)

Админ задаёт много исключений, и жеребьёвка становится невозможной (или очень трудной). Сейчас поиск распределения может
занять сотни миллисекунд процессора, и бесплатный тариф обрывает запрос с ошибкой сервера. После исправления проверка
и проведение жеребьёвки всегда укладываются в лимит, а админ видит понятное объяснение.

**Why this priority**: Ошибка сервера в ключевой момент игры; на бесплатном тарифе вероятна уже при 15–20 участниках.

**Independent Test**: 30 участников с невыполнимыми ограничениями → проверка отвечает «распределить не получается…»
за отведённый объём вычислений; 30 участников без ограничений → жеребьёвка проходит.

**Acceptance Scenarios**:

1. **Given** невыполнимые ограничения (до 50 участников), **When** админ нажимает «Проверить», **Then** приходит
   понятный ответ, а не ошибка сервера.
2. **Given** обычные ограничения (пары-супруги, «не повторять прошлый год»), **When** жеребьёвка, **Then** она проходит
   так же, как раньше.
3. **Given** распределение существует, но найти его за отведённый объём вычислений не удалось, **When** проверка,
   **Then** сообщение предлагает попробовать ещё раз или ослабить исключения.

### User Story 4 — Двойная жеребьёвка невозможна (Priority: P2)

Два админа одновременно (или один — двойным нажатием) запускают жеребьёвку. Сейчас вторая жеребьёвка может перезаписать
пары первой и разослать участникам второе уведомление. После исправления проходит ровно одна жеребьёвка.

**Why this priority**: Редкая гонка, но последствия — смена подопечных после того, как люди их уже увидели.

**Independent Test**: Два одновременных запроса «Провести жеребьёвку» → один успешен, второй получает «Жеребьёвка уже
проведена»; у каждого участника ровно одно уведомление и неизменный подопечный.

**Acceptance Scenarios**:

1. **Given** эвент без жеребьёвки, **When** два запроса жеребьёвки приходят одновременно, **Then** пары записаны один
   раз, уведомлений ровно по одному на участника, второй запрос получает отказ.

---

### User Story 5 — Админ видит, кому не доходят сообщения (Priority: P2)

Участник заблокировал бота (или удалил чат). Сейчас сообщения ему молча пропадают, а в статусах у него всё нормально.
После исправления админ видит в списке участников эвента отметку «🚫 не получает сообщения»; отметка снимается, как
только человек снова пишет боту или открывает приложение.

**Why this priority**: Иначе человек выпадает из игры незаметно (не знает подопечного, не видит переписку).

**Independent Test**: Telegram отвечает «бот заблокирован» на сообщение участнику → в панели админа у него отметка;
участник пишет боту /start → отметка исчезает.

**Acceptance Scenarios**:

1. **Given** Telegram отклонил сообщение участнику как «бот заблокирован пользователем», **When** админ открывает панель
   эвента, **Then** у участника отметка «не получает сообщения».
2. **Given** отметка стоит, **When** участник пишет боту или открывает мини-приложение, **Then** отметка снята.

---

### User Story 6 — Мелкие исправления (Priority: P3)

- Повторное нажатие «Раскрыть» не рассылает имена Сант ещё раз.
- Сообщение «Организатор удалил тебя из эвента» получает только тот, кто действительно был участником.
- Исключение можно добавить только между двумя участниками эвента.
- Переименовать администратора или владельца может только владелец (себя — любой админ); обычных участников — любой админ.
- Если сообщение из очереди не удалось отправить по временной причине, следующие сообщения тому же человеку не обгоняют
  его, а сам повтор не сдвигает сообщение в конец очереди; сбой обработки очереди не теряет сообщения.

**Why this priority**: Мелкие, но заметные шероховатости; по отдельности не ломают игру.

**Acceptance Scenarios**:

1. **Given** тайна уже раскрыта, **When** админ снова нажимает «Раскрыть», **Then** ответ «Уже раскрыто», рассылки нет.
2. **Given** человек не участвует в эвенте, **When** запрос «удалить его из эвента», **Then** отказ, сообщения ему нет.
3. **Given** один из двух людей не участник эвента, **When** админ добавляет исключение, **Then** отказ.
4. **Given** обычный админ, **When** он переименовывает другого администратора или владельца, **Then** отказ
   «Переименовать администратора может только владелец».
5. **Given** обработка очереди оборвалась после того, как сообщения были взяты из очереди, **When** очередь
   обрабатывается снова, **Then** неотправленные сообщения отправляются (допустим редкий дубль, недопустима потеря).

### User Story 7 — Схема базы через миграции (Priority: P1)

Владелец готовит бота к первому выкату. Сейчас схема базы создаётся кодом при первом запросе, а смена версии схемы
удаляет таблицы. Ценность бота — история за годы, поэтому изменения схемы должны применяться явными миграциями, которые
никогда не удаляют данные молча. README объясняет, как применить миграции и как сделать резервную копию.

**Why this priority**: После первого выката поменять подход без риска потерять данные уже нельзя.

**Independent Test**: Чистая база → применить миграции → бот работает; база, созданная прежней версией кода (схема 005),
→ применить миграции → данные на месте, новые поля появились; база без миграций → бот отвечает понятной инструкцией,
а не падает.

**Acceptance Scenarios**:

1. **Given** пустая база, **When** владелец применяет миграции по README, **Then** все таблицы созданы, бот работает.
2. **Given** база схемы 005 с данными, **When** применены миграции, **Then** эвенты, письма, пары и переписка сохранены.
3. **Given** миграции не применены, **When** приходит запрос, **Then** ответ с текстом «База не подготовлена: примени
   миграции (см. README)», ничего не удаляется.
4. **Given** README, **When** владелец следует ему с нуля, **Then** там есть шаги применения миграций (локально и в
   Cloudflare) и создания резервной копии базы.

### Edge Cases

- Перенос с аккаунта, который уже удалён из Telegram: уведомление прежнему аккаунту не доходит — это нормально, админы
  всё равно уведомлены.
- Перенос на «второй» аккаунт, который на самом деле контролирует сам админ, технически не отличить от честного; защита —
  уведомление прежнему аккаунту и всем админам (остаточный риск записан в Assumptions).
- Название эвента состоит из эмодзи: сокращение не разрывает символ пополам.
- Человек заблокировал бота, а потом разблокировал, но не писал боту: отметка остаётся до первого сообщения или открытия
  приложения — это приемлемо.
- Telegram ограничил частоту отправки (429): все оставшиеся сообщения пачки переносятся на следующий запуск без потери
  порядка.
- Жеребьёвка запущена, когда кто-то параллельно удаляет участника: жеребьёвка учитывает состав на момент запуска; удалённый
  после неё участник удаляется уже с перестройкой пар (как раньше).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-601**: Перенос участия MUST отклоняться, если новый аккаунт — администратор или владелец (в том числе сам
  выполняющий перенос).
- **FR-602**: После переноса прежний аккаунт MUST получить уведомление с именем нового аккаунта, а все администраторы,
  кроме выполнившего перенос, — уведомление о том, кто, кого и куда перенёс. Уведомления не содержат пар и писем.
- **FR-603**: Уведомление о сообщении в переписке MUST помещаться в одно сообщение Telegram для любого названия эвента
  (до 80 символов) и любого текста (до 4000 символов); название в заголовке при необходимости сокращается с «…».
- **FR-604**: Отказ Telegram в доставке сообщения из очереди MUST записываться в журнал Worker с кодом и описанием
  ошибки, без текста сообщения.
- **FR-605**: Проверка и проведение жеребьёвки MUST укладываться в лимит процессорного времени бесплатного тарифа
  при любом наборе ограничений для эвентов до 50 участников; при неудаче — понятное сообщение админу.
- **FR-606**: Для ограничений, допускающих распределение, жеребьёвка MUST по-прежнему находить его (качество не хуже
  текущего на типичных наборах: пары-супруги, «не повторять прошлый год», кольцевая).
- **FR-607**: Жеребьёвка эвента MUST проводиться не более одного раза даже при одновременных запросах; второй запрос
  получает «Жеребьёвка уже проведена», пары и уведомления не дублируются.
- **FR-608**: Система MUST запоминать, что Telegram отклонил сообщение человеку из-за блокировки бота, и показывать
  админу в списке участников эвента отметку «не получает сообщения».
- **FR-609**: Отметка «не получает сообщения» MUST сниматься, когда человек пишет боту, нажимает кнопку бота или
  открывает мини-приложение.
- **FR-610**: Повторное раскрытие тайны MUST отклоняться без рассылки.
- **FR-611**: Удаление из эвента MUST отклоняться для человека, который в нём не участвует; уведомление об удалении
  получают только участники.
- **FR-612**: Исключение MUST добавляться только между двумя разными участниками эвента.
- **FR-613**: Переименовывать администраторов и владельца MUST только владелец; администратор может переименовать себя
  и обычных участников.
- **FR-614**: Очередь сообщений MUST сохранять исходный порядок при повторе; сообщение человеку не отправляется раньше
  более старого неотправленного сообщения тому же человеку; сбой обработки не теряет взятые сообщения (повтор не ранее
  чем через минуту).
- **FR-615**: Схема базы MUST создаваться и изменяться только миграциями из папки `migrations/`; код MUST NOT создавать
  или удалять таблицы.
- **FR-616**: Если миграции не применены или устарели, бот MUST отвечать понятной инструкцией (HTTP 500 с текстом для
  страниц/API, без падения cron) и не изменять данные.
- **FR-617**: Миграции MUST применяться и к пустой базе, и к базе, созданной кодом 005, без потери данных.
- **FR-618**: README MUST описывать применение миграций (локально и в Cloudflare), порядок при обновлении бота
  и создание резервной копии базы.

### Key Entities *(include if feature involves data)*

- **Человек (users)**: добавляется отметка времени «Telegram сообщил, что бот заблокирован» (пусто — сообщения доходят).
- **Очередь сообщений (outbox)**: добавляется время, до которого сообщение «взято в отправку»; после успешной отправки
  сообщение удаляется, после сбоя снова доступно.
- **Миграция**: пронумерованный SQL-файл; применённые миграции учитываются в базе; номер схемы в настройках бота
  показывает коду, что база готова.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-601**: 0 способов для администратора или владельца получить ответ API с подопечным, Сантой или перепиской
  чужого участника (проверяется сквозным тестом переноса).
- **SC-602**: 100% сообщений переписки длиной до 4000 символов доходят получателю при любом названии эвента до 80 символов.
- **SC-603**: Проверка жеребьёвки для 50 участников с невыполнимыми ограничениями укладывается в 10 мс процессорного
  времени на эталонном замере (Node, тест), а для 50 участников без ограничений находит распределение в 100% запусков.
- **SC-604**: При двух одновременных запросах жеребьёвки — ровно один набор пар и ровно одно уведомление на участника.
- **SC-605**: Админ узнаёт о заблокировавшем бота участнике при следующем открытии панели эвента после первой неудачной
  доставки.
- **SC-606**: Обновление с базы 005 на 006 по README проходит без потери данных (сквозной тест на копии базы).

## Assumptions

- Бот ещё ни разу не выкатывался: первая миграция повторяет схему 005 (`CREATE TABLE IF NOT EXISTS`), поэтому она
  безопасна и для пустой базы, и для локальной базы разработчика, созданной кодом 005; изменения 006 — во второй миграции.
- Полностью исключить злоупотребление переносом (на «второй» аккаунт, подконтрольный админу) нельзя без отказа от
  переноса; принятая защита — запрет на аккаунты админов и уведомление прежнего аккаунта и всех админов. Это
  согласуется с принципом I: админ не может получить пары незаметно.
- Лимит процессорного времени проверяется эталонным замером в Node с запасом (порог теста — 10 мс на один вызов
  проверки); в Workers время не идёт во время вычислений, поэтому ограничение — по числу шагов алгоритма, а не по часам.
- Отметка «не получает сообщения» ставится только по ответу Telegram «бот заблокирован / пользователь удалён»
  (код 403); прочие ошибки 400 отметку не ставят.
- Редкий дубль сообщения после сбоя обработки очереди допустим; потеря — нет.
- Функции админа из ревью (объявления, расписание, «подарок получен», шаблон эвента, отмена жеребьёвки, журнал) —
  отдельная фича 007; адрес доставки, «семьи», заявки — фича 008.
