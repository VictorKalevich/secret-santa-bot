# Feature Specification: Полный сброс события; удаление и перенос участников

**Feature Branch**: `004-event-reset`

**Created**: 2026-11-12

**Status**: Implemented

**Input**: User description: "У админа должна быть возможность произвести полный сброс события: этот сброс удаляет всех
зарегистрированных, а также сбрасывает заполненные данные о подарках. И отдельно удалять поштучно зарегистрированных людей,
например, если кто-то был зарегистрирован, потерял доступ к аккаунту и снова зарегистрировался."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Полный сброс события (Priority: P1)

Владелец во вкладке «Админ» в «Опасной зоне» нажимает «🧨 Полный сброс игры», читает, что будет удалено, вводит слово
«СБРОС» и подтверждает. Удаляются все участники и администраторы (кроме самого владельца), письма, пары, исключения,
отметки «подарок готов», переписка, история прошлых пар и параметры игры (бюджет, даты, место, заметки). Создаётся новая
пригласительная ссылка, регистрация открывается. Удалённые получают сообщение, что игра начата заново.

**Why this priority**: Нужно начать событие с нуля (новая компания, новый год, тестовый прогон перед настоящей игрой).

**Independent Test**: Зарегистрировать 4 человек, провести жеребьёвку, сделать сброс → в админке только владелец, старая
пригласительная ссылка не работает, новая работает, у владельца пустое письмо и нет подопечного.

**Acceptance Scenarios**:

1. **Given** идёт игра, **When** владелец вводит «СБРОС» и подтверждает, **Then** все, кроме владельца, удалены,
   данные игры очищены, получена новая пригласительная ссылка.
2. **Given** слово введено неверно, **When** владелец жмёт «Сбросить», **Then** ничего не происходит (кнопка недоступна;
   сервер тоже отклоняет).
3. **Given** обычный админ, **When** он открывает «Админ», **Then** кнопки полного сброса нет, а прямой запрос отклоняется.
4. **Given** сброс выполнен, **When** удалённый участник открывает приложение или старую ссылку, **Then** видит, что нужна
   новая пригласительная ссылка.

### User Story 2 — Удаление участника поштучно (Priority: P1)

Админ открывает участника в списке (кнопка «⋯») и выбирает «🗑 Удалить из игры». Работает и для недорегистрированных
(«регистрируется…»), и после жеребьёвки (как в 001 — меняется минимум пар). Ограничения ролей из 002 сохраняются.

**Why this priority**: Убрать лишнюю или «мёртвую» запись — частая операция.

**Independent Test**: Удалить недорегистрированную запись и обычного участника — обе исчезают из списка.

**Acceptance Scenarios**:

1. **Given** запись «регистрируется…», **When** админ удаляет её, **Then** запись исчезает.
2. **Given** участник после жеребьёвки, **When** админ удаляет его, **Then** пары остальных меняются минимально (как в 001).

---

### User Story 3 — Перенос участия на новый аккаунт (Priority: P1)

Человек потерял доступ к Telegram-аккаунту и зарегистрировался заново с нового. Админ открывает старую запись («⋯») →
«🔁 Перенести на новый аккаунт» → выбирает новую запись → подтверждает. Новый аккаунт получает место старого: письмо
(если в новом пусто), подопечного и Санту, отметку «подарок готов», исключения, переписку, роль админа. Старая запись
удаляется. Пары остальных не меняются, никто, кроме самого человека, не получает уведомлений.

**Why this priority**: Это пример пользователя; простое удаление после жеребьёвки поменяло бы подопечного у его Санты и
отняло у человека уже выбранного подопечного.

**Independent Test**: После жеребьёвки Катя регистрируется с нового аккаунта; админ переносит старую Катю на новую → у новой
тот же подопечный, та же переписка и письмо; у её Санты подопечный не изменился; старой записи нет.

**Acceptance Scenarios**:

1. **Given** старая и новая записи после жеребьёвки, **When** админ переносит, **Then** новая запись — в жеребьёвке
   на месте старой, пары у всех остальных прежние, старая удалена.
2. **Given** у новой записи уже есть письмо, **When** перенос, **Then** письмо новой записи сохраняется.
3. **Given** старая запись — владелец, **When** админ пытается перенести, **Then** отказ: владелец восстанавливает доступ
   по ссылке владельца (002).
4. **Given** старая запись — админ, а действует не владелец, **When** перенос, **Then** отказ (как удаление админа в 002).
5. **Given** новая запись уже участвует в жеребьёвке, **When** перенос, **Then** отказ с объяснением.

### Edge Cases

- Сброс, когда владелец — единственный пользователь → данные игры очищаются, ссылка обновляется.
- Сообщения в очереди для удалённых при сбросе → не отправляются (очередь очищается перед уведомлением о сбросе).
- Перенос до жеребьёвки → переносятся письмо, исключения и роль; пар ещё нет.
- Перенос на ту же запись → отказ.
- Перенос, когда в исключениях есть и старая, и новая запись → дубликаты исключений не появляются, «сам себе» удаляется.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-401**: Только владелец MUST иметь возможность выполнить полный сброс; требуется ввод слова «СБРОС».
- **FR-402**: Полный сброс MUST удалить всех пользователей, кроме владельца, и очистить: письма, пары, исключения,
  отметки «подарок готов», переписку, историю пар, очередь сообщений, параметры игры; MUST сбросить состояние жеребьёвки
  и раскрытия, открыть регистрацию и выпустить новую пригласительную ссылку.
- **FR-403**: После сброса владелец MUST остаться владельцем; его письмо очищается, участие сохраняется.
- **FR-404**: Удалённые сбросом пользователи MUST получить сообщение, что игра начата заново.
- **FR-405**: Админ MUST иметь возможность удалить любую запись (в том числе недорегистрированную) с учётом ограничений 002.
- **FR-406**: Админ MUST иметь возможность перенести участие со старой записи на новую зарегистрированную запись, которая
  не участвует в жеребьёвке: пары (как Санта и как подопечный), «подарок готов», переписка, исключения, история пар,
  роль админа, письмо (если у новой пусто); старая запись удаляется.
- **FR-407**: Перенос MUST NOT менять пары других участников и MUST NOT рассылать уведомления, кроме сообщения новой записи.
- **FR-408**: Перенос записи владельца MUST быть невозможен; перенос записи админа — только владельцем.
- **FR-409**: Действия над участником (письмо, переименовать, перенести, удалить) MUST быть собраны в одном меню участника.

### Key Entities *(include if feature involves data)*

- Без новых сущностей; затрагиваются все таблицы из 001–003.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-401**: После сброса в базе 1 пользователь (владелец), 0 пар, 0 исключений, 0 сообщений переписки.
- **SC-402**: Перенос участия меняет 0 пар других участников (100% проверок).
- **SC-403**: Сброс невозможно выполнить случайно: нужны 3 действия (кнопка, ввод слова, подтверждение).

## Assumptions

- «Полный сброс» отличается от «Новой игры» (001): новая игра сохраняет участников и письма, сброс удаляет всех.
- Настройки бота (адрес, имя бота, владелец) сброс не трогает; `ADMIN_SECRET` и токен остаются прежними.
- Удалённые сбросом при желании регистрируются заново по новой ссылке.
