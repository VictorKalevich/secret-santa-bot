# Исследование 056: автозавершение брошенных событий

## R1. Где проверять правила

- **Decision**: в ежедневном шаге cron (`dailyStep`, с `REMINDER_HOUR` по местному времени), в той же ветке, что и
  ежедневные напоминания: только для событий с `last_daily != сегодня`, затем событие отмечается проверенным.
- **Rationale**: шаг уже читает все идущие события по индексу `events_active` (054) — у правил А и Б нет ни одного
  лишнего чтения; отметка `last_daily` даёт «не чаще раза в сутки»; «одно тяжёлое действие за запуск» (009, FR-911)
  ограничивает рассылки предупреждений и завершения.
- **Alternatives**: отдельный шаг cron раз в сутки по своему расписанию — второй триггер (на бесплатном тарифе их 5 на
  аккаунт) и свой учёт «сегодня сделано»; проверка в минутной проверке уведомлений — каждую минуту, лишние чтения.

## R2. Как хранить «предупреждены»

- **Decision**: колонка `events.finish_warned TEXT NOT NULL DEFAULT ''` — местная дата предупреждения `YYYY-MM-DD`;
  миграция `0019`, схема 19.
- **Rationale**: явное состояние «предупреждены / нет» с датой: завершение — когда `addDays(finish_warned, 7) <= сегодня`
  (по датам, как остальные правила расписания — `draw_auto_date`, `event_date`; при сравнении миллисекунд завершение
  уезжало бы на день из-за минут между проходами); снятие — простая запись `''`; новый цикл предупреждения — с чистого
  листа.
- **Alternatives**: запись журнала `finish.warn` как отметка — без миграции, но снятие отметки и повторное
  предупреждение не выразить (пришлось бы писать запись «отмена» или считать предупреждение действительным N дней:
  после «указал дату → убрал дату» событие завершилось бы без нового предупреждения); миллисекунды — см. выше.

## R3. Порядок и разбиение правил

- **Decision**: дата есть → только А (`addDays(event_date, 7) <= сегодня`); даты нет → Г (без жеребьёвки, `outsiders = 0`,
  `addDays(создано, 23) <= сегодня`), иначе Б (`addDays(создано, 113) <= сегодня`). Местная дата создания —
  `localDate(env, created_at)`. Отметка не помнит причину (spec, Assumptions).
- **Rationale**: будущая дата защищает от всех правил; группы не пересекаются, и «перенеси / укажи дату» — единственный
  совет, который всегда оставляет событие.

## R4. «Участники, кроме организаторов» без лишних запросов

- **Decision**: колонка `outsiders` в том же запросе событий ежедневного шага:
  `CASE WHEN ?open AND last_daily != ?today AND event_date = '' AND draw_done = 0 AND created_at <= ?since
  THEN (SELECT COUNT(*) FROM members m WHERE m.event_id = events.id AND m.user_id != <владелец бота> AND NOT EXISTS
  (<строка company_members компании события с is_admin = 1>)) ELSE -1 END`.
  `since` — сейчас минус 22 дня (точная проверка 23 дней — по датам в JS).
- **Rationale**: обычная минута остаётся на 3 запросах (`queries`: `cron (обычная минута)` — `[3, 0]`); CASE в SQLite
  вычисляет подзапрос только при истинном условии — читаются участники лишь событий-кандидатов, ещё не проверенных
  сегодня (после проверки `last_daily = сегодня`); поиск — по ключам `members (event_id, user_id)`, `company_members
  (company_id, user_id)`, `settings (key)` (тест планов — без полных просмотров, кроме разрешённых). Владелец компании
  всегда имеет строку с `is_admin = 1` (инвариант I3, 050/051: `createOwnCompany`, `ownerChange`), поэтому отдельной
  проверки `companies.owner_id` нет — и таблица компаний в обычную минуту не упоминается (`cron-reads`: «компании не
  читаются»); владелец бота — организатор в любой компании (Конституция VII), даже где он гость без строки. Запрос —
  без псевдонима (`FROM events WHERE status = 'active'`, как в 054: тест `cron-reads` находит его по этому тексту).
- **Alternatives**: отдельный запрос участников кандидатов — +1 запрос в минуты с кандидатами; признак в JS по
  `ctx.in(...).users()` — по запросу на компанию.

## R5. Приоритеты в ежедневном шаге

- **Decision**: автодействия расписания (`dueAutoAction`) — как были, первыми. Для события, не проверенного сегодня:
  завершение по правилам → кандидат; иначе ежедневное напоминание → кандидат (как было); иначе предупреждение →
  кандидат; иначе снятие отметки (без сообщений, пакетом с `last_daily`); иначе «тихое» (как было).
- **Rationale**: завершённому событию напоминание не нужно; предупреждение может подождать день; напоминания и
  автодействия ведут себя прежне. Кандидаты — общий список, один за запуск (выбор по минуте суток, как было).

## R6. Атомарность предупреждения

- **Decision**: `atomic(db, "EXISTS (SELECT 1 FROM events WHERE id = ? AND status = 'active' AND finish_warned = '')")`:
  сообщения организаторам (`enqueue`) и `audit(finish.warn)` — перед захватом, захват —
  `UPDATE events SET finish_warned = ?, last_daily = ? WHERE id = ? AND status = 'active' AND finish_warned = ''`
  (вид «по прежнему состоянию», 020).
- **Rationale**: два одновременных запуска cron (или ручное завершение рядом) — одно предупреждение и одна запись; если
  событие уже завершено — ничего. Завершение — существующее `finishEvent` (атомарное с 009/020).

## R7. Получатели и тексты

- **Decision**: получатели — `adminRecipients(await ctx.users())` контекста компании события (как сообщение о неудачной
  автожеребьёвке): администраторы компании (у владельца компании строка администратора есть всегда); владелец бота —
  только если он человек компании. Тексты — в контракте (`contracts/auto-finish.md`): «⏳ Событие «…» завершится
  автоматически <дата>: <причина>.» + как оставить + кнопка «⚙️ Открыть событие».
- **Rationale**: «событие» по правилам 013; без имён и пар; дата — `formatDate`, как в напоминаниях.

## R8. Только открытый бот

- **Decision**: правила включает `openBot(env)` (единственное чтение `OPEN_BOT`, 052). В закрытом боте `outsiders`
  не считается (параметр `open = 0`), правила не проверяются, отметка не ставится.
- **Rationale**: решение владельца «закрытый бот не меняется».
