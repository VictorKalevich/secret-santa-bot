# Research: повторные нажатия — одно действие, один результат

Все пакеты — помощником `atomic` (`src/claim.js`, фича 020). Два вида условий: «захват мой» (у захвата уникальное
значение; захват первым, остальное — после него по этому значению) и «по прежнему состоянию» (всё — перед захватом с
условием на состояние, которое захват отменяет; захват последним). Время и автор не служат признаком «мой захват».

## R1. Рассылки по желанию: объявление, напоминания, приглашение — окно в минуту

**Decision**: «по прежнему состоянию» с окном `REPEAT_MS = 60 000` мс. Опора — то, что рассылка оставляет в базе:

| Действие | Условие (до записи) | Захват — последним |
|---|---|---|
| `admin.announce` | нет объявления с тем же текстом в событии новее `now − REPEAT_MS` | `INSERT INTO announcements … SELECT … WHERE` условие |
| `admin.remind.unfilled`, `admin.remind.santas` (ручные) | нет записи журнала `remind.unfilled` / `remind.santas` в событии новее `now − REPEAT_MS` | запись журнала |
| `admin.event.invite_from` | нет записи `invite.from` в событии новее `now − REPEAT_MS` | запись журнала |

Сообщения людям (`enqueue`) — перед захватом с тем же условием. Второй из одновременных вызовов (пакеты D1 идут по
очереди) видит опору первого — его условие ложно, ничего не пишется; `run()` → `won: false` → отказ. Время здесь —
граница окна, а не признак «мой»: у двух вызовов в одну миллисекунду граница одна и та же, опора первого (время `now`)
новее неё.

Тексты отказов: «Это объявление уже отправлено.»; «Напоминание уже отправлено — повторить можно через минуту.»;
«Приглашения уже отправлены — повторить можно через минуту.»

Плановые напоминания (cron, `actor = 0`) — прежний путь: у них своя отметка `last_daily` в том же пакете (009), а при
окне её запись тоже пришлось бы делать условной. Ручное напоминание видит и плановое (та же запись журнала).

**Alternatives considered**: ключ запроса от приложения (одноразовый код на нажатие) — отличает осознанный повтор от
случайного, но нужна таблица ключей (миграция, `REGISTRY`) и правка всех вызовов в приложении; повторы сети и второе
устройство всё равно приходят с разными ключами от второго устройства. Отклонено: окно проще и закрывает все
источники. Окно по любому объявлению (не по тексту) — запретило бы двум админам разные объявления. Отклонено.

## R2. Полный сброс — «захват мой» по новому коду приглашения

**Decision**: сброс и так ставит новый случайный `invite_code`. Захват — первым: `UPDATE events SET … invite_code =
<новый> … WHERE id = ? AND invite_code = <прежний>` (прежний — из события, прочитанного конвейером); остальное — после
него с условием `EXISTS (SELECT 1 FROM events WHERE id = ? AND invite_code = <новый>)`: уведомления удалённым,
удаление данных (`eventDataDeleteStmts(…, keepEvent)` с `guard`), журнал. Для захвата — новый построитель
`updateEventIfStmt(db, id, fields, guard, …args)` в `src/db.js` (как `enqueueIfStmt`/`auditIfStmt`). Второй сброс (и
сброс одновременно со сменой ссылки) — `won: false` → 400 «Событие уже сброшено или изменилось одновременно со сбросом
— обнови экран.»; строка `admin.reset.full` в `ACTIONS` передаёт отказ.

## R3. Роли и владение — «по прежнему состоянию»

**Decision**:

- `grantAdmin`: условие `EXISTS (SELECT 1 FROM users WHERE tg_id = ? AND is_admin = 0)`; уведомление назначенному,
  остальным админам, журнал; захват последним — `UPDATE users SET is_admin = 1 WHERE tg_id = ? AND is_admin = 0`;
  проигравший — «Он(а) уже администратор.» (прежний текст).
- `revokeAdmin`: условие `… AND is_admin = 1`; возврат обращений (`returnThreadsStmts` получает `guard`, по умолчанию
  без условия — как раньше), уведомления, журнал; захват — `UPDATE users SET is_admin = 0 WHERE tg_id = ? AND
  is_admin = 1`; проигравший — «Он(а) не администратор.» (прежний текст).
- `setOwner` при передаче (`via: 'transfer'`): условие `EXISTS (SELECT 1 FROM settings WHERE key = 'owner_id' AND
  value = ?)` (прежний владелец); права админа новому, журнал, уведомления; захват — `UPDATE settings SET value = ?
  WHERE key = 'owner_id' AND value = ?`; проигравший — 400 «Права владельца уже переданы.» Переход по ссылке владельца
  (`via: 'link'`) — как раньше (защита — `claimOwnerLink`).

## R4. Новая семья — отказ вместо 500

**Decision**: пакет D1 — транзакция: второй одновременный вызов падает на первичном ключе `family_members.user_id`
(человек уже в семье) и откатывается целиком — данные не портятся. `saveFamily` ловит только ошибку `UNIQUE constraint
failed: family_members`, заново читает «кто уже в семье» (тот же запрос, что до записи) и отвечает прежним текстом
«<Имя> уже в семье «<название>».»; другие ошибки — как раньше (500).

**Alternatives considered**: условия «по прежнему состоянию» на каждом операторе — у новой семьи нет номера до
вставки, а условие «никто из состава не в семье» становится ложным после первой же вставки члена этой семьи. Отклонено.

## R5. Кнопки приложения

**Decision**: `busy(btn, fn)` (`src/app/02-core.js.txt`) принимает кнопку, список кнопок или `null`; шесть вызовов
`busy(null, …)` получают кнопки: режимы уведомлений — все три; строка администратора — обе (👑 и ✕); заявка — обе
(✅ и ❌); удаление исключения и закреплённой пары — нажатая (`e.currentTarget`). Классы не меняются. Вида
«недоступна» у `ds-icon-btn` и `ds-segmented__item` нет (есть у `ds-btn`: `opacity: var(--ds-opacity-disabled)`) —
добавляется то же правило `:disabled` в `design-system/components.css`, состояние показывается в `preview.html` и
упоминается в `design-system/README.md` (правило 2 `CLAUDE.md`; новых токенов нет). Новый тест
`tests/app-buttons.test.mjs`: в склейке нет `busy(null` и `busy(undefined`; «от противного» — на искусственном тексте.

## R6. Что не меняется и как проверяется

- Число запросов: каждое действие — те же чтения и один пакет записи; `tests/queries.test.mjs` без правок.
- Эталон отказов (`tests/fixtures/api-refusals.json`) — отказы до обработчика, не меняются.
- `tests/atomic.test.mjs` — блок «повторные нажатия (024)», в одну миллисекунду (`sameMoment`): 9 действий по одной
  проверке + разные тексты объявлений одновременно + то же объявление через минуту (время записей сдвигается в базе
  теста). До правки кода проверки падают.
- Тексты отказов — по правилам слов (013), `tests/wording.test.mjs`.
