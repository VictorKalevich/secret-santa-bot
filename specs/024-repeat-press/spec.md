# Feature Specification: Повторные нажатия — одно действие, один результат

**Feature Branch**: `024-repeat-press`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Фича «повторные нажатия»: пункты 6, 7 и кнопки из 11 списка «Решения владельца» —
рассылки без защиты от двойного вызова (объявление, напоминания, полный сброс, назначение админа, передача владения,
приглашение из события), двойное сохранение новой семьи (500 вместо понятного отказа), кнопки приложения, которые не
блокируются на время запроса."

## Контекст

Правило проекта «одно действие — один результат» (фичи 009, 020) выполняется у жеребьёвки, раскрытия, завершения,
удаления, отмен, заявок, обращений, исключений и закреплённых пар. Остались действия без защиты — двойной вызов
(два устройства, два админа, повтор запроса сетью, кнопка без блокировки) даёт двойной результат (проверено на
текущем коде, `docs/refactoring/baseline.md`, раздел 4):

| Действие | Что сейчас при двойном вызове |
|---|---|
| Объявление | каждый участник получает его дважды, две записи объявления и журнала |
| Напоминание о пустом письме, напоминание Сантам | два напоминания каждому, две записи журнала |
| Приглашение из другого события | два приглашения каждому, две записи журнала |
| Полный сброс | два уведомления каждому удалённому, две записи журнала |
| Назначение админа | два уведомления назначенному и остальным админам |
| Снятие прав админа | два уведомления, обращения «снова ничьи» — дважды всем админам, две записи журнала |
| Передача владения | два уведомления, две записи журнала |
| Сохранение новой семьи | второй — «Ошибка сервера. Попробуй ещё раз.» вместо понятного отказа |

В приложении шесть кнопок не блокируются на время запроса: уведомления (звук/тихо/выкл), передача владения, снятие
прав админа, «принять»/«отклонить» заявку, удаление исключения, удаление закреплённой пары.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Рассылка уходит один раз (Priority: P1)

Админ отправляет объявление, напоминание или приглашение; запрос приходит дважды (второе устройство, второй админ,
повтор сети). Люди получают сообщение один раз; второй вызов получает понятный отказ.

**Why this priority**: двойные сообщения видят все участники — самый заметный дефект.

**Independent Test**: два одновременных вызова (оба читают, потом пишут; в одну миллисекунду) — считаются сообщения
участникам и записи журнала.

**Acceptance Scenarios**:

1. **Given** событие с участниками, **When** два вызова «объявление» с одним текстом приходят одновременно, **Then**
   каждый участник получает объявление один раз, объявление сохранено один раз, запись журнала одна; второй вызов —
   400 «Это объявление уже отправлено.»
2. **Given** то же, **When** два админа одновременно отправляют объявления с разными текстами, **Then** уходят оба.
3. **Given** то же объявление было отправлено больше минуты назад, **When** админ отправляет его снова, **Then** оно
   уходит (повтор по желанию не запрещён).
4. **Given** участники с пустыми письмами, **When** «напомнить о письме» нажато дважды одновременно, **Then** каждый
   получает одно напоминание, запись журнала одна; второй — 400 «Напоминание уже отправлено — повторить можно через
   минуту.» То же для напоминания Сантам.
5. **Given** другое событие с участниками, **When** «пригласить из события» вызвано дважды одновременно, **Then**
   каждый получает одно приглашение, запись журнала одна; второй — 400 «Приглашения уже отправлены — повторить можно
   через минуту.»

---

### User Story 2 — Роли, владение и сброс — один раз (Priority: P1)

Владелец назначает или снимает админа, передаёт владение или делает полный сброс события, и запрос приходит дважды.
Действие выполняется один раз: одно уведомление каждому, одна запись журнала; второй вызов получает отказ.

**Why this priority**: лишние уведомления о ролях и сбросе путают людей, двойные записи журнала — организаторов.

**Independent Test**: два одновременных вызова владельца (в одну миллисекунду).

**Acceptance Scenarios**:

1. **Given** зарегистрированный человек не админ, **When** «назначить админом» ×2, **Then** одно уведомление ему, одно
   каждому другому админу, одна запись журнала; второй — 400 «Он(а) уже администратор.»
2. **Given** админ, **When** «снять права» ×2, **Then** одно уведомление ему, одно — остальным; его обращения
   «снова ничьи» — по одному сообщению; одна запись `role.revoke`; второй — 400 «Он(а) не администратор.»
3. **Given** владелец, **When** «передать владение» ×2, **Then** одно уведомление новому владельцу, одна запись
   журнала; второй — 400 «Права владельца уже переданы.»
4. **Given** событие с участниками, **When** «полный сброс» (слово «СБРОС») ×2, **Then** каждый удалённый получает одно
   уведомление, запись `reset` одна; второй — 400 «Событие уже сброшено или изменилось одновременно со сбросом —
   обнови экран.»

---

### User Story 3 — Семья: понятный отказ вместо ошибки сервера (Priority: P2)

Админ сохраняет новую семью, и запрос приходит дважды. Семья сохраняется одна; второй вызов получает тот же отказ,
что и при последовательном повторе: «<Имя> уже в семье «<название>».»

**Why this priority**: данные не портятся и сейчас (второй вызов откатывается целиком), но «Ошибка сервера» пугает.

**Independent Test**: два одновременных вызова «сохранить семью» с одним составом.

**Acceptance Scenarios**:

1. **Given** двое без семьи, **When** «сохранить новую семью» из них ×2, **Then** семья одна, ответы 200 и 400 с
   текстом «<Имя> уже в семье «<название>».», ошибок сервера нет, запись журнала одна.

---

### User Story 4 — Кнопки приложения блокируются на время запроса (Priority: P2)

Каждая кнопка приложения, которая отправляет запрос, недоступна, пока запрос идёт: второе нажатие не отправляет
второй запрос.

**Why this priority**: убирает самый частый источник двойного вызова — нетерпеливое второе нажатие.

**Independent Test**: проверка собранной страницы — у вызова «занято» всегда есть кнопка, которую он блокирует.

**Acceptance Scenarios**:

1. **Given** экран уведомлений, **When** нажата «Тихо», **Then** все три кнопки режима недоступны до ответа.
2. **Given** список администраторов, **When** после подтверждения идёт передача владения или снятие прав, **Then**
   обе кнопки этой строки недоступны до ответа.
3. **Given** заявка на вступление, **When** нажато «принять» или «отклонить», **Then** обе кнопки заявки недоступны до
   ответа.
4. **Given** исключение или закреплённая пара, **When** нажат «✕», **Then** эта кнопка недоступна до ответа.

---

### Edge Cases

- **Окно повтора — минута.** Рассылка того же вида в том же событии меньше чем через минуту считается повтором; через
  минуту — снова можно. Для объявления повтор — тот же текст; другой текст уходит сразу.
- **Плановые напоминания бота (cron)** — не меняются: у них своя отметка «сегодня уже напоминал» (009). Ручное
  напоминание сразу после планового получает отказ «уже отправлено» — люди его только что получили.
- **Сброс одновременно со сменой пригласительной ссылки** — сброс получает тот же отказ (событие изменилось); после
  обновления экрана можно повторить.
- **Повторное сохранение существующей семьи** (переименование, состав) — без изменений: результат тот же, это не
  ошибка.
- **Владелец через ссылку `/setup`** — без изменений (у ссылки своя одноразовая защита).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-2401**: Объявление с тем же текстом в том же событии в течение минуты после предыдущего не рассылается и не
  сохраняется повторно; второй вызов — 400 «Это объявление уже отправлено.» Объявления с другим текстом не
  ограничиваются.
- **FR-2402**: Ручное напоминание о пустом письме и ручное напоминание Сантам в том же событии в течение минуты после
  предыдущего такого же (ручного или планового) не рассылается; 400 «Напоминание уже отправлено — повторить можно через
  минуту.» Плановые напоминания — как раньше.
- **FR-2403**: Приглашение из другого события в то же событие в течение минуты после предыдущего не рассылается;
  400 «Приглашения уже отправлены — повторить можно через минуту.»
- **FR-2404**: Из двух одновременных полных сбросов события выполняется один: уведомления, удаление данных и запись
  журнала — один раз; второй — 400 «Событие уже сброшено или изменилось одновременно со сбросом — обнови экран.»
- **FR-2405**: Из двух одновременных назначений одного человека админом выполняется одно (уведомления и журнал — один
  раз), второе — 400 «Он(а) уже администратор.»; то же для снятия прав — второе 400 «Он(а) не администратор.», включая
  возврат его обращений в «ничьи» (сообщения о них — один раз).
- **FR-2406**: Из двух одновременных передач владения выполняется одна; вторая — 400 «Права владельца уже переданы.»
- **FR-2407**: Второе одновременное сохранение новой семьи с тем же составом получает 400 с тем же текстом, что и
  последовательное («<Имя> уже в семье «<название>».»), а не 500; данные — как после одного сохранения.
- **FR-2408**: Признак «действие уже выполнено» — состояние базы до записи (отправленное объявление, запись журнала,
  роль, владелец, код приглашения события), а не время или автор вызова; два нажатия одного человека в одну
  миллисекунду тоже дают один результат (правило 020). Пакеты собираются помощником атомарных действий.
- **FR-2409**: Каждый вызов «занято» в приложении блокирует кнопку (кнопки), которой он запущен; вызовов без кнопки в
  собранной странице нет — это проверяет тест.
- **FR-2410**: Не меняются: тексты сообщений людям, прочие отказы, права, число запросов к базе и к Telegram на вызов,
  схема базы, плановые напоминания бота, вид приложения.
- **FR-2411**: `docs/api.md` (новые отказы в разделах действий), `CLAUDE.md`, план рефакторинга («Решения владельца»:
  пункты сделаны), замеры (раздел 4 `baseline.md`) — в той же ветке.

### Key Entities

- **Объявление** — текст, событие, автор, время; повтор — тот же текст в том же событии за минуту.
- **Запись журнала** — событие, код действия, время; по ней узнаётся недавнее напоминание и приглашение.
- **Роль** — признак «администратор» у человека; **владелец** — один, в настройках бота.
- **Код приглашения события** — меняется при сбросе; по новому коду сброс узнаёт свой результат.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-2401**: Для каждого из 9 действий (объявление, 2 напоминания, приглашение, сброс, назначение, снятие, передача
  владения, новая семья) два одновременных вызова в одну миллисекунду дают ровно один результат: одно сообщение
  каждому получателю, одна запись журнала, второй ответ — 400 с текстом из требований (семья — без 500).
- **SC-2402**: Два объявления с разными текстами одновременно — оба уходят; то же объявление через минуту — уходит.
- **SC-2403**: В собранной странице приложения 0 вызовов «занято» без кнопки (было 6).
- **SC-2404**: Все прочие проверки проходят без правок ожиданий: эталон 1125 отказов, таблица числа запросов, тайна,
  права, сквозной сценарий.

## Assumptions

- Минута — достаточное окно: повторы сети и двойные нажатия приходят за секунды, а осознанная повторная рассылка
  того же через минуту не запрещена.
- README не меняется: установка, команды и роли те же; новые отказы видны только при повторе.
- Конституция не меняется: правило «одно действие — один результат» уже в `CLAUDE.md`.
- Повторное сохранение существующей семьи с тем же составом и названием даёт тот же результат и запись журнала —
  в фичу не входит (не дефект данных).
