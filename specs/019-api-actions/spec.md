# Feature Specification: Таблица действий API и контекст запроса

**Feature Branch**: `019-api-actions`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Таблица действий API и контекст запроса. Разработчик добавляет действие API одной строкой
таблицы, где указаны роль, нужно ли событие и разрешено ли действие в завершённом событии; проверки прав выполняются в
одном месте до обработчика, а тесты прав и автотест «владелец ⊇ админ» берут список действий из таблицы. Предметная

ответов те же, порядок проверок тот же, число запросов на действие не растёт, жеребьёвка не медленнее. Основа —
`docs/refactoring/step-4-api-table-context.md`."

Шаг 4 плана рефакторинга (`docs/refactoring-roadmap.md`). Подробности — `docs/refactoring/step-4-api-table-context.md`,

## User Scenarios & Testing *(mandatory)*

Действующие лица — участники, админы и владелец бота (пользуются мини-приложением и чатом с ботом: для них не меняется
ничего, кроме того, что каждое действие делает меньше обращений к базе и оставляет больший запас до лимита бесплатного
тарифа) и разработчик, который добавляет новое действие API или меняет права существующего.

### User Story 1 — Права и условия каждого действия — в одной таблице (Priority: P1)

Разработчик добавляет в мини-приложение новое действие организатора (например, «скопировать параметры события»). Сейчас
обработчики 46 действий админа стоят в одном переключателе на 470 строк: проверка «только владелец» написана внутри
каждой ветки, список «разрешено в завершённом событии» лежит отдельно, а для участников проверки разбросаны по веткам.
Новое действие легко добавить без проверки прав или без строки «разрешено в завершённом». После фичи у каждого из 59
действий (13 участника, 46 админа) есть строка таблицы: кто может его вызвать (любой с подписью, зарегистрированный,
участник события, участник или админ, админ, владелец — с текстом отказа), нужно ли событие, разрешено ли действие в
завершённом событии. Общие проверки выполняются в одном месте до обработчика в прежнем порядке; тесты прав и автотест
«владелец может всё, что админ» берут список действий из таблицы.

**Why this priority**: права — граница тайны пар (Конституция, принципы I и VII). Ошибка в них стоит дороже любой
экономии запросов; таблица делает пропуск проверки видимым.

**Independent Test**: эталон ответов «без прав / несуществующее событие / завершённое событие» для каждого из 59
действий, снятый до изменений, совпадает побайтно по коду и тексту; тесты прав и тайны зелёные без правки ожиданий;
список действий берётся из таблицы.

**Acceptance Scenarios**:

1. **Given** участник без прав админа, **When** он вызывает любое из 46 действий админа (и любое неизвестное действие
   админа), **Then** ответ — 403 «Только для администратора.», как сейчас.
2. **Given** админ, не владелец, **When** он вызывает действие только для владельца на идущем событии, **Then** ответ —
   403 с тем же текстом, что сейчас («… может только владелец бота.» с подлежащим действия или «Служебный просмотр
   доступен только владельцу бота.»).
3. **Given** админ, не владелец, и завершённое событие, **When** он вызывает действие только для владельца, которое
   нельзя в завершённом событии (например, полный сброс), **Then** ответ — 400 «Событие завершено — менять его уже
   нельзя…», а не 403 (проверка владельца — после проверки «событие завершено», как сейчас).
4. **Given** владелец, **When** он вызывает каждое действие админа на свежем событии, **Then** ни одного отказа по
   правам (403).
5. **Given** несуществующее событие, **When** вызывается действие события (участника или админа), **Then** ответ — 404
   «Событие не найдено.»; действия админа без события (создать событие, семьи, пользователи, роли, перенос) отвечают,
   как сейчас.
6. **Given** разработчик добавил в таблицу строку без роли или без признака «разрешено в завершённом» для действия
   события, **When** запускаются быстрые тесты, **Then** тест таблицы падает.

### User Story 2 — Каждое действие делает меньше обращений к базе (Priority: P1)

Организатор открывает панель события, проводит жеребьёвку, удаляет или вписывает участника, отвечает на обращение.
Сейчас каждый вызов админа читает настройки и всех пользователей, а функции читают их снова: панель события — 15
запросов к базе, удаление участника после жеребьёвки — 16, вписывание — 15, жеребьёвка — 14 при лимите 50 на вызов
вместе с сообщениями. Проверка жеребьёвки читает письма всех участников ради списка пустых, открытие события
участником — ради числа участников. После фичи настройки и пользователи читаются один раз на вызов, независимые чтения
идут одним пакетом, вместо текстов писем и адресов из базы приходит признак «пусто / не пусто».

**Why this priority**: лимит бесплатного тарифа (Конституция, принцип V) — 50 внешних запросов и 10 мс процессора на
вызов. Самый тяжёлый вызов — жеребьёвка — сейчас занимает около 40 из 50; разбор писем входит в те же 10 мс, что и
расчёт пар.

**Independent Test**: тест числа запросов со сниженными порогами зелёный; тест паритета «пустое письмо» в базе и в коде
зелёный; эталон жеребьёвки и замер скорости без ухудшения.

**Acceptance Scenarios**:

1. **Given** сценарий числа запросов (владелец, админ, 12 участников), **When** выполняются его 46 действий, **Then** к
   базе: панель события — не больше 6, проверка жеребьёвки — не больше 6, жеребьёвка — не больше 10, удаление
   участника после жеребьёвки — не больше 12, вписывание — не больше 11, каждое действие обращений — на 2 меньше
   базового, остальные — не больше базовых; к Telegram — ровно столько же, сколько сейчас.
2. **Given** письмо или адрес из одних пробельных символов (обычные, неразрывные, табуляция, переводы строк, широкий
   пробел), **When** панель события и проверка жеребьёвки считают «письмо есть / адрес указан / пустые письма»,
   **Then** результат тот же, что сейчас.
3. **Given** любое действие, **When** сравниваются ответ, сообщения и записи журнала с прежней версией, **Then** они те
   же (тесты тайны, прав, атомарности, остатков данных и e2e зелёные без правки ожиданий).
4. **Given** проверки одновременных вызовов («все читают, затем пишут»), **When** чтения объединены в пакеты, **Then**
   оба вызова по-прежнему успевают прочитать до первой записи (проверки гонок не становятся пустыми), а результаты — те
   же (19 «один результат», 2 известных дефекта шага 5 — с пометкой).

### User Story 3 — Предметная логика — в модулях, общие правила — в одном месте (Priority: P2)

Разработчик меняет правило исключений, закреплённых пар, параметров события или отметки «подарок получен». Сейчас эта
логика вместе с SQL лежит внутри обработчика API, а простые проверки «событие завершено», «переписка ещё открыта»
импортируются из модуля жизненного цикла события, который тянут семь модулей. Функции модулей принимают разный набор
параметров (окружение или базу, «я», «владелец ли я», список пользователей). После фичи в обработчике API остаются
разбор запроса, таблица и ответ; исключения и закреплённые пары — в модуле правил пар, участие админа и семьи — в модуле
участия, параметры события — в модуле событий, письмо, адрес, подопечный и отметки подарка — в модуле участника, сборка
панели события — отдельной функцией; простые проверки состояния события — в модуле без зависимостей; функции модулей
получают первым параметром один контекст вызова.

**Why this priority**: делает шаги 5 (захваты и снимки) и 7 (сводный контракт) возможными без повторного разбора
обработчика API; сам по себе людям не виден.

**Independent Test**: в обработчике API нет ни одного прямого SQL-запроса; все тесты зелёные; модуль простых проверок
не импортирует ничего.

**Acceptance Scenarios**:

1. **Given** код после фичи, **When** в обработчике API ищутся прямые запросы к базе, **Then** их нет.
2. **Given** модуль простых проверок состояния события, **When** проверяются его импорты, **Then** их нет; модули
   жеребьёвки, участия, обращений, переписки, бота и расписания берут проверки оттуда.
3. **Given** любое действие API, бота или расписания, **When** оно выполняется, **Then** функции модулей получают один
   контекст вызова (окружение, база, «я», настройки, пользователи и владелец — лениво, с одним чтением на вызов).

### User Story 4 — Попутные мелочи в затронутых файлах (Priority: P3)

В файлах, которые меняет фича, исправляются мелочи из плана рефакторинга: побайтно одинаковые тексты в нескольких местах
сводятся к одному; повторённая около 20 раз клавиатура «одна кнопка приложения» — к одному помощнику; рассылка «…
присоединяется к событию» в чате бота — к рассылке модуля участия; разбор режима ответа (`pending`) — к паре функций
«разобрать/собрать» (старый формат по-прежнему распознаётся); страница настройки `/setup` — в отдельный модуль без
изменений; недостижимая ветка «перенести администратора может только владелец» — удаляется; построители «обновить
пользователя / событие» с пустым набором полей — явная ошибка вместо некорректного SQL; имена для журнала исключений —
из уже прочитанного списка пользователей.

**Why this priority**: снижает число мест, где тексты и разметка могут разойтись; на людей не влияет.

**Independent Test**: тест слов, e2e, тест числа запросов и эталон отказов зелёные; тексты сообщений побайтно те же.

**Acceptance Scenarios**:

1. **Given** любой из объединённых текстов, **When** он отправляется, **Then** текст побайтно тот же, что сейчас.
2. **Given** старый режим ответа `msg_<сторона>:<событие>` в базе, **When** человек пишет боту, **Then** он получает
   «⌛ Время ответа истекло…», как сейчас.
3. **Given** страница `/setup`, **When** она открывается и отправляется форма, **Then** HTML и заголовки те же.

### Edge Cases

- `me` отвечает и незарегистрированному (`registered: false`); владельца вычисляет только для админа — как сейчас.
- Отметка «бот заблокирован» снимается при любом вызове API до любых отказов по правам — как сейчас.
- `admin.audit` без поля `event` — общий журнал; с полем `event` — журнал события (несуществующее событие — 404).
- Неизвестное действие админа: без события — 404 «Событие не найдено.»; с завершённым событием — 400 «Событие
  завершено…»; с идущим — 404 «Неизвестное действие». Неизвестное действие участника: несуществующее событие — 404
  «Событие не найдено.», не участник — 403 «Ты не участвуешь в этом событии.», участник — 404 «Неизвестное действие».
- `event.get` доступен участнику или админу (не участнику — 403); остальные действия участника — только участнику, даже
  админу.
- `admin.event.invite_from` разрешено в завершённом событии ради своего текста отказа: сначала «Выбери другое
  событие.», затем «Событие завершено — приглашать в него нельзя.».
- `delivery.save` в завершённом событии без адреса доставки отвечает «В этом событии адрес доставки не нужен.», с
  адресом — «Событие завершено: адрес теперь только для чтения.» (порядок проверок свой).
- Действия обращений и переписка в завершённом событии разрешены, пока открыта переписка (7 суток); проверка — внутри
  модулей, порядок отказов прежний (например, «Обращение не найдено.» раньше «только для чтения»).
- Условные права остаются в обработчиках: переименование админа и владельца, удаление админа, заморозка исключений для
  не-владельца, видимость переписки обращений.
- Владелец, указанный в настройках, недействителен: самый ранний админ назначается владельцем при первом же вызове
  админа, как сейчас (вычисление владельца для действий админа не откладывается).
- Отказы «событие завершено» в отменах жеребьёвки и объявлении через API недостижимы (их перекрывает общий отказ) —
  остаются как защита.
- Повторные чтения, которые нужны намеренно, остаются: событие внутри атомарных действий, проверки после неудачного
  захвата, повторное чтение события после записи исключений и закреплённых пар.
- Список пользователей — снимок на момент первого чтения в вызове; если вызов сам меняет пользователей (новый
  пользователь по ссылке владельца), следующая функция читает их заново.
- Порядок участников жеребьёвки (время вступления) и состав прочитанного не меняются — при том же зерне пары те же.

## Requirements *(mandatory)*

### Functional Requirements

**Инварианты (поведение не меняется)**

- **FR-1901**: Коды, тексты и поля ответов API, их порядок там, где его сверяют тесты, тексты и получатели сообщений,
  записи журнала — прежние для каждого из 59 действий и для неизвестных действий.
- **FR-1902**: Порядок проверок прежний: не POST — 405; подпись — 401; снятие отметки «бот заблокирован»; `me`;
  не зарегистрирован — 403; `notify.set`; действие админа и не админ — 403; действия админа без события; событие не
  найдено — 404; событие завершено и действие в нём не разрешено — 400; проверка владельца; обработчик; неизвестное
  действие — 404. Для действий участника: событие не найдено — 404; `event.get` — участник или админ; остальные — только
  участник (403).
- **FR-1903**: Условия захватов и состав пакетов записи атомарных действий не меняются — меняется только, откуда берутся
  прочитанные данные. Схема базы и миграции не меняются.
- **FR-1904**: Алгоритм жеребьёвки не меняется; порядок и состав участников, исключений, семей, прошлых и закреплённых
  пар, передаваемых в расчёт, — прежние; эталон жеребьёвки зелёный без пересоздания; замер жеребьёвки — без ухудшения
  (ни одна медиана не выросла больше разброса двух прогонов «до»).
- **FR-1905**: Число запросов к Telegram на действие — прежнее; к базе — не больше прежнего; ни один вызов не выходит
  за 50 внешних запросов.

**Таблица действий**

- **FR-1906**: Для каждого из 59 действий в одной таблице указаны: роль (любой с подписью / зарегистрированный /
  участник события / участник или админ / админ / владелец), текст отказа владельца (у действий только для владельца),
  нужно ли событие (да / нет / только если оно передано — общий и событийный журнал), разрешено ли действие в
  завершённом событии (нет — общий отказ; свой текст отказа; да — только чтение или своя проверка внутри) и обработчик.
- **FR-1907**: Проверки роли, наличия события, «событие завершено» и владельца выполняются в одном месте до обработчика
  по таблице, в порядке FR-1902. Неизвестное действие проходит те же проверки, что сейчас (FR-1902, «Edge Cases»).
- **FR-1908**: Тесты прав и автотест e2e «владелец может всё, что админ» берут список действий из таблицы (импорт
  модуля), а не из текста файла; в таблице 59 действий, из них 46 действий админа; порядок действий админа в таблице —
  прежний порядок ветвей (автотест e2e выполняет их по очереди на одном событии).
- **FR-1909**: Новый тест сверяет каждую строку таблицы: роль из списка ролей; у действий только для владельца — текст
  отказа; у действий события — явный признак «разрешено в завершённом».
- **FR-1910**: Новый эталон ответов снимается скриптом до изменения кода и лежит в `tests/fixtures/`: для каждого из 59
  действий и для неизвестных действий — код и текст ответа на запрос без прав (незарегистрированному, постороннему,
  участнику на действия админа, админу на действия владельца), на несуществующее событие и на завершённое событие
  (админом и владельцем; участником — на действия участника). Тест сверяет текущие ответы с эталоном.

**Контекст вызова и чтения**

- **FR-1911**: На каждый вызов API, бота и расписания создаётся один контекст: окружение, база, «я»; настройки,
  пользователи и владелец — с одним чтением на вызов, лениво (в вызове админа владелец вычисляется сразу, FR-1902).
  Функции модулей получают контекст первым параметром.
- **FR-1912**: Пользователь и настройки в начале вызова API и сообщения боту читаются одним пакетом.
- **FR-1913**: Независимые чтения объединяются в один пакет: проверка жеребьёвки; панель события вместе со списком
  обращений; чтения перед перестройкой пар при удалении и вписывании участника; экран «мои события»; экран события
  участника; чтения обращений (пользователи вместе с обращением, обращение вместе с перепиской).
- **FR-1914**: Узкие чтения: число участников для экрана события — подсчётом в базе; для жеребьёвки — человек, имя,
  время изменения письма и адреса и признак «письмо пустое», посчитанный в базе; для панели события — признаки «письмо
  есть», «адрес указан» вместо текстов; для рассылок завершения, объявления, приглашения, удаления события и сброса —
  только получатели.
- **FR-1915**: Пустота текста в базе совпадает с пустотой после обрезки пробелов в коде на всех символах U+0001–U+FFFF
  (кроме суррогатов); тест паритета обязателен.
- **FR-1916**: Подмена базы в быстрых тестах считает пакет только из чтений чтением, а не записью: проверки
  одновременных вызовов «все читают, затем пишут» по-прежнему ставят барьер перед первой записью.

**Модули и слои**

### Key Entities

- **Таблица действий** — для каждого действия API: роль, текст отказа владельца, нужно ли событие, разрешено ли в
  завершённом событии, обработчик. Порядок строк — порядок проверки в автотесте.
- **Контекст вызова** — один объект на вызов API, сообщения боту или запуск расписания: окружение, база, «я»; настройки,

- **Пакет чтений** — несколько независимых запросов на чтение, выполняемых одним обращением к базе; результаты — по

- **Эталон отказов** — снятые до изменений коды и тексты ответов каждого действия в ситуациях «без прав»,

## Assumptions

- Шаг выполняется одной фичей (019), а не двумя: файл шага допускает деление, но объём помещается в одну ветку;
  коммиты разделены по границе «часть А — таблица и модули» / «часть Б — контекст и чтения» / «мелочи».
- Эталон отказов снимается скриптом на коде до изменений (первой задачей реализации) и не пересоздаётся; «без прав»
  проверяется теми ролями, которые сейчас получают отказ: незарегистрированный, посторонний, участник (действия админа),
  админ (действия владельца). Тела запросов минимальные — как в тесте прав (без слов подтверждения и людей), поэтому
  опасные действия отказывают по данным, а не меняют их.
- Пакет чтений D1 считается одним запросом в лимите 50 и принимает `SELECT` (документация Cloudflare D1); в подмене базы
  для быстрых тестов пакет без записей не ставит барьер «перед записью» — это и есть поведение настоящей базы (чтение
  ничего не блокирует), а иначе проверки гонок стали бы пустыми.
- Пользователь и настройки в начале вызова читаются одним пакетом — это даёт по одному запросу экономии на каждом
  вызове API и сообщении боту и нужно, чтобы действия обращений стали на 2 запроса легче.
- Владелец в вызове админа вычисляется сразу (как сейчас), экономия — на повторных чтениях списка пользователей.
- `delivery.save` в таблице помечено «разрешено в завершённом — своя проверка»: проверка «адрес не нужен» стоит раньше
  «событие завершено», и перенос её в общее место изменил бы ответ. Остальные действия участника, у которых проверка
  «событие завершено» стоит первой (письмо, «подарок готов», «подарок получен»), получают свой текст отказа из таблицы.
- Действия обращений и отправка в переписку помечены «разрешено в завершённом — проверка переписки внутри»: их порядок
  отказов («обращение не найдено» раньше «только для чтения») сохраняется.
- Список пользователей, прочитанный в вызове, используется до конца вызова; единственное место, где вызов сам добавляет
  пользователя и затем читает список (ссылка владельца в чате бота), перечитывает его.
- Семьи как исключения и снимки переезжают в модуль правил пар без изменения выражений (снимки переделывает шаг 5).
- Общие тексты хранятся в модуле общих помощников текста (`src/format.js`, без импортов); текст, зависящий от лимита
  переписки, — рядом с лимитом.
- Попутные мелочи берутся только из файлов, которые фича меняет; «Событие завершено больше недели назад…» — четыре
  разных текста, они не объединяются.
- Решения владельца (захваты рассылок, CSP, слово «ОТКРЫТЬ» в API, журнал `admin.rename`, индекс непрочитанных) в шаг не
  входят.
- README не меняется: установка, настройка, секреты, команды, роли и использование те же. Задача на README в
  `tasks.md` — проверка этого.
