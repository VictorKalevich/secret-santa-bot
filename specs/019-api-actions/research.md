# Research: Таблица действий API и контекст запроса

Номера строк — по `main` на `c8d1cf9` (после 018), поиск — по именам функций.

## R1. Форма таблицы действий

**Decision**: `export const ACTIONS` в `src/api.js` — объект «имя → строка» в порядке прежних `case` (сначала 13 действий
участника, затем 11 общих действий админа, затем 35 действий события; `admin.audit` — на месте первого вхождения, среди
общих). Поля строки:

- `role` — `ANY` (любой с подписью: `me`), `USER` (зарегистрированный: `notify.set`), `VIEWER` (участник или админ:
  `event.get`), `MEMBER` (участник события), `ADMIN`, `OWNER`;
- `owner` — текст отказа владельца (есть ровно у `OWNER`): шаблон `onlyOwner('Назначать и снимать администраторов')`
  → «… может только владелец бота.»; у служебного просмотра — «Служебный просмотр доступен только владельцу бота.»;
- `event` — `true` (нужно событие), не задано (не нужно), `'given'` (только если поле `event` передано: `admin.audit`);
- `finished` (обязателен у действий события) — `true` (разрешено: чтение, свой текст отказа внутри, проверка переписки
  внутри) или строка — текст отказа 400 в завершённом событии: общий `CLOSED` («Событие завершено — менять его уже
  нельзя…») у админа, свой у `wishlist.save`, `ward.gift`, `ward.received`;
- `confirm` — `[слово, текст отказа]` (`ОТМЕНА`, `УДАЛИТЬ`, `СБРОС`) — проверка одной функцией `confirmed(body, word)`;
- `run(ctx, body, ev, member)` — обработчик: данные ответа (объект без `ok`) или `refuse(текст, код)`.

Неизвестное действие — строки-заглушки `UNKNOWN_ADMIN` (`ADMIN`, событие, `finished: CLOSED`) и `UNKNOWN` (`MEMBER`,
событие, `finished: true`), обработчик — 404 «Неизвестное действие».

**Rationale**: файл шага требует «одну строку таблицы» с ролью, событием и «разрешено в завершённом»; у трёх действий
только для владельца первая строка обработчика после проверки владельца — слово подтверждения, это тоже условие действия.
Строка-заглушка даёт неизвестным действиям ровно прежний путь (FR-1907) без отдельных веток. Обработчики возвращают
данные, а не `Response`: один `respond()` собирает `{ ok: true, ...данные }` (порядок полей прежний: у всех ответов
`ok` — первым) или `{ ok: false, error }`.

**Alternatives considered**: отдельный файл `src/actions.js` с таблицей — файл шага оставляет таблицу в `src/api.js`;
`finished` как набор значений (`'no'|'yes'|'own'|'chat'`) — строка-текст короче и убирает список `FINISHED_OK` целиком,
а «своя проверка внутри» и «7 суток» — пояснения в комментарии строки; `delivery.save` со своим текстом в таблице —
меняет ответ (R2).

## R2. Конвейер проверок и его порядок

**Decision**: `handleApi`: не POST → 405; подпись → 401; тело; контекст (пользователь + настройки одним пакетом, R4);
снятие отметки «бот заблокирован»; строка (`ACTIONS[action]` или заглушка); роль не `ANY` и не зарегистрирован → 403
«Сначала зарегистрируйся…»; `admin.*` и не админ → 403 «Только для администратора.»; `admin.*` → владелец вычисляется
сразу (`ctx.ownerId()`); действие без события → владелец (`owner`) → обработчик; иначе событие (`getEvent(body.event)`) →
404; для не-`admin.*` — участие (`getMember`) → 403 «Ты не участвуешь в этом событии.», кроме `VIEWER` у админа;
`isFinished(ev)` и `finished !== true` → 400 с текстом строки; владелец → 403 текстом строки; слово подтверждения → 400;
обработчик.

Сохраняемые тонкости (файл шага, «Порядок проверок» и «Подводные камни»):

- владелец проверяется **после** «событие завершено»: админ на завершённом событии получает 400, а не 403;
- `admin.audit` с `event` — действие события (несуществующее — 404), без — общее;
- `admin.event.invite_from` — `finished: true`: «Выбери другое событие.» раньше «Событие завершено — приглашать в него
  нельзя.» (обработчик);
- `delivery.save` — `finished: true`, проверка в обработчике: «В этом событии адрес доставки не нужен.» стоит раньше
  «Событие завершено: адрес…»; перенос в конвейер поменял бы ответ на завершённом событии без адреса;
- обращения (`support.*`, `admin.support.*`) и `message.send` — `finished: true`: проверка «переписка открыта» внутри
  модулей, после «обращение не найдено» и других;
- `chat.get`, `ward.get`, `support.get` в завершённом событии работают (только чтение);
- условные права остаются в обработчиках: `admin.rename` (админа и владельца — только владелец), `admin.remove`
  (админа — только владелец), заморозка исключений для не-владельца, видимость переписки обращений, передача и
  закрытие обращения (ответственный или владелец);
- отказы «событие завершено» внутри `cancelDraw`, `forceCancelDraw`, `announce` недостижимы через API и остаются.

**Rationale**: каждая строка — существующий отказ с тем же кодом и текстом; эталон отказов (R3) сверяет это побайтно.

**Alternatives considered**: проверка участия в конвейере для всех ролей — для `admin.*` её сейчас нет (админ работает с
событиями, где не участвует).

## R3. Эталон отказов

**Decision**: `tests/support/refusals-scenario.mjs` — общий сценарий: мир с владельцем, админом, участником,
посторонним (зарегистрирован, но не в событии) и незнакомцем (без записи); идущее событие E (участник в нём), завершённые
события F (без адреса доставки) и FD (с адресом), несуществующее 999999. Для каждого из 59 действий (список в порядке
прежних `case`, записан в сценарии явно) и для `admin.nope` / `nope` записываются `{ status, error }` (`error` — `null`
при успехе) в ситуациях:

- `stranger` — незнакомец (идущее событие);
- `outsider` — посторонний (идущее событие);
- `member` — участник: действия админа (на идущем событии);
- `admin` — админ, не владелец, на **свежем** событии для каждого действия (как `tests/rights.test.mjs`: выполненное
  действие не портит следующие);
- `missing` — несуществующее событие: действия админа — владельцем, действия участника — участником;
- `finished` — завершённое F: владельцем и админом (действия админа), участником F (действия участника);
- `finishedDelivery` — завершённое FD участником (действия участника).

Тела минимальные: `{ event, id: 0, from: 0, to: 0, giver: 0, receiver: 0 }` (без слов подтверждения, людей и текстов).
`tests/fixtures/make-api-refusals.mjs` пишет `tests/fixtures/api-refusals.json` (действия, порядок, ответы); снимается
**до** изменения кода и не пересоздаётся. `tests/api-refusals.test.mjs` прогоняет тот же сценарий и сравнивает с эталоном
целиком (`deepEqual`), а набор действий эталона — с ключами `ACTIONS`.

**Rationale**: файл шага: «для каждого действия ответ на запрос без прав, на несуществующее событие и на завершённое
событие — тот же код и тот же текст, что до шага». Свежее событие у админа и минимальные тела — приём теста прав: ни
одно действие не меняет данные, от которых зависят следующие ответы. Мир детерминирован (номера событий —
`AUTOINCREMENT`, одинаковый порядок вызовов), поэтому эталон воспроизводим.

**Alternatives considered**: сравнивать и успешные ответы целиком — в них время и коды (`invite_link`, `created_at`),
это проверяют тесты тайны и e2e.

## R4. Контекст вызова

**Decision**: `src/context.js`:

- `makeContext(env, { me, settings })` → `{ env, db, me, settings(), users(), ownerId(), isOwner(), read(named),
  forgetUsers() }`. `settings()`, `users()`, `ownerId()` — кэш обещания на вызов; при ошибке кэш сбрасывается (шаги cron
  изолированы: упавшее чтение одного шага не отравляет следующий). `ownerId()` = `resolveOwner(db, settings, users)` —
  тот же код с возможной записью нового владельца.
- `openContext(env, userId)` — пользователь и настройки одним пакетом (API и сообщение боту). Нажатие кнопки в боте —
  `makeContext(env, { me })` после чтения пользователя (настройки — лениво, как сейчас: не всем нажатиям они нужны).
- Cron — `makeContext(env)`.
- В вызове `admin.*` владелец вычисляется сразу после проверки «админ» (как `handleAdmin` сейчас): ленивое вычисление
  отложило бы запись нового владельца (файл шага, «Подводные камни»).
- Список пользователей — снимок на момент первого чтения. Единственное место, где вызов сам добавляет пользователя и
  потом читает список, — ссылка владельца в чате (`createUser` → `setOwner`): там `ctx.forgetUsers()` перед `setOwner`.
- `ctx.me` в боте обновляется, когда бот перечитывает пользователя (после ввода имени, после ссылки владельца).

Функции модулей получают `ctx` первым параметром вместо `env`/`db` + `me` + `isOwner` + `users` (контракт —
`contracts/api-actions.md`). Низкоуровневые чтения и построители операторов (`db.js`, `drawCancelable`, `chatPair`,
`returnThreadsStmts`, `rejoinBlocked`) по-прежнему принимают `db`.

**Rationale**: «Один объект на вызов: env, db, settings, me, лениво — users и ownerId» (файл шага). Обещания вместо
значений — потому что в нажатиях кнопок настройки сейчас читаются не всегда, а пользователи — почти никогда.

**Alternatives considered**: читать пользователей всегда в начальном пакете — лишние данные для каждого вызова участника;
передавать `isOwner`/`ownerId` параметрами — именно эту разнобойность сигнатур и убирает шаг.

## R5. Пакет чтений и барьер подмены D1

**Decision**: `readMany(db, { имя: оператор | null })` в `src/db.js` — один `db.batch` из заданных операторов, результат
по именам (`results` каждого; пропущенные — `[]`); пустой набор — без запроса. `ctx.read(named)` — то же, плюс
`users: true` / `settings: true`: из кэша или в этом же пакете (и тогда кладётся в кэш). В подмене D1
(`tests/support/d1-sqlite.mjs`) `batch` ставит барьер `together()`, только если в пакете есть запись
(`INSERT|UPDATE|DELETE`).

**Rationale**: `db.batch` считается одним запросом и принимает `SELECT` (документация D1, `baseline.md`, «Что проверено»);
результаты — по порядку операторов, имена исключают путаницу позиций (файл шага, «Подводные камни»). Без правки подмены
пакет чтений вставал бы на барьер «перед записью»: второй вызов читал бы уже после записи первого, и проверки гонок
перестали бы проверять гонку. Настоящая D1 чтением ничего не блокирует — правка приближает подмену к ней. Свойство
закрепляется в `tests/d1-sqlite.test.mjs`.

**Alternatives considered**: `Promise.all` отдельных `first()` — столько же запросов, сколько сейчас.

## R6. Узкие чтения и признак «пусто» в базе

**Decision**: `BLANK_SQL(колонка)` = `trim(колонка, char(9,10,11,12,13,32,160,5760,8192,…,8202,8232,8233,8239,8287,
12288,65279)) = ''` — набор символов, которые срезает `String.prototype.trim()`. Узкие чтения (`src/db.js`):

- `drawMembersQuery` — участники для жеребьёвки и перестройки пар: `user_id, name, username, registered,
  wishlist_updated_at, delivery_updated_at, wishlist_blank`; та же выборка `FROM members m JOIN users u … WHERE
  m.event_id = ? ORDER BY m.joined_at`, фильтр «зарегистрирован» — в коде, как сейчас;
- `panelMembersQuery` — для `admin.state`: человек, имя, ник, `registered`, `is_admin`, `blocked_at`, `has_wishlist`,
  `has_delivery`; пары панели — `santa, ward, gift_ready, gift_received, seen_text IS NOT NULL AS seen`;
- `participantCountQuery` — `COUNT(*)` зарегистрированных для `event.get`;
- `memberIdsQuery` / `participantIdsQuery` (зарегистрированные) — получатели рассылок завершения, объявления,
  приглашения, удаления и сброса; `unfilledIdsQuery` — получатели напоминания о пустом письме (`BLANK_SQL`);
- `pairLinksQuery` — `santa, ward` для раскрытия и служебного просмотра пар.

Проверено (скрипт в черновике сессии): `EXPLAIN QUERY PLAN` старой и новой выборки участников одинаков
(`SEARCH m USING INDEX sqlite_autoindex_members_1 (event_id=?) | SEARCH u … | USE TEMP B-TREE FOR ORDER BY`), порядок
при равном `joined_at` тот же; `trim(char(n), набор) = ''` и `!String.fromCharCode(n).trim()` совпадают на всех n от 1 до
65535, кроме суррогатов (25 символов «пустые» в обоих).

**Rationale**: файл шага, «Узкие чтения»; разбор писем по 4000 символов — до 1,9 мс CPU на 200 человек
(`baseline.md`, раздел 6). Порядок и состав участников, переданных в `planDraw`, не меняются → пары при том же зерне те
же.

**Alternatives considered**: `length(trim(x)) = 0` без набора — SQLite по умолчанию срезает только пробел (U+0020).

## R9. Попутные мелочи

**Decision** (только побайтно одинаковое, только в затронутых файлах):

- общие тексты в `src/format.js`: `NOT_REGISTERED` («Сначала зарегистрируйся по пригласительной ссылке.» —
  `api`, `bot`), `ADMIN_ONLY` («Только для администратора.» — `api`, `bot` ×2), `NO_DRAW` («Жеребьёвка ещё не
  проведена.» — `api`, `events`, `pairs`), `PAIRS_RACE` («Пары изменились одновременно с этим действием — попробуй ещё
  раз.» — `pairs`, `events`);
- `tooLong(n)` в `src/chat.js` рядом с `MAX_CHARS` («Слишком длинно: … (лимит сообщения Telegram).» — письмо, переписка,
  обращения);
- `requestRejected(ev)` в `src/membership.js` («Организатор не одобрил заявку…» — `bot`, `membership`);
- в `src/bot.js`: `registrationClosed(ev)` (два места), `REPLY_EXPIRED` (два места), `parsePending` / `replyPending` /
  `supportPending` — разбор и сборка `pending` (`name:<событие>:<код>`, `msg_<сторона>:<событие>[:<собеседник>:<мс>]`,
  `sup_u:…`, `sup_a:…`; старый формат без собеседника распознаётся и даёт «время ответа истекло»);
- `appKeyboard(settings, text, params)` в `src/format.js` → `{ reply_markup: { inline_keyboard: [[openAppButton(…)]] } }`
  (порядок ключей сообщения прежний: `msg(text, { disable_notification, ...appKeyboard(…) })`);
- `joinedNoticeStmts(db, users, user, ev)` в `src/membership.js` — рассылка «… присоединяется к событию» для
  `joinByInvite` и ввода имени в боте (у бота имя уже сохранено, `displayName(user)` = введённое имя);
- `/setup` — `src/setup.js` (`setup`, `renderSteps`, `SETUP_HEADERS`, `SETUP_FORM`) без правок текста;
- недостижимая ветка `src/api.js:357` удаляется;
- `updateUserStmt` / `updateEventStmt` с пустым набором полей бросают ошибку с понятным текстом (сейчас так не
  вызываются);
- имена для журнала исключений — из `ctx.users()`.

Не объединяются: четыре разных «Событие завершено больше недели назад…» (`chat`, `support`, `bot` ×2).

**Rationale**: раздел «Мелочи» плана рефакторинга.

## R11. Автотест e2e «владелец ⊇ админ»

**Decision**: список — `Object.keys(ACTIONS).filter((a) => a.startsWith('admin.'))` (импорт `../src/api.js`), порядок
— прежний порядок `case` (R1); сценарий e2e не меняется. `tests/rights.test.mjs` — тот же импорт; утверждение «ровно 46,
включая действия с «_»» остаётся, добавляется «всего 59».

**Rationale**: автотест e2e выполняет действия по очереди на одном событии: `admin.registration` закрывает набор,
`admin.event.finish` завершает событие, после чего действия вне «разрешено в завершённом» получают 400 раньше проверки
владельца — при том же порядке результат тот же (файл шага, «Что заденет в тестах»).
