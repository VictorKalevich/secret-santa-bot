# 054. Минутная проверка читает только идущие события

**Feature Branch**: `054-cron-active-reads`

**Created**: 2026-11-24

**Status**: Draft

**Input**: User description: "Сделать так, чтобы минутная проверка читала только пары идущих событий. Поведение бота не
изменится, а потолок вырастет и перестанет зависеть от истории."

## Контекст

Бесплатный тариф D1 — 5 млн прочитанных строк в сутки на аккаунт; при превышении база до 00:00 UTC не отвечает. Раз в
минуту бот (cron) проверяет, не обновил ли подопечный письмо или адрес, чтобы написать Санте. Сейчас этот запрос
просматривает **всю** таблицу пар — и завершённых событий тоже: ~2 900 строк в сутки на каждую пару, когда-либо
созданную ботом. С 10:00 до полуночи cron ещё и каждую минуту просматривает все события и все компании. Расход растёт с
историей: каждый сезон уменьшает запас, даже если в боте никто не играет.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — История не съедает лимит (Priority: P1)

Владелец бота держит бот годами: завершённые события копятся. Минутная проверка читает только идущие события и их пары,
поэтому расход чтений в минуты без действий зависит только от того, что сейчас идёт, а не от прошлых сезонов.

**Why this priority**: это и есть фича — запас бесплатного тарифа не уменьшается с каждым сезоном.

**Independent Test**: мир с завершёнными событиями (с парами), идущим событием до жеребьёвки и идущим после — каждый
запрос минутной проверки ищет по индексам; ни один не просматривает целиком пары, участников, людей, события или компании.

**Acceptance Scenarios**:

1. **Given** в базе завершённые события с парами и идущие события, **When** выполняется минутная проверка, **Then** ни
   один её запрос не просматривает целиком таблицы пар, участников, людей, событий и компаний: события — только идущие
   (по индексу), пары и участники — только этих событий.
2. **Given** идущих событий нет (только история), **When** выполняется минутная проверка, **Then** пары, участники и
   компании не читаются вовсе.
3. **Given** идущее событие до жеребьёвки, **When** выполняется минутная проверка, **Then** участники события не
   перебираются (пар ещё нет — проверять нечего).

---

### User Story 2 — Поведение прежнее (Priority: P1)

Санта получает «📝 Твой подопечный … обновил письмо» так же, как раньше: через `NOTIFY_DELAY_MINUTES` после последней
правки, один раз на правку, с учётом режима уведомлений; автодействия расписания и напоминания идут в те же минуты.

**Why this priority**: правка — только про чтения; любое изменение того, кто и когда получает сообщения, — ошибка.

**Independent Test**: прежние тесты уведомлений, расписания и напоминаний (`npm test`, e2e) — без изменений и зелёные;
число запросов минутной проверки в обычную минуту — прежнее (3).

**Acceptance Scenarios**:

1. **Given** подопечный в идущем событии обновил письмо, **When** прошла задержка и сработала минутная проверка,
   **Then** его Санта получает то же сообщение, что и до 054, один раз.
2. **Given** в минуту наступило автодействие (жеребьёвка, раскрытие, завершение) или напоминание, **When** срабатывает
   минутная проверка, **Then** действие выполняется так же, в контексте компании события.

### Edge Cases

- Индекс ещё не создан (код выкачен раньше миграции): бот работает как прежде, просто читает все события вместо идущих —
  код от индекса не зависит, порядок «миграция ↔ выкат» и откат безопасны.
- Событие завершилось — его пары в минутную проверку больше не попадают (как и раньше по смыслу: уведомления — только в
  идущих событиях).
- Компании в минуты без действий не читаются; в минуту с действием — читаются один раз, как требует контекст компании.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Запрос уведомлений об изменении письма начинает с идущих событий и берёт пары и участников только этих
  событий; пары завершённых событий не читаются.
- **FR-002**: Идущие события находятся по индексу только идущих событий (новая миграция только с индексом, без изменения
  строк и версии схемы — как `0008`).
- **FR-003**: Ежедневный шаг (автодействия и напоминания) читает идущие события по тому же индексу и не читает список
  компаний, пока не выполняет действие.
- **FR-004**: Кто, когда и какие сообщения получает, какие действия выполняются и в каком порядке — без изменений; число
  запросов минутной проверки в обычную минуту — прежнее.
- **FR-005**: Тест проверяет планы всех запросов минутной проверки на базе с историей: полный просмотр допустим только у
  служебных таблиц (настройки, очередь сообщений) и у индекса идущих событий; «от противного» — прежние запросы и база
  без индекса находятся.
- **FR-006**: README и `CLAUDE.md` описывают новую миграцию (только индекс, порядок с выкатом не важен) и применение в обе
  базы.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Чтения минутной проверки в минуту без действий: было ≈ 2 × (все пары) + все события + все компании, стало
  ≈ 2 × (пары идущих событий) + 2 × (идущие события); при 0 идущих событий — только служебные таблицы.
- **SC-002**: Для бота с 1 000 пар в завершённых событиях и без идущих — экономия ≈ 2,9 млн строк в сутки (больше половины
  бесплатного лимита).
- **SC-003**: Все прежние тесты (`npm run test:all`) зелёные без изменения ожиданий по сообщениям и действиям.

## Assumptions

- Пары и участники идущих событий по-прежнему перебираются каждую минуту (≈ 2 900 строк в сутки на пару идущего
  события); сделать проверку пропорциональной числу правок — отдельная задача (нужна отметка «ждёт уведомления»).
- Запросы, которые читают таблицы людей и компаний целиком на каждый вызов API и бота (контекст компании, список людей
  компании), — вне этой фичи: это отдельная задача о нагрузке открытого бота.
- Планы запросов D1 совпадают с планами SQLite в тестах (тот же движок); после выката план проверяется на базе бота
  (`quickstart.md`).
