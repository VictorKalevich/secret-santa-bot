# Research: Один список данных события и человека

Основа — `docs/refactoring/step-3-data-registry.md`; номера строк сверены с `main` на `b3cf6d4` (после 017): шаги 1–2
`src/events.js`, `src/pairs.js`, `src/roles.js`, `src/api.js` (кроме `draw.js`) не трогали, номера из файла шага верны.

## R1. Где живёт список и какой он формы

- **Decision**: объект `REGISTRY` в `src/db.js` — по ключу на каждую из 17 таблиц схемы. Описание таблицы: колонка
  события (`event`) или родитель (`via`), колонки человека с ролью (`people`), якорь (`anchor`), что с таблицей делают
  удаление события (`onEventDelete`), уход участника (`onLeave`) и перенос (`onTransfer`), плюс поправки переноса
  (`transferBefore`/`transferAfter`) там, где у таблицы есть своё правило. Порядок ключей — порядок операторов:
  дочерние таблицы (`support_messages`) раньше родительских. Роли:
  - `MEMBER` — участник: данные человека как участника (переходят при переносе, уходят с ним по `onLeave`);
  - `ACTOR` — кто сделал: ссылка на действовавшего; перенос её не трогает (решение владельца, план рефакторинга);
  - `ACTOR_MOVED` — кто сделал, но перенос переносит: ответственный за обращение и отправитель сообщения обращения
    (так с 012 — это текущее состояние обращения, а не история);
  - `RECIPIENT` — получатель сообщения очереди: перенос не трогает, сообщение уходит старому аккаунту;
  - `NOT_PERSON` — имя похоже на человека, но это не человек (`messages.sender` — роль `santa`/`ward`);
  - `users.tg_id` — сама запись человека (`anchor: 'person'`).
- **Rationale**: файл шага требует список в `src/db.js`; объект с именами таблиц читается как таблица из файла шага и
  даёт тесту схемы прямое сравнение «таблица → колонки». Порядок ключей объекта со строковыми ключами в JS
  гарантирован (порядок вставки).
- **Alternatives considered**: читать схему во время работы (`PRAGMA table_info`) — лишние запросы, и схема не знает
  ролей; отдельный модуль `src/data.js` — шаг 4 будет делить `db.js`, сейчас лишний перенос; внешние ключи с
  `ON DELETE CASCADE` — запрещены (схема не меняется), и перенос ими не выражается.

## R2. Построители и параметры действий

- **Decision**: три построителя в `src/db.js`, каждый возвращает массив операторов и принимает условие `guard` с
  параметрами последними аргументами, как `enqueueIfStmt`:
  - `eventDataDeleteStmts(db, eventId, { keepMember, keepEvent }, guard, ...args)` — удаление события
    (`keepMember = 0`, `keepEvent = false`) и сброс (`keepMember = владелец`, `keepEvent = true`): у оставшегося
    участника стираются поля из `REGISTRY.members.cleared` (письмо и адрес со временем изменения);
  - `memberDataDeleteStmts(db, eventId, userId, guard, ...args)` — удаление участника и выход админа: таблицы события
    с колонкой `MEMBER` и `onLeave: 'delete'`, их дочерние через `via`, строка участника — последней;
  - `personTransferStmts(db, fromId, toId, { merge }, guard, ...args)` — перенос: колонки `MEMBER` и `ACTOR_MOVED`
    по политике таблицы, запись старого аккаунта — последней.
  Якорь (строка события, участника, человека) всегда последний оператор построителя: по нему действие узнаёт исход, а
  условия «событие ещё есть», «участник ещё в событии», «старая запись ещё есть» верны для всех операторов до него.
- **Rationale**: «отличия действий — параметры построителя, а не отдельные списки таблиц» (файл шага); удаление
  события и сброс различаются только тем, что остаётся; удаление участника и выход админа — только условием.
- **Alternatives considered**: один построитель с режимом — смешал бы три разных обхода списка; построители,
  возвращающие уже выполненный `batch`, — вызывающему нужно ставить свои операторы (рассылка, журнал, перестройка пар)
  в тот же `batch`.

## R3. Условие в операторах

- **Decision**: каждый оператор построителя получает `AND (${guard})` — условие в скобках; параметры условия
  добавляются в конец `bind`. Где у оператора своё `OR` (`giver = ? OR receiver = ?`), оно тоже в скобках.
  По умолчанию `guard = '1'` (сброс: захвата нет — решение владельца).
- **Rationale**: без скобок `a OR b AND guard` выполнялся бы при `a` вопреки условию — ровно та ошибка склейки, о
  которой говорит обзор (`src/support.js:44–46`, шаг 5).
- **Alternatives considered**: условие только у якоря — операторы до него выполнились бы и у проигравшего вызова.

## R4. Дефект 1: выход админа из участия одновременно с жеребьёвкой

- **Decision**: `admin.participate` (выкл) — `batch` из записи журнала «не участвует» и `memberDataDeleteStmts` с
  условием `EXISTS (SELECT 1 FROM events WHERE id = ? AND draw_done = 0)` у всех операторов. Исход — по записи
  журнала (первый оператор, то же условие): не записалась — отказ «После жеребьёвки так нельзя. Попроси владельца бота
  вписать тебя.» Проверка `ev.draw_done` до записи остаётся (быстрый отказ без записи, как сейчас).
- **Rationale**: по удалению строки участника исход не узнать: админ, который не участвует, тоже получает 0 удалённых
  строк, а ответ ему сейчас успешный, и журнал пишется (edge case спецификации). Запись журнала стоит под тем же
  условием, что и удаление, поэтому её «записалась / нет» — ровно «условие выполнилось / нет».
- **Alternatives considered**: перечитать событие после неудачи — лишний запрос и всё равно гонка; условие
  «участник ещё в событии» — меняло бы ответ не-участнику.

## R5. Дефект 2: двойной перенос участия

- **Decision**: все операторы `transferAccount` — с условием `EXISTS (SELECT 1 FROM users WHERE tg_id = ?)` (старый
  аккаунт); порядок: уведомления новому и старому аккаунту, остальным админам, запись журнала, затем
  `personTransferStmts` (удаление старой записи — последним). Исход — последний оператор: 0 строк — «Старая запись не
  найдена.». Слияние двух участий в одном событии считается по прочитанным строкам (`mergeMembership(from, to)` в
  `src/db.js`: письмо и адрес — нового, если не пусты по `trim()` JS, каждый со своим временем изменения; строка —
  старого, то есть его время вступления). Оставшиеся участия старого переносятся одним оператором
  `UPDATE members SET user_id = новый WHERE user_id = старый`; права админа — `MAX` текущих значений в базе.
- **Rationale**: тот же приём, что в `deleteEvent` (010): всё — пока «опора» существует, опора удаляется последней;
  второй вызов видит старую запись удалённой и ничего не делает. Уведомления встают перед переносом, а не после
  удаления записи — иначе их условие было бы ложным; порядок сообщений в очереди тот же.
  Пустота письма по-прежнему считается в JS: `trim()` SQLite по умолчанию снимает только пробелы.
- **Alternatives considered**: захват отдельным оператором (метка в `users.pending`) — лишняя запись и новый
  признак «свой захват» (это шаг 5); слияние в SQL — `trim()` SQLite отличается от JS без набора символов
  (`baseline.md`, раздел 6), это шаг 4.

## R6. Дефект 3: двойное удаление участника до жеребьёвки

- **Decision**: в `removeMember` все операторы, кроме захвата версии пар и перестройки пар, получают условие
  `${v.guard} AND EXISTS (SELECT 1 FROM members WHERE event_id = ? AND user_id = ?)`; уведомление удалённому, журнал и
  отметка «удалён организатором» стоят перед `memberDataDeleteStmts`. Исход — последний оператор (строка участника)
  вместо поиска по номеру `removeAt`; отказ при 0 строк — как сейчас (`PAIRS_RACE` или «Человек не участвует…» по
  повторному чтению).
- **Rationale**: до жеребьёвки условие версии пар («жеребьёвка не проведена») верно для обоих вызовов; «участник ещё в
  событии» — нет. Отметка «удалён» под тем же условием: иначе второй вызов переписал бы ей время и автора, хотя
  получил отказ. После жеребьёвки дополнительное условие ничего не меняет — захват версии пар и так один.
- **Alternatives considered**: условие только у уведомления и журнала (минимум файла шага) — отметка менялась бы у
  проигравшего; захват «строки участника» первым оператором — изменил бы порядок, по которому определяется исход.

## R7. Тест схемы

- **Decision**: `tests/data-registry.test.mjs` применяет миграции (`createMigratedD1`), читает список таблиц
  (`sqlite_master`, без `sqlite_*`) и `PRAGMA table_info` и сверяет с `REGISTRY` в обе стороны:
  1. каждая таблица схемы есть в списке и наоборот;
  2. каждая «подозрительная» колонка описана: имя `event_id`, `user_id`, `tg_id`, `chat_id`, любое `…_id` и `…_by`,
     любое имя колонки человека, встречающееся в списке (`giver`, `santa`, `actor`, `author`, `assignee`, `sender`…);
     «описана» — это колонка события, `via`, колонка человека любой роли или `NOT_PERSON`;
  3. каждая описанная колонка есть в схеме.
  Сверка — функция `registryGaps(sqlite, registry)`, которая возвращает список расхождений; «от противного» — три
  проверки на изменённой базе или копии списка: `ALTER TABLE settings ADD COLUMN event_id`, новая таблица с
  `user_id`, лишняя колонка в копии списка.
- **Rationale**: колонку с человеком под новым именем (`helper_id`, `approved_by`) ловят правила `…_id`/`…_by`;
  колонку с прежним именем в новой таблице — требование «все таблицы в списке».
- **Alternatives considered**: только четыре имени из файла шага — пропустили бы `giver` в новой таблице;
  сравнение по типу `INTEGER` — пропустило бы человека в колонке `TEXT`.

## R8. Тест «после действия не остаётся строк»

- **Decision**: в том же файле — «богатый мир» (через `tests/support/world.mjs`): владелец участвует, админ, 6
  участников, второе событие с одобрением заявок, письма и адреса, исключение, закреплённая пара, семья, обращение с
  ответом и закрытием, объявление, удалённый организатором, жеребьёвка, открытый подопечный, переписка пары. Поиск
  оставшихся строк идёт по списку: значения события — по колонкам события (и сироты `via`), значения человека — по
  всем колонкам человека и `users.tg_id`. Разрешённые остатки записаны в тесте явно, по таблице файла шага:
  - удаление события — только `audit`; сирот `support_messages` нет;
  - сброс — строка события (параметры по умолчанию, новая ссылка), участие владельца с пустыми письмом и адресом,
    `audit`;
  - удаление участника (до и после жеребьёвки) — в этом событии только `removed_members`, `join_requests` и роли
    `ACTOR`/`RECIPIENT`; участие в другом событии цело; в парах человека нет, пары остальных целы;
  - перенос — старый аккаунт только в колонках `ACTOR` и `RECIPIENT`.
- **Rationale**: тест проверяет поведение, а не построители: ожидания взяты из таблицы «что делает сейчас», а не из
  политик списка; полноту места поиска гарантирует тест схемы.
- **Alternatives considered**: сравнение снимков базы до и после — хрупко к меткам времени и порядку строк.

## R9. Что видно снаружи от перестановки операторов

- **Decision**: порядок сообщений в очереди не меняется ни в одном действии (уведомления в `transferAccount` и
  `removeMember` переезжают вместе, их взаимный порядок прежний); число запросов не меняется (каждое действие —
  те же чтения и один `batch`; `batch` — один запрос). Текст оператора удаления участника сохраняет подстроку
  `DELETE FROM members WHERE event_id = ? AND user_id = ?` — на неё опирается `beforeWrite` в
  `tests/atomic.test.mjs`.
- **Rationale**: инварианты FR-1801, FR-1805.

## R10. Что остаётся вне построителей

- **Decision**: после правки поиск `DELETE FROM` и `UPDATE … SET <колонка человека>` по `src/` находит, кроме
  построителей и перестройки пар (`applyPairsChange`), только действия над одной сущностью: одно исключение
  (`admin.exclusion.del`), одна закреплённая пара (`admin.fixed.del`), семья (`saveFamily`, `deleteFamily`), снятие
  отметки «удалён» (`clearRemovedStmt`), отправленные сообщения очереди (`flushOutbox`), пары и переписка при
  жеребьёвке и отменах (`runDraw`, `cancelDraw`, `forceCancelDraw`), ответственный за обращение (`take`, `pass`,
  `returnThreadsStmts` — смена ответственного, а не перенос человека). Список — в `quickstart.md`.
- **Rationale**: SC-1806; файл шага говорит о каскадах.
