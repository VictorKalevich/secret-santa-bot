# Data Model: Один список данных события и человека

Схема базы не меняется (схема 11, миграции 0001–0007). Новое — описание схемы в коде: `REGISTRY` в `src/db.js`.
Формат описания и построители — `contracts/data-registry.md`.

## Роли колонок человека

| Роль | Смысл | Уход участника | Перенос |
|---|---|---|---|
| `MEMBER` (участник) | данные человека как участника | по `onLeave` таблицы | переходит |
| `ACTOR` (кто сделал) | ссылка на действовавшего | остаётся | остаётся (решение владельца) |
| `ACTOR_MOVED` (кто сделал, переносится) | текущее состояние обращения | — | переходит (как с 012) |
| `RECIPIENT` (получатель) | получатель сообщения очереди | — | остаётся: сообщение уходит старому аккаунту |
| `SELF` (сам человек) | `users.tg_id` | — | старая запись удаляется последней |
| `NOT_PERSON` (не человек) | похоже по имени, но это не человек | — | — |

Политики переноса:

- `update` — `UPDATE t SET c = новый WHERE c = старый` для каждой переносимой колонки (конфликтов нет: перенос на
  участника той же жеребьёвки запрещён до записи; открытое обращение закрывается до переноса).
- `dedupe` — `UPDATE OR IGNORE` для каждой переносимой колонки, затем удалить строки, где осталась ссылка на старый
  аккаунт (дубли), и — для таблиц с `noSelf` — строки «сам себе».
- `merge` (`members`) — в событиях, где участвуют оба аккаунта: удалить участие нового, в участие старого записать
  письмо и адрес нового, если они не пусты (`personal`, каждый со своим временем изменения); затем все участия старого
  перевести на новый аккаунт одним оператором. Строка участия — старого (его время вступления, порядок в списке).

Личные поля участия (`members.personal`): `wishlist` + `wishlist_updated_at`, `delivery` + `delivery_updated_at`.
Сброс стирает их у оставшегося владельца (`''` и `0`); слияние берёт их у нового аккаунта, если значение не пусто.

## Действия и условия

| Действие | Построитель | Условие у всех операторов | Свои операторы действия (в том же `batch`) | Исход — по |
|---|---|---|---|---|
| Удаление события (`deleteEvent`) | `eventDataDeleteStmts(e)` | событие ещё есть | уведомления участникам, запись в общий журнал — раньше | удалению строки события (последний) |
| Полный сброс (`resetEvent`) | `eventDataDeleteStmts(e, { keepMember: владелец, keepEvent: true })` | нет (`'1'`) | уведомления, параметры события по умолчанию, журнал | — (как сейчас) |
| Удаление участника (`removeMember`) | `memberDataDeleteStmts(e, u)` | версия пар (до жеребьёвки — «не проведена») **и участник ещё в событии** | захват версии и перестройка пар (только версия), затем уведомление, журнал, отметка «удалён» | удалению строки участника (последний) |
| Выход админа (`admin.participate` выкл) | `memberDataDeleteStmts(e, админ)` | **жеребьёвка не проведена** | журнал «не участвует» — первым | записи журнала |
| Перенос (`transferAccount`) | `personTransferStmts(старый, новый, { merge })` | **старая запись ещё есть** | уведомления новому и старому, остальным админам, журнал — раньше | удалению старой записи (последний) |

Жирным — условия, которых не было (дефекты 1–3).

## Что остаётся после действия (проверяет `tests/data-registry.test.mjs`)

| Действие | Остаётся с этим событием / человеком |
|---|---|
| Удаление события | `audit` события; в общем журнале — `event.delete` |
| Сброс | строка события (параметры по умолчанию, новая ссылка), участие владельца с пустыми письмом и адресом, `audit` |
| Удаление участника | в этом событии — `removed_members` (если удалил организатор), `join_requests`, колонки ACTOR и RECIPIENT; другие события не затронуты |
| Перенос | старый аккаунт — только в колонках ACTOR (`audit.actor`, `announcements.author`, `events.created_by`, `families.created_by`, `join_requests.decided_by`, `removed_members.removed_by`, `support_threads.closed_by`) и RECIPIENT (`outbox.chat_id`) |
