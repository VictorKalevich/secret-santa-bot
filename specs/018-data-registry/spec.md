# Feature Specification: Один список данных события и человека

**Feature Branch**: `018-data-registry`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "Один список данных события и человека. Разработчик добавляет таблицу с данными события
или человека и получает упавший тест, пока не опишет её в одном списке; удаление события, полный сброс, удаление
участника, выход админа из участия и перенос участия на новый аккаунт строятся из этого списка. Поведение, тексты и
ответы API не меняются. Исправляются три дефекта одновременных вызовов: выход админа из участия одновременно с
жеребьёвкой больше не оставляет в парах человека, которого нет в событии; двойной перенос участия больше не удаляет
участие нового аккаунта; двойное удаление участника до жеребьёвки даёт одно уведомление и одну запись журнала. Схема
базы не меняется. Основа — `docs/refactoring/step-3-data-registry.md`."

Шаг 3 плана рефакторинга (`docs/refactoring-roadmap.md`). Подробности — `docs/refactoring/step-3-data-registry.md`,
базовые числа — `docs/refactoring/baseline.md` (разделы 3 и 4).

## User Scenarios & Testing *(mandatory)*

Действующие лица — владелец бота и админы (удаляют событие, сбрасывают его, удаляют участника, выключают «Я участвую»,
переносят участие), участники (получают уведомления, теряют или сохраняют свои данные) и разработчик, который добавляет
в базу новые данные. Экраны, тексты, ответы API и записи журнала остаются прежними; меняется то, что происходит при
двух одновременных вызовах, и то, как разработчик узнаёт о забытых данных.

### User Story 1 — Одновременные вызовы больше не портят данные (Priority: P1)

Организаторы работают с двух устройств, сеть повторяет запрос, админ нажимает кнопку одновременно с другим админом или
с расписанием. Сейчас три таких случая портят данные или дублируют сообщения:

1. Админ выключает «Я участвую» в ту же секунду, когда другой организатор проводит жеребьёвку. Если жеребьёвка
   записалась первой, админ уходит из события, а в парах остаётся: его Санта видит «ждём», его подопечный остаётся без
   Санты.
2. Владелец дважды переносит участие на новый аккаунт, который уже участвует в том же событии. Второй вызов удаляет
   участие, только что перенесённое первым, вместе с письмом: было 8 участников — стало 6 вместо 7.
3. Два организатора одновременно удаляют одного участника до жеребьёвки. Удалённый получает два одинаковых сообщения,
   в журнале две записи.

После фичи в каждом случае действие выполняется один раз, а проигравший вызов получает тот отказ, который получил бы,
придя на секунду позже.

**Why this priority**: это единственная часть фичи, которую почувствуют люди, и один из случаев — потеря данных
(письма участника). Принцип «одно действие — один результат» (009) обязателен.

**Independent Test**: три проверки одновременных вызовов с навязанным чередованием (сейчас помечены «будет исправлено
в шаге 3») проходят без пометки.

**Acceptance Scenarios**:

1. **Given** админ участвует в событии до жеребьёвки, **When** он выключает «Я участвую», а жеребьёвка записывается
   между его проверкой и его записью, **Then** админ остаётся участником, пар с людьми вне события нет, админ получает
   отказ «После жеребьёвки так нельзя. Попроси владельца бота вписать тебя.», записи журнала «не участвует» нет.
2. **Given** админ участвует в событии до жеребьёвки, **When** он выключает «Я участвую», а жеребьёвка пытается
   записаться после него, **Then** админ вышел, жеребьёвка просит повторить (как сейчас).
3. **Given** старый и новый аккаунт участвуют в одном событии, у старого есть письмо, **When** владелец дважды
   одновременно переносит участие со старого на новый, **Then** участников стало на одного меньше, участие нового
   аккаунта есть, одно уведомление новому аккаунту, одна запись журнала «перенос», второй вызов получает отказ
   «Старая запись не найдена.».
4. **Given** участник в событии до жеребьёвки, **When** два организатора одновременно удаляют его, **Then** он удалён,
   одно уведомление ему, одна запись журнала «удалён», второй вызов получает отказ «Человек не участвует в этом
   событии.».
5. **Given** любое из пяти действий (удаление события, сброс, удаление участника, выход админа, перенос) выполняется
   один раз без гонки, **When** сравниваются ответ, сообщения и журнал с прежней версией, **Then** они совпадают.

### User Story 2 — Данные события и человека описаны в одном месте (Priority: P1)

Разработчик добавляет новую возможность с новой таблицей или колонкой, где хранится событие или человек (например,
«отметки участника в событии»). Сейчас, чтобы эти данные исчезали вместе с событием, уходили с удалённым участником и
переходили при переносе, нужно поправить пять мест в четырёх файлах; фичи 012 и 014 так и делали, а пропуск одного
места оставляет «осиротевшие» данные человека, который потом вернётся в событие. После фичи список таблиц с событием
и человеком — один; пять действий строятся из него; тест падает, пока новая колонка не описана в списке.

**Why this priority**: обе ошибки User Story 1 — следствие расхождения пяти мест; без одного списка следующая таблица
снова разойдётся. Шаг 4 плана опирается на эти построители.

**Independent Test**: тест схемы зелёный на текущих миграциях и падает, если в тестовой базе добавить колонку
`event_id` (или новую таблицу с `user_id`), не описав её в списке.

**Acceptance Scenarios**:

1. **Given** схема из миграций, **When** запускается тест схемы, **Then** каждая таблица схемы есть в списке, каждая
   колонка события или человека описана, каждая описанная колонка есть в схеме.
2. **Given** в тестовой базе временно добавлена колонка `event_id` в существующую таблицу, **When** запускается
   проверка, **Then** она сообщает об этой колонке.
3. **Given** в тестовой базе временно добавлена новая таблица с колонкой `user_id`, **When** запускается проверка,
   **Then** она сообщает о таблице, которой нет в списке.
4. **Given** в списке описана колонка, которой нет в схеме, **When** запускается проверка, **Then** она сообщает о
   лишней колонке.

---

### User Story 3 — После действия не остаётся чужих строк (Priority: P2)

Владелец удаляет событие или сбрасывает его, организатор удаляет участника, владелец переносит участие. После действия
в базе не остаётся строк с этим событием или человеком, кроме тех, что остаются намеренно: журнал события, отметка
«удалён организатором», прошлые заявки, ссылки «кто сделал» и сообщение в очереди старому аккаунту.

**Why this priority**: это проверка того, что построители из списка делают ровно то, что делали пять мест вручную;
она же поймает таблицу, которую список описал, а действие забыло.

**Independent Test**: новый тест готовит событие со всеми видами данных (участники, письма, адреса, исключения,
закреплённые пары, семья, заявки, удалённый, обращения с перепиской, объявление, жеребьёвка, переписка пары), выполняет
каждое действие и ищет оставшиеся строки по всем колонкам события и человека.

**Acceptance Scenarios**:

1. **Given** событие со всеми видами данных, **When** владелец удаляет его, **Then** строк с этим событием нет нигде,
   кроме журнала события; запись об удалении — в общем журнале.
2. **Given** то же событие, **When** владелец делает полный сброс, **Then** у события остаются: строка события с
   параметрами по умолчанию и новой ссылкой, участие владельца с пустыми письмом и адресом, журнал; больше ничего.
3. **Given** участник со всеми видами данных в событии, **When** организатор удаляет его до жеребьёвки и после неё,
   **Then** в этом событии о нём остаются только отметка «удалён организатором», его прошлые заявки и записи журнала;
   в парах его нет, остальные пары целы.
4. **Given** человек со всеми видами данных в нескольких событиях, **When** владелец переносит его участие на новый
   аккаунт, **Then** старый аккаунт остаётся только в ссылках «кто сделал» (журнал, объявления, создатель события и
   семьи, решение по заявке, кто удалил, кто закрыл обращение) и в очереди сообщений как получатель; записи пользователя
   нет.

### Edge Cases

- Админ выключает «Я участвую», не будучи участником (до жеребьёвки): ответ успешный и запись журнала «не участвует»,
  как сейчас.
- Выход админа из участия до жеребьёвки удаляет его исключения, закреплённые пары и обращения в событии; переписки
  до жеребьёвки не бывает (она есть только у пар) — её удаление ничего не меняет.
- Удаление участника после жеребьёвки: пары перестраиваются как сейчас (минимальная замена), изменившиеся Санты
  получают сообщения, удалённый — уведомление; гонка двух удалений разных людей — второй просит повторить (как сейчас).
- Удаление участника одновременно с жеребьёвкой, жеребьёвка записалась первой — удаление отказывает (как сейчас).
- Два одновременных удаления одного участника после жеребьёвки — одно удаление (как сейчас).
- Перенос, когда новый аккаунт уже участвует в жеребьёвке того же события, — прежний отказ до записи.
- Перенос: если у обоих аккаунтов в одном событии есть участие, остаётся одно — с письмом и адресом нового аккаунта,
  если они не пусты, иначе старого; порядок участника в списке (время вступления) — старого, как сейчас.
- Перенос: дубли исключений и закреплённых пар и пары «сам себе» удаляются; если новый аккаунт уже в семье — остаётся
  его семья; отметки «удалён организатором» переходят, кроме событий, где новый аккаунт теперь участник; открытое
  обращение старого закрывается, если у нового в том же событии уже есть открытое; обращение, где человек стал сам
  себе ответственным, снова ничьё.
- Перенос не меняет получателя сообщений, уже стоящих в очереди старому аккаунту: они уходят старому аккаунту.
- Перенос админа: права администратора у нового аккаунта объединяются; ссылки «кто сделал» остаются на старом
  аккаунте (журнал подписан «кто-то», объявления — «Организатор»), как сейчас.
- Полный сброс: участие владельца остаётся, его письмо и адрес стираются; журнал события остаётся.
- Удаление события: журнал события остаётся, запись об удалении — в общем журнале; второе одновременное удаление —
  отказ «Событие уже удалено.» (как сейчас).
- Колонка `sender` переписки Санты и подопечного хранит роль («santa»/«ward»), а не человека — в списке она отмечена
  как «не человек».

## Requirements *(mandatory)*

### Functional Requirements

**Инварианты (поведение не меняется)**

- **FR-1801**: Ответы API (коды и тексты), тексты сообщений, их получатели и порядок, записи журнала (действие,
  подробности, кто) для удаления события, полного сброса, удаления участника, выхода админа из участия и переноса
  участия — прежние, если вызов не пересекается с другим.
- **FR-1802**: Что каждое из пяти действий делает с каждой таблицей — прежнее (таблица «Что каждое действие делает
  сейчас» в `docs/refactoring/step-3-data-registry.md`): журнал события остаётся при удалении и сбросе; сброс оставляет
  участие владельца и стирает его письмо и адрес; удаление участника перестраивает пары прежним способом и ставит
  отметку «удалён организатором», если удаляет организатор; перенос не трогает ссылки «кто сделал» (кроме
  ответственного за обращение и отправителя сообщения обращения — они переходят, как сейчас) и получателя в очереди.
- **FR-1803**: Перестройка пар после удаления и вписывания, версия пар и захваты жеребьёвки, раскрытия, завершения,
  отмен — без изменений; пары при том же зерне те же (эталон жеребьёвки не пересоздаётся).
- **FR-1804**: Схема базы и миграции не меняются; внешние ключи не добавляются.
- **FR-1805**: Число запросов к базе на действие не растёт, к Telegram — то же (таблица базовых чисел шага 1).

**Один список**

- **FR-1806**: В одном месте описаны все таблицы схемы: для каждой — колонка события (или «через» родительскую
  таблицу), колонки человека с ролью «участник» или «кто сделал», колонки, которые похожи на человека, но им не
  являются, и что с данными таблицы делают удаление события, удаление участника и перенос.
- **FR-1807**: Удаление события, полный сброс, удаление участника, выход админа из участия и перенос участия получают
  операторы записи данных из построителей по этому списку. Отличия действий (оставить участие владельца, оставить строку
  события, условие выполнения) задаются параметрами построителя, а не своими списками таблиц. Каждый построитель
  принимает условие выполнения с параметрами — как постановка сообщения в очередь по условию.
- **FR-1808**: Вне построителей и перестройки пар в коде нет операторов, которые удаляют данные события или человека
  каскадом или переносят человека на другой аккаунт; оставшиеся удаления — отдельные действия над одной сущностью
  (одно исключение, одна закреплённая пара, семья, снятие отметки «удалён», отправленные сообщения очереди, пары при
  жеребьёвке и её отмене) — перечислены поиском.
- **FR-1809**: Тест схемы применяет миграции и сверяет список со схемой в обе стороны: каждая таблица схемы есть в
  списке; каждая колонка с именем события или человека (`event_id`, `user_id`, `tg_id`, `chat_id`, любая
  `…_id`/`…_by` и любое имя колонки человека из списка) описана; каждая описанная колонка существует. Проверка
  «от противного» (временная колонка `event_id`, новая таблица с `user_id`, лишняя колонка в списке) роняет её.

**Три дефекта одновременных вызовов**

- **FR-1810**: Выход админа из участия записывает изменения только при условии «жеребьёвка не проведена», проверенном в
  момент записи. Если условие не выполнилось — ничего не меняется и не пишется, ответ — тот же отказ, что при проверке
  до записи: «После жеребьёвки так нельзя. Попроси владельца бота вписать тебя.»
- **FR-1811**: Все операторы переноса участия выполняются только при условии «старая запись ещё существует»; удаление
  старой записи — последним. Проигравший из двух одновременных переносов ничего не меняет и не рассылает и получает
  отказ «Старая запись не найдена.»
- **FR-1812**: При удалении участника уведомление удалённому, запись журнала, отметка «удалён организатором» и удаление
  его данных выполняются, только если он ещё участник события в момент записи, и стоят раньше удаления строки
  участника. Второй из двух одновременных вызовов ничего не меняет и получает отказ «Человек не участвует в этом
  событии.» (до жеребьёвки) или прежний отказ (после неё).

**Проверки и документы**

- **FR-1813**: Три проверки одновременных вызовов с пометкой «шаг 3» проходят без пометки; две пометки «шаг 5» остаются.
- **FR-1814**: Новый тест: после удаления события, сброса, удаления участника (до и после жеребьёвки) и переноса в базе
  нет строк с этим событием или человеком, кроме перечисленных в FR-1802 и User Story 3.
- **FR-1815**: `CLAUDE.md` (таблица фич, структура `src/db.js`, жёсткое правило о новых данных), план рефакторинга
  (статус шага 3), `baseline.md` (раздел 1 — число тестов; раздел 4 — три случая теперь «один результат»),
  спецификации затронутых фич (004, 005, 010, 012, 014 — где описан каскад) и память проекта обновлены. README не
  меняется, если не меняются установка, команды и роли.

### Key Entities

- **Список данных события и человека** — для каждой таблицы схемы: колонка события или родительская таблица; колонки
  человека и их роль («участник» — данные человека как участника; «кто сделал» — ссылка на того, кто действовал);
  колонки, похожие на человека, но не являющиеся им; что делают с таблицей удаление события, уход участника, перенос.
- **Построитель операторов** — по списку и параметрам действия выдаёт операторы записи с общим условием выполнения:
  «удалить данные события», «удалить данные участника в событии», «перенести человека на другой аккаунт».
- **Условие выполнения** — проверка в момент записи, при которой выполняются все операторы действия (событие ещё есть,
  жеребьёвка не проведена, участник ещё в событии, старая запись ещё есть); строка, по которой действие определяет
  исход, удаляется последней.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1801**: 3 из 3 известных дефектов одновременных вызовов шага 3 исправлены: проверки без пометки зелёные;

## Assumptions

- Под «таблицами списка» в критерии «нет `DELETE FROM` вне построителей» понимаются каскады данных события и человека.
  Удаления одной сущности (одно исключение или закреплённая пара по кнопке, семья, снятие отметки «удалён» при
  возвращении, отправленные сообщения очереди, пары и переписка при жеребьёвке и её отменах) — сами действия, а не
  каскады; они остаются на местах и перечисляются в `quickstart.md`.
- В список входят все 17 таблиц схемы — даже `settings`, где колонок события и человека нет: человек там хранится
  значением `owner_id`. Это отмечено в списке; построители его не трогают (запись владельца не переносится, на аккаунт
  владельца перенос запрещён).
- `support_threads.assignee` и `support_messages.sender` — ссылки «кто сделал», но перенос их переносит (так сейчас, это
  текущее состояние обращения, а не история). Остальные ссылки «кто сделал» — `audit.actor`, `announcements.author`,
  `events.created_by`, `families.created_by`, `join_requests.decided_by`, `removed_members.removed_by`,
  `support_threads.closed_by` — не переносятся; менять это — решение владельца.
- Дефект 3 исправляется полнее, чем требует файл шага: под условием «участник ещё в событии» стоят не только
  уведомление и журнал, но и отметка «удалён организатором» и удаление данных. Без этого второй вызов переписывал бы
  отметке время и автора удаления. Ответы и сообщения — те же.
- Выход админа из участия удаляет и его переписку в событии: до жеребьёвки её не бывает, удаление ничего не меняет, а
  действие использует тот же построитель, что и удаление участника.
- Перенос: оставшиеся участия старого аккаунта переносятся одним оператором (а не по одному на событие), права админа
  объединяются по текущим значениям в базе; результат без гонки тот же.
- Захваты не добавляются в сброс, объявления, напоминания и роли (решения владельца); двойной сброс по-прежнему даёт
  два уведомления.
- Порядок проверок в API (права, «событие завершено», подтверждение словом) не меняется — это шаг 4.
- README не меняется: установка, настройка, секреты, команды, роли и использование те же. Задача на README в
  `tasks.md` — проверка этого.
- Тайна (принцип I) не затрагивается: построители не читают и не отдают пар, перенос на аккаунт админа запрещён до
  записи, как сейчас. Права (принцип VII) — без изменений.
