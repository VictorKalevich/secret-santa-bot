# Research: 010 — права владельца

## R1. Ключ `/setup` и одноразовая ссылка владельца

**Decision**:
- `GET /setup` всегда показывает только форму (поле пароля + кнопка), ключ из адреса игнорируется.
- `POST /setup` читает ключ из тела формы (`application/x-www-form-urlencoded`). Сравнение — через HMAC обеих строк
  (`derivedSecret(env, 'setup-key:' + x)`), чтобы не зависеть от длины совпавшего префикса.
- Отметка «ссылка использована» — `settings.owner_link_used = derivedSecret(env, 'owner-used:' + ADMIN_SECRET, 24)`.
  Пока она равна значению для текущего секрета — `/setup` (POST с верным ключом) и ссылка владельца заблокированы.
  Смена `ADMIN_SECRET` меняет и ожидаемое значение, и сам код ссылки — блокировка снимается автоматически, старая ссылка
  перестаёт совпадать.
- Захват ссылки атомарный: один оператор
  `INSERT INTO settings (key, value) VALUES ('owner_link_used', ?) ON CONFLICT(key) DO UPDATE SET value = excluded.value
  WHERE settings.value != excluded.value` — изменил строку только первый переход; остальные получают «уже использована».
- Заголовки страницы: `cache-control: no-store`, `referrer-policy: no-referrer` (+ `<meta name="referrer">`),
  `content-security-policy: frame-ancestors 'none'`, `x-robots-tag: noindex`.

**Rationale**: ключ не попадает в историю браузера, журналы прокси и `Referer`; ссылка владельца — одноразовый «ключ
от всех пар», поэтому повторно не срабатывает. Отметка — производная от секрета, а не флаг: не нужно отдельное
«разблокировать», не нужна миграция (таблица `settings` — ключ/значение).

**Alternatives considered**:
- Флаг `owner_link_used = 1` + ручной сброс — нужна отдельная команда, легко забыть; отвергнуто.
- Блокировать `/setup` сразу после первой настройки (до перехода по ссылке) — тогда закрытая вкладка без перехода
  потребовала бы смены секрета; отвергнуто (FR-1006).
- Хранить в базе сам код ссылки — по базе можно было бы восстановить ссылку; храним производную от другой метки.

## R2. Перенос участия — только владелец

**Decision**: `admin.transfer` → `if (!isOwner) return ownerOnly('Переносить участие на новый аккаунт')`; в приложении
кнопка «Перенести» только у владельца. Прежние запреты (на аккаунт админа/владельца, запись владельца) остаются.

**Rationale**: перенос на свой второй (не-админский) аккаунт открывал админу чужие пары. Владелец пары и так может
открыть в служебном просмотре — для него это не обход.

## R3. Служебный просмотр (`src/vault.js`)

**Decision**: два действия, только владелец (`403` остальным), разрешены и в завершённых эвентах:
- `admin.vault.person {event, id}` — подопечный и Санта (id + имя), «в жеребьёвке ли», письмо, адрес (если
  `delivery_on`), переписка с Сантой и с подопечным (последние 200 сообщений каждой, с датами и стороной-отправителем).
- `admin.vault.pairs {event}` — все пары «Санта → подопечный» (имена и id).
- Каждый вызов пишет запись журнала эвента (`vault.person` — имя участника, `vault.pairs` — число пар) до ответа;
  если запись не удалась, данные не отдаются.
- Никаких `UPDATE` статусов: `seen_text`, `read_at`, `notified_at` не трогаются.
- В приложении: раздел «🔐 Служебный просмотр» внизу панели эвента (только владелец) → ввод «ОТКРЫТЬ» → полноэкранный
  лист: выбор участника → карточка; кнопка «Показать все пары» с подтверждением. Если владелец участник — до ввода
  предупреждение. Слово проверяется в приложении (как сценарий входа), API защищён ролью.

**Rationale**: просмотр «по одному участнику» по умолчанию уменьшает случайное знание пар (в том числе своего Санты);
журнал без пар делает каждое открытие видимым всем админам. Отдельный модуль — единственная точка, где пары читаются не
для Санты.

**Alternatives considered**: требовать слово в каждом API-запросе — не добавляет защиты (запрос делает сам владелец);
рассылать админам уведомления — отклонено владельцем проекта (ответ 1-б).

## R4. Освобождения владельца от «анти-вычислительных» ограничений

**Decision**: для владельца не действуют: заморозка исключений после жеребьёвки (`admin.exclusion.*`), заморозка состава
семей при идущей жеребьёвке (`saveFamily`/`deleteFamily` получают `{ owner: true }`), запрет вписать себя
(`admin.insert`). «Я участвую» после жеребьёвки запрещено и владельцу (целостность пар, не тайна). В приложении
соответствующие элементы владельцу доступны.

**Rationale**: эти ограничения существуют только чтобы админ не вычислил пары; владелец может открыть пары напрямую.

## R5. Автотест «владелец ⊇ админ» (FR-1007)

**Decision**: e2e-тест читает `src/api.js`, собирает все `case 'admin.…'`, создаёт отдельный эвент и вызывает каждое
действие от владельца с минимальным телом (`{ event }`); ни один ответ не должен быть `403`. Порядок — как в исходнике
(завершение и удаление идут последними и без слова подтверждения не выполняются).

**Rationale**: новое действие админа автоматически попадает в проверку — правило VII проверяется без ручного списка.

## R6. Закрытая регистрация и семьи в жеребьёвке

**Decision**:
- `decideRequest(approve)` при `registration_open = 0` → отказ «Регистрация в эвент «…» закрыта — открой её, чтобы
  принять заявку.»; условие повторено в захвате (`UPDATE join_requests … AND EXISTS(events … registration_open = 1 AND
  status = 'active')`). Отклонить можно всегда.
- `inviteFromEvent` при закрытой регистрации → «Регистрация закрыта — открой её, чтобы приглашать.», без рассылки.
- Жеребьёвка: снимок семей участников (`count:SUM(user_id*family_id):SUM(family_id)` по `family_members` зарегистрированных
  участников эвента) — третий компонент снимка; в условии захвата сравнивается, только если `families_on = 1`.
  Сообщение при несовпадении снимка — «Участники, исключения или семьи изменились во время жеребьёвки — попробуй ещё раз.»
  Автожеребьёвка уже сообщает админам текст ошибки (007).

**Rationale**: «закрыто — значит никто» одним переключателем; жеребьёвка не записывает пары по устаревшим правилам семей.

## R7. Возврат удалённых

**Decision**:
- Миграция `0005`: `events.rejoin INTEGER NOT NULL DEFAULT 1`; таблица `removed_members(event_id, user_id, removed_by,
  removed_at, PRIMARY KEY(event_id, user_id))`.
- Отметку пишет только `admin.remove` (в batch удаления, по тому же условию версии пар). «Я участвую» (выкл.), сброс
  (стирает отметки эвента), перенос (переносит отметки на новый аккаунт) — не удаление.
- Отметка снимается при любом вступлении (ссылка, ввод имени, принятая заявка, «Я участвую») и действием
  `admin.removed.allow` (журнал `member.allow`).
- При `rejoin = 0`: `joinByInvite` → `'removed'` раньше заявки; бот до ввода имени не добавляет человека и отвечает
  «Организатор удалил тебя из эвента «…» — вернуться по ссылке нельзя. Если это ошибка — напиши ему.»; админам ничего;
  `inviteFromEvent` пропускает отмеченных.
- `admin.state` → `removed: [{ id, name, removed_at }]`, `settings.rejoin`. Приложение показывает список при `rejoin = 0`.
- Эвент по образцу копирует `rejoin`; полный сброс возвращает `rejoin = 1` и стирает отметки; удаление эвента стирает.

**Alternatives considered**: триггер SQLite «вставка в members снимает отметку» — меньше кода, но поведение спрятано в
схеме; явные операторы в 4 местах вступления понятнее.

## R8. Атомарное удаление эвента

**Decision**: batch: уведомления участникам и запись журнала — по условию `EXISTS (SELECT 1 FROM events WHERE id = ?)`,
затем удаление дочерних строк, последним — `DELETE FROM events`. Его `meta.changes = 0` → «Эвент уже удалён.». Batch D1 —
одна транзакция, а транзакции записи выполняются по очереди: второй одновременный batch видит эвент уже удалённым.

**Rationale**: без токенов и новых полей; второй запрос ничего не рассылает и не пишет в журнал.
