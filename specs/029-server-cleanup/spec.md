## User Scenarios & Testing *(mandatory)*

Действующие лица — участники, админы и владелец бота (для них не меняется ничего) и разработчик, который добавляет
параметр события, команду бота или отказ.

### User Story 1 — Новый параметр события нельзя забыть в сбросе (Priority: P1)

Сейчас параметр события описан в нескольких местах: значения по умолчанию — в создании события и ещё раз в полном
сбросе, допустимые к записи поля — отдельным перечнем, правила сохранения (предел длины, дата, флажок, «только до
жеребьёвки») — отдельными строками. Разработчик добавляет параметр и забывает сброс: «Полный сброс» молча оставляет
прежнее значение, и ни один тест этого не замечает. После фичи параметр описывается один раз, а создание, сброс и
сохранение строятся из этого описания.

**Why this priority**: единственное из трёх мест, где расхождение даёт настоящую ошибку для людей (событие «сброшено»,
а правило осталось), а не только неудобство чтения.

**Independent Test**: проверка «каждая колонка события описана — как параметр или как служебная»; проверка «после
полного сброса каждый параметр равен значению по умолчанию»; проверка «событие по образцу получает ровно те параметры,
которые копируются».

**Acceptance Scenarios**:

1. **Given** событие, у которого каждый параметр отличается от значения по умолчанию, **When** владелец делает полный
   сброс, **Then** каждый параметр равен значению по умолчанию, название прежнее.
2. **Given** событие-образец с изменёнными параметрами и датами, **When** админ создаёт событие по образцу, **Then** в
   новом — бюджет, место, заметки и правила образца; даты вручения, срока письма и автожеребьёвки пустые.
3. **Given** в схеме появилась колонка события, не описанная ни как параметр, ни как служебная, **When** идут быстрые
   тесты, **Then** тест падает и называет колонку.
4. **Given** значение по умолчанию в описании параметра расходится со схемой базы, **When** идут быстрые тесты,
   **Then** тест падает и называет параметр.
5. **Given** любое сохранение параметров (в том числе отказы «после жеребьёвки не изменить»), **When** оно выполняется
   после фичи, **Then** ответ, записанные значения и запись журнала — те же, что до неё.

### User Story 2 — Команду бота видно целиком (Priority: P2)

Обработка сообщения боту — одна функция на двести строк: ссылка владельца, пригласительная ссылка, ввод имени, ответ в
переписку и ответ в обращение идут подряд и делят общие переменные. Нажатия кнопок — вторая такая функция. Запросы к
базе написаны прямо в ней, хотя во всём остальном коде они лежат в модулях. Правило «кто может ответить в обращение»
записано трижды — в боте, в API и в ответе экрана обращения. После фичи у каждой команды и каждого вида кнопки свой
обработчик, запросов в файле бота нет, правило одно.

**Why this priority**: бот — единственный серверный модуль, не приведённый к общему виду в 019; правка одной команды
требует читать все. Людям это не видно.

**Independent Test**: сквозной сценарий и быстрые тесты бота зелёные без правок ожиданий; статическая проверка: в файле
бота нет запросов к базе.

**Acceptance Scenarios**:

1. **Given** любой сценарий чата из сквозного теста (ссылка владельца, приглашение, имя, заявка, ответ в переписку и в
   обращение, кнопки), **When** он выполняется после фичи, **Then** сообщения бота и ответы на нажатия — прежние.
2. **Given** обращение: закрытое, своё, взятое другим админом, в событии, завершённом больше недели назад, **When**
   админ отвечает из бота, из приложения или открывает экран обращения, **Then** отказ и признак «можно писать» — те
   же, что до фичи, во всех трёх местах.
3. **Given** в файл бота добавлен запрос к базе, **When** идут быстрые тесты, **Then** тест падает.

---

### User Story 3 — Отказ записывается одним способом (Priority: P3)

Отказ модуля «не получилось, вот почему» записан литералом около восьмидесяти раз, а в трёх модулях — своими
помощниками с разными именами. После фичи помощник один.

**Why this priority**: чистая единообразность; ошибок не даёт.

**Independent Test**: эталон отказов (1125 ответов) и остальные быстрые тесты зелёные; статическая проверка: в модулях
нет литерала отказа.

**Acceptance Scenarios**:

1. **Given** любой отказ API или бота, **When** он возвращается после фичи, **Then** код и текст — прежние.
2. **Given** в модуль добавлен литерал отказа, **When** идут быстрые тесты, **Then** тест падает и называет файл и
   строку.

---

### Edge Cases

- Событие по образцу, у которого параметр хранит пустое значение там, где умолчание непустое (старые события до
  появления параметра): берётся значение образца, как сейчас; для отсутствующего значения — умолчание.
- Сохранение параметров с несколькими причинами отказа сразу (плохое название, дата автожеребьёвки и правило семей
  после жеребьёвки): возвращается та же причина, что сейчас (порядок проверок прежний).
- Параметры со своим действием (кольцевая, «не повторять пары») общим сохранением не меняются — как сейчас.
- Обращение, взятое другим админом, в событии, завершённом больше недели назад: бот и приложение сейчас называют разные
  причины (порядок проверок разный) — так и остаётся; общим становится само правило, а не порядок текстов.
- Отказы с добавочными признаками (например, «пара изменилась») сохраняют их.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-2901**: Параметры события описаны одним списком: имя, вид (текст с пределом длины, дата, флажок), значение по
  умолчанию, копируется ли из образца, меняется ли только до жеребьёвки (с текстом отказа), есть ли у параметра своё
  действие.
- **FR-2902**: Создание события, полный сброс, сохранение параметров и перечень полей, допустимых к записи, строятся из
  этого списка; значения по умолчанию нигде не повторены.
- **FR-2903**: Тест сверяет список со схемой базы в обе стороны: каждая колонка события — параметр или служебная; у
  каждого параметра значение по умолчанию совпадает со схемой. У проверки есть случай «от противного».
- **FR-2904**: Тесты проверяют поведение: полный сброс возвращает все параметры к умолчаниям; событие по образцу
  получает копируемые параметры и не получает остальные; панель организатора отдаёт каждый параметр.
- **FR-2905**: У каждой команды бота (ссылка владельца, пригласительная ссылка, ввод имени, отмена, ответ в переписку,
  ответ в обращение) и у каждого вида кнопки (ответить в переписку, обращения, заявка, уведомления) — свой обработчик.
- **FR-2906**: В файле бота нет запросов к базе: чтения — функциями модулей. Проверяется тестом.
- **FR-2907**: Условия «обращение закрыто / своё / ведёт другой / событие только для чтения» вычисляются одной функцией;
  ею пользуются бот, ответ организатора в API и признак «можно писать» экрана обращения. Тексты и порядок отказов в
  каждом месте — прежние.
- **FR-2908**: Отказ модуля создаётся одним общим помощником; литералов отказа и локальных помощников в модулях нет.
  Проверяется тестом (с «от противного»).
- **FR-2909**: Поведение не меняется: ответы API (код, текст, данные), сообщения и кнопки бота, записи журнала, схема
  базы, тексты. Эталон отказов и эталон жеребьёвки не пересоздаются.
- **FR-2910**: Запросов к базе на действие — не больше прежнего, к Telegram — столько же (таблица базовых чисел
  `queries` без правок в большую сторону).
- **FR-2911**: Приложение (`src/app/`), дизайн-система и `docs/api.md` не меняются; `CLAUDE.md` описывает новое
  устройство.

### Key Entities

- **Параметр события**: настройка, которую задаёт организатор (бюджет, место, заметки, даты, правила жеребьёвки и
  набора). У параметра есть значение по умолчанию; часть копируется из образца, часть меняется только до жеребьёвки.
- **Служебное поле события**: состояние, которое меняет сам бот (идёт/завершено, жеребьёвка, раскрытие, регистрация,
  код приглашения, отметки расписания) и неизменяемые сведения (кто и когда создал).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-2901**: Чтобы добавить параметр события, достаточно миграции, одной строки списка и мест, где параметр
  показывается; забытая строка списка или расхождение со схемой останавливают тесты.
- **SC-2902**: Все прежние проверки зелёные без изменения ожиданий: быстрые тесты (237 до фичи) и сквозной сценарий
  (69 шагов).
- **SC-2903**: Самая длинная функция бота — не длиннее 60 строк (сейчас 204 и 107).
- **SC-2904**: Литералов отказа в модулях — 0 (сейчас около 80), помощник — один (сейчас три).
- **SC-2905**: Ни одно действие не делает больше запросов к базе, чем до фичи.

## Assumptions

- Списки полей, которые отдаются участнику и панели (`publicEvent`, настройки `admin.state`), остаются явными: что
  показывать людям — вопрос тайны, а не удобства; тест лишь проверяет, что панель отдаёт каждый параметр.
- Различия в пунктуации одинаковых по смыслу отказов бота и API («…назад — обращения…» и «…назад: обращения…»)
  сохраняются: их выравнивание — изменение текстов, не входит в фичу.
- `src/db.js` не делится: проблемы в нём нет, на него завязаны тесты и документация.
- Часть разбора, касающаяся приложения (деление `renderAdmin`, повторы в шторках и панели), и исправление переключателя
  «Регистрация открыта» — следующая фича, после обсуждения с владельцем.
- Выкат — на усмотрение владельца: поведение не меняется, откат — прежняя версия.
