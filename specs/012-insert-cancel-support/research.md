# Research: 012 — вписывание, принудительная отмена, обращения

## R1. Выбор Санты при вписывании

- **Decision**: `insertIntoAssignment(pairs, n, isAllowed, rng, { ring, rank })` — `rank(santa) → 0 | 1 | null`
  (null — нельзя). Допустимые связки «А → Б» (по исключениям, семьям, кольцевой) группируются по рангу А; выбор —
  случайный внутри лучшей непустой группы. Без `rank` — поведение прежнее (все связки — ранг 0), поэтому удаление и
  старые тесты не меняются. `pairs.js` считает ранг: 0 — `seen_text IS NULL` и в паре нет сообщений; 1 —
  `gift_ready = 0` и `gift_received = 0`; иначе null.
- **Rationale**: чистая функция тестируется в Node (SC-001/SC-002), правила группы — в одном месте.
- **Alternatives**: случайный выбор + повтор при «плохом» Санте — недетерминированно и не гарантирует порядок групп.

## R2. Гонка «Санта открыл подопечного / отметил подарок в ту же секунду»

- **Decision**: захват версии пар при вписывании дополнен условием выбранной группы для пары «А → Б»:
  `EXISTS (SELECT 1 FROM pairs WHERE event_id = ? AND santa = A AND ward = Б AND gift_ready = 0 AND gift_received = 0
  [AND seen_text IS NULL AND NOT EXISTS (сообщения пары)])`. Не выполнилось — ничего не меняется, ответ «Пары изменились
  одновременно с этим действием — попробуй ещё раз.» (как при других гонках пар).
- **Rationale**: «одно действие — один результат» (009); Санта не увидит подопечного, которого у него тут же заберут.
- **Alternatives**: без условия — редкая, но реальная потеря купленного подарка.

## R3. Кто вписывает и что видит админ

- **Decision**: `admin.insert` — только владелец (403 «Вписывать в жеребьёвку после неё может только владелец бота.»);
  проверка «вписать себя» удаляется (владелец может себя). Админ под участником «не в жеребьёвке» видит подсказку
  «Вписать в жеребьёвку может владелец бота». Отказ «Я участвую» после жеребьёвки — «Попроси владельца бота вписать тебя.»
- **Rationale**: решение владельца проекта (вопрос «Кто может вписывать?»); как перенос участия (010).

## R4. Принудительная отмена

- **Decision**: `forceCancelDraw(env, ev, actor)` в `pairs.js`: захват `UPDATE events SET draw_done = 0, draw_at = 0,
  draw_token = <новый>, registration_open = 1, draw_auto_date = '' WHERE id = ? AND draw_done = 1 AND draw_token = ? AND
  revealed = 0 AND status = 'active'`; по условию «токен наш» — `DELETE pairs`, `DELETE messages` эвента, уведомления
  каждому Санте из прежних пар, журнал `draw.cancel.force` («пар удалено: N»). API `admin.draw.cancel.force` — владелец,
  слово «ОТМЕНА» (без слова — 400, чтобы автотест «владелец ⊇ админ» не считал это отказом по правам).
- **Rationale**: тот же шаблон, что `cancelDraw` (007), без условия «никто не открыл»; переписка Сант привязана к парам и
  после отмены бессмысленна. Очередь `outbox` не чистится: уведомления переписки без имён.
- **Alternatives**: давать админам — участвующий админ переигрывал бы жеребьёвку (Assumptions спецификации).

## R5. Хранение обращений

- **Decision**: две таблицы (миграция `0006_support.sql`): `support_threads` (эвент, автор, статус `open|closed`,
  ответственный `assignee` — 0 если ничьё, времена, кто закрыл) с уникальным индексом «одно открытое обращение участника
  в эвенте» и `support_messages` (обращение, отправитель, `from_admin`, текст, время, `read_at`).
- **Rationale**: уникальный частичный индекс сам защищает от двух одновременных «первых» сообщений (`INSERT OR IGNORE`),
  как `join_requests_pending` (008).
- **Alternatives**: хранить в `messages` (переписка Сант) — у неё другие стороны и правила тайны; смешивать нельзя.

## R6. Атомарность действий с обращением

- **Decision**: каждое действие — один batch: первый оператор меняет обращение по условию прежнего состояния (взять —
  `assignee = 0`; передать — `assignee = <прежний>`; закрыть — `status = 'open'`), остальные (уведомления, журнал) — по
  условию `EXISTS (… assignee = ? AND taken_at = ?)` / `closed_at = ? AND closed_by = ?` с временем этого вызова.
  Сообщение участника: `INSERT OR IGNORE` обращения (создаётся, только если открытого нет) → `INSERT` сообщения в открытое
  обращение → рассылка «новое обращение» по условию `created_at = <время вызова>`, иначе — ответственному
  (`assignee = X`) или всем админам без звука (`assignee = 0`).
- **Rationale**: два админа нажали «Взять» одновременно — закрепится за одним, второй получит «уже взял(а)»; повторов
  рассылки нет.

## R7. Видимость

- **Decision**: участник — свои обращения в эвенте целиком (+ имя ответственного). Админ: ничьё (в т.ч. закрытое
  до взятия) — читает; своё — читает и пишет; чужое — только участник, статус, ответственный, даты. Владелец читает
  всё; писать — после передачи себе. Прочитанными сообщения участника помечает только ответственный.
- **Rationale**: решение владельца проекта (вопрос «Кто читает переписку обращения?»).

## R8. Ответ из чата бота

- **Decision**: кнопки уведомлений: участнику — «↩️ Ответить» `sup:u:<эвент>` и «💬 Открыть» (приложение,
  `?event=…&support=my`); админу — «🙋 Взять» `sup:take:<id>` (ничьё), «↩️ Ответить» `sup:a:<id>` и «💬 Открыть»
  (`?event=…&support=<id>`). Режим ответа в `users.pending`: `sup_u:<эвент>:<мс>` / `sup_a:<id>:<мс>`, живёт час,
  сбрасывается любой командой (как `msg_…`, 009). Участник пишет «в эвент» (открытое или новое обращение); админ —
  в обращение: закрыто/передано — не отправляется, бот объясняет.
- **Rationale**: тот же опыт, что в переписке Сант; без миграции (`pending` уже есть).

## R9. Жизненный цикл

- **Decision**: снятие прав админа (`revokeAdmin`) — его открытые обращения становятся ничьими, админам — сообщение с
  кнопкой «Взять», участнику — «снова ждёт ответа»; удаление участника из эвента (`removeMember`, «Я участвую» —
  выкл.) — его обращения в эвенте удаляются; перенос участия — `user_id`, `assignee`, `sender` переходят на новый
  аккаунт (открытое обращение старого закрывается, если у нового уже есть открытое в том же эвенте); сброс и удаление
  эвента — обращения эвента удаляются. Завершённый эвент — писать/брать/передавать/закрывать можно, пока `chatWritable`.
- **Rationale**: те же правила, что для письма и переписки Сант (Конституция: удалённый теряет данные эвента).
- **С 018**: удаление, сброс и перенос обращений строятся из списка `REGISTRY` (`src/db.js`; контракт —
  `specs/018-data-registry/contracts/data-registry.md`), правила те же.
