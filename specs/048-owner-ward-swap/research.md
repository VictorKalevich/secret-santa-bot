# Research: 048. Обмен подопечных после жеребьёвки

## R1. Два действия: проверка и обмен

**Decision**: `admin.draw.swap.check { event, a, b }` → `{ possible, rules: [{ rule, text }], version }` и
`admin.draw.swap { event, a, b, version, agree: [rule…] }` → `{}`. Оба — `role: OWNER`, `event: true`,
`finished: CLOSED`, текст отказа не владельцу — «Менять подопечных после жеребьёвки может только владелец бота.»

**Rationale**: как `admin.draw.check` / `admin.draw` — приложение сначала узнаёт, что произойдёт, и показывает окно или
предупреждение; обмен пересчитывает всё сам и не доверяет клиенту.

**Alternatives**: одно действие с отказом «нужно согласие» и списком правил в отказе — отказ API несёт только `error`
(класс `Refusal`), пришлось бы расширять конвейер; выбор пар на клиенте — клиенту пришлось бы отдать пары.

## R2. Версия пар — против повтора и устаревшего согласия

**Decision**: проверка отдаёт `version` = `events.draw_token` (меняется при каждой жеребьёвке, вписывании, удалении,
отмене и обмене). Обмен с другой версией — отказ «Пары уже изменились — открой обмен заново.»; запись — через
`pairsVersion(db, ev, cond)` с версией из запроса.

**Rationale**: обмен симметричен — повтор того же запроса после успеха вернул бы пары обратно. Версия делает повтор
отказом (FR-13) и заодно ловит «между проверкой и нажатием пары поменялись». Значение — случайная строка, по ней ничего не
вычислить; отдаётся только владельцу.

**Alternatives**: «ожидаемые подопечные» в запросе — клиенту пришлось бы знать пары; метка времени — не уникальна при
нажатиях в одну миллисекунду (020).

## R3. Какие правила проверяются и как

Обмен меняет ровно две связки: `a → w(b)` и `b → w(a)` (w — нынешний подопечный). Проверяются только они:

| Код | Нарушение | Когда проверяется |
|---|---|---|
| `self` | `w(a) = b` или `w(b) = a` — кто-то дарил бы сам себе; обмен невозможен (`possible: false`) | всегда, первым; остальные правила тогда не считаются |
| `exclusion` | новая связка есть в исключениях события | всегда |
| `family` | новая связка — внутри семьи (`familyExclusions`) | `families_on` |
| `ring` | новая связка образует взаимную пару: `w(w(b)) = a` или `w(w(a)) = b` | `ring` |
| `fixed` | закреплённая пара (обе стороны в жеребьёвке), которая сейчас действует, после обмена не действует | всегда |
| `history` | новая связка повторяет пару прошлого события (`previousPairs`, как в жеребьёвке) | `avoid_previous` |

Тексты — без имён, в порядке таблицы. Чистая функция `swapRules(pairs, a, b, data, { ring, families, history })` —
тестируется отдельно.

**Rationale**: остальные пары не меняются — их нарушения (если жеребьёвка шла «без истории») не относятся к обмену.
Закреплённую пару проверяем по факту «действовала и перестала», а не по одному «a — закреплённый Санта»: так верно и для
подопечных из закреплённых пар.

**Alternatives**: правило `pairRules` целиком — оно «закреплённая пара важнее запретов» и не различает, какое правило
сработало; тексты были бы общими.

## R4. Согласие на правила

**Decision**: обмен пересчитывает нарушения; если хоть одно не входит в `agree` — отказ «Правила жеребьёвки для этого
обмена изменились — проверь ещё раз.» (без нарушений `agree` не нужен). `self` — отказ «Этих двоих поменять нельзя —
выбери другую пару.» при любом `agree`.

**Rationale**: согласие — на конкретные правила; если между проверкой и нажатием появилось новое нарушение (добавили
исключение — версия пар от этого не меняется), владелец должен увидеть его.

## R5. Запись: тот же путь, что вписывание и удаление

**Decision**: `applyPairsChange(ctx, ev, a, rows, newMap, [A, Б], members, text)` — удаляет две пары и переписку
прежних пар, вставляет две новые с чистыми отметками (маска, посылка, «получил» — по умолчанию схемы), ставит в очередь
сообщения двум Сантам. Текст сообщения — новый параметр (`SWAP_TEXT`), у вписывания и удаления — прежний. Условие версии:
`revealed = 0 AND status = 'active' AND <снимок правил>` (`snapshotGuard` — участники, исключения, семьи, закреплённые
пары, как у жеребьёвки), журнал `draw.swap` «пар изменено: 2» в том же пакете, захват — оператор версии (`claim(version)`).
Проигравшему — отказ по тому, что изменилось: раскрыто, завершено, иначе `PAIRS_RACE`.

**Rationale**: один проверенный путь переписывания пар (003: новая пара — с чистого листа); «захват мой» —
случайная версия (020), поэтому два нажатия в одну миллисекунду дают один обмен. Снимок правил в условии — чтобы обмен
не записался по правилам, которые изменились во время вызова.

**Alternatives**: `UPDATE pairs SET ward = …` двух строк — остались бы отметки «открыл», «получил», маска и посылка
чужой пары, а переписка перешла бы к новому Санте (утечка: Б прочитал бы письма А подопечному 1).

## R6. Ход подарка не проверяется и не показывается

**Decision**: обмен разрешён при любых отметках; предупреждение о последствиях — одинаковое для любого выбора.

**Rationale**: отметка «получил» в панели — у подопечного; предупреждение по выбранным двоим назвало бы, что Санта
получившего — А или Б. Отметки Санты («открыл», «готов», «отправлен») безопасны, но правило «разрешено всегда, текст
одинаковый» проще и честнее, чем разные пути.

## R7. Интерфейс

**Decision**: секция `adminSwap(p)` (05-admin) — только `me.is_owner && s.draw_done && !s.revealed && !done`, перед
`adminVault`. Шторка `openSwapSheet(p)` (06-vault-audit, рядом со служебным просмотром): плашка для владельца-участника,
подсказка, список `ds-card ds-card--flush` из `label.ds-list-item.ds-check` с флажком (участники `in_draw` по алфавиту
`localeCompare('ru')`), строка выбора, кнопка «🔀 Поменять подопечных» (`busy`), место результата. Проверка → нет нарушений
— `confirmBox`; есть — `ds-notice ds-notice--error` с текстом, `ds-details` «Подробнее» (список `ds-bullets`), строкой
последствий, галочкой `ds-check` и кнопкой `ds-btn--danger`; невозможно — плашка с текстом и «Подробнее» без кнопки.
Успех — toast, сброс выбора, тихая перестройка панели (`p.again({ quiet: true })`). Отказ сервера — toast и новая
проверка не запускается сама (владелец нажимает снова).

**Rationale**: флажки — уже есть в дизайн-системе (`ds-check`), понятны на iPhone; две отметки — порядок не важен (обмен
симметричен). Шторка — рядом с кодом служебного просмотра, панель (05-admin) остаётся секциями.

## R8. Компонент «Подробнее»

**Decision**: `<details class="ds-details"><summary class="ds-details__summary">Подробнее</summary>…</details>`: свой
значок «▸» (`::before`, поворот на 90° у `[open]`), системный маркер скрыт (`list-style: none`,
`::-webkit-details-marker`), цвет — от родителя (внутри плашки ошибки — её цвет), вес `semibold`, высота строки не меньше
`--ds-size-control-sm`, отступ содержимого `--ds-space-1-5`. Новых токенов не нужно. Дизайн-система 1.7.0 → 1.8.0.

**Rationale**: родной `<details>` работает в WebKit и Chromium без скрипта, доступен с клавиатуры и экранного диктора;
политика страницы (032) не мешает.
