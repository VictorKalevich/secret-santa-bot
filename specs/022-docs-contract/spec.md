# Feature Specification: Сводный контракт API и правки документов

**Feature Branch**: `022-docs-contract`

**Created**: 2026-11-14

**Status**: Реализовано (2026-11-14; задачи — `tasks.md`, все выполнены)

**Input**: User description: "Сводный контракт API и правки документов. Разработчик открывает один документ и видит
актуальное описание всех 59 действий API: кто может вызвать, поля запроса и ответа, отказы, работа в завершённом
событии; тест падает, если действие есть в коде, но не описано. `CLAUDE.md`, README и Конституция приведены в

Шаг 7 (последний) плана рефакторинга (`docs/refactoring-roadmap.md`). Подробности — `docs/refactoring/step-7-docs-contract.md`,

## User Scenarios & Testing *(mandatory)*

Действующие лица — разработчик (человек или агент в новой сессии, на другой модели), который меняет API, бота или
мини-приложение, и владелец проекта, который по README ставит и сопровождает бота. Участники, админы и владелец бота
не видят никаких изменений: код приложения не меняется.

### User Story 1 — Одно место, где описано всё API (Priority: P1)

Сейчас описание одного действия собирается из многих файлов: `admin.state` — из девяти контрактов фич, `admin.remove` —
из семи; контракт 005, который `CLAUDE.md` называет актуальным, сам отсылает к 001–004; около 17 действий описаны только
в контрактах 001, 002 и 004, `admin.ring` — нигде; часть полей ответов не описана вовсе, тексты отказов в старых
контрактах давно другие. После фичи разработчик открывает один документ и по любому из 59 действий видит: кто может
вызвать, нужно ли событие и что будет в завершённом событии, поля запроса, поля ответа, отказы с кодом и текстом.
Там же — общие правила, которые раньше приходилось восстанавливать по коду: порядок проверок доступа, общие отказы и
коды ответа, коды журнала, формат режима ожидания ответа в чате (`users.pending`), кнопки бота (`callback_data`),
параметры ссылки на мини-приложение.

**Why this priority**: это цель шага. Без сводного документа каждая правка API начинается с археологии по девяти файлам
и кончается расхождением.

**Independent Test**: для выбранных наугад действий (участника, админа, владельца; с событием и без) описание в
документе сверяется с кодом: роль, событие, «в завершённом», поля запроса и ответа, тексты отказов.

**Acceptance Scenarios**:

1. **Given** сводный документ, **When** разработчик ищет любое действие из таблицы действий кода, **Then** находит
   один раздел с ролью, событием, поведением в завершённом событии, полями запроса и ответа и отказами (код и текст).
2. **Given** действие с проверкой, которая зависит от данных (переименовать админа — только владельцу, удалить админа —
   только владельцу, исключения после жеребьёвки — только владельцу, взятое обращение — ответственному и владельцу),
   **When** разработчик читает его раздел, **Then** условие и отказ записаны в нём.
3. **Given** разработчик правит проверки доступа, **When** он открывает документ, **Then** видит порядок проверок
   конвейера и общие отказы (неверная подпись, не зарегистрирован, не админ, нет события, не участник, событие
   завершено, не владелец, нет слова подтверждения, неизвестное действие, не тот метод, ошибка сервера).
4. **Given** разработчик правит бота, **When** он открывает документ, **Then** находит все кнопки бота
   (`callback_data`), все форматы режима ожидания ответа (`users.pending`, включая старый формат, который всегда даёт
   «время ответа истекло») и параметры ссылки на мини-приложение.
5. **Given** разработчик добавляет запись журнала, **When** он открывает документ, **Then** видит все коды журнала:
   кто пишет, к событию или общий, что в подробностях.

### User Story 2 — Тест не даёт документу отстать от кода (Priority: P1)

Документ полезен, пока совпадает с кодом. После фичи быстрые тесты сверяют сводный документ с таблицей действий:
действие в коде без описания или описание без действия в коде роняют тест; так же — если в документе другая роль,
другое «нужно ли событие», другое поведение в завершённом событии или нет текста отказа, слова подтверждения из
таблицы. Коды журнала в документе сверяются с кодами, которые пишет сервер.

**Why this priority**: без проверки документ устареет с первой новой строкой таблицы действий — ровно так устарели
контракты 001–014.

**Independent Test**: «от противного» — временно убранный раздел действия, лишний раздел, неверная роль в сводной
таблице, удалённый из раздела текст отказа и выдуманный код журнала роняют тест.

**Acceptance Scenarios**:

1. **Given** действие есть в таблице действий кода, **When** в документе нет его раздела или строки сводной таблицы,
   **Then** тест падает и называет действие.
2. **Given** в документе раздел или строка действия, которого нет в коде, **When** запускаются быстрые тесты, **Then**
   тест падает и называет действие.
3. **Given** роль, «нужно ли событие» или «в завершённом» в сводной таблице не совпадают с таблицей действий, **When**
   запускаются быстрые тесты, **Then** тест падает.
4. **Given** у действия в коде есть текст отказа «событие завершено», текст отказа не владельцу или слово
   подтверждения, **When** этого текста нет в разделе действия, **Then** тест падает.
5. **Given** сервер пишет код журнала, **When** его нет в документе (или в документе код, которого сервер не пишет),
   **Then** тест падает.

### User Story 3 — `CLAUDE.md`, README и Конституция говорят то же, что код (Priority: P2)

Файл шага перечисляет утверждения, которые расходятся с кодом: в `CLAUDE.md` — указатель на актуальный контракт,
«каждое действие админа и бота пишет журнал», «423 до смены `ADMIN_SECRET`», «схема D1 (сейчас 11)», нет
`npm run test:all`, «полный набор артефактов» фичи; в README — напоминания «за 2 дня до срока письма», описание
`npm test`, нет `npm run test:all`; в Конституции — «письмо до 1000 слов» при лимите 4000 символов; заголовок
сквозного теста «Сценарии 001–008». После фичи каждое такое утверждение записано так, как работает код.

**Why this priority**: агент в новой сессии и владелец проекта верят этим файлам больше, чем коду; неверное
утверждение ведёт к неверной правке или неверной настройке.

**Independent Test**: поиск по `CLAUDE.md`, README, Конституции и заголовку сквозного теста не находит ни одного
утверждения из списка в прежнем виде.

**Acceptance Scenarios**:

1. **Given** владелец проекта читает README о напоминаниях, **When** сверяет с поведением бота, **Then** README говорит
   «за 2 дня, за день и в день срока письма, только до жеребьёвки — тем, у кого оно пустое».
2. **Given** агент читает `CLAUDE.md` о странице `/setup`, **When** ссылка владельца уже использована, **Then**
   `CLAUDE.md` говорит, что блокировку снимает смена `ADMIN_SECRET` или `BOT_TOKEN`.
3. **Given** Конституция, **When** читается принцип II, **Then** лимит письма — 4000 символов (одно сообщение
   Telegram), версия Конституции повышена, отчёт о синхронизации записан.

### User Story 4 — Старые контракты помечены как история (Priority: P3)

Контракты фич 001–014 остаются как история решений, но в начале каждого стоит строка: актуальное описание — в
сводном документе. Разработчик, попавший в старый контракт поиском, сразу видит, куда идти.

**Why this priority**: без пометки старый контракт по-прежнему выглядит актуальным; переписывать их нельзя (история).

**Independent Test**: у каждого файла в `specs/001…014/*/contracts/` первая содержательная строка — указатель на сводный
документ; остальной текст файлов не изменился (`git diff` — только добавленные строки в начале).

**Acceptance Scenarios**:

1. **Given** любой контракт фич 001–014, **When** разработчик его открывает, **Then** первым видит указатель на
   сводный документ.
2. **Given** `git diff` по старым контрактам, **When** он просмотрен, **Then** в каждом файле только добавленный
   указатель, без правок прежнего текста.

### Edge Cases

- **Неизвестное действие** — не строка таблицы: оно проходит тем же путём, что известное (админское — до события и
  «завершено», участника — до участия), и получает 404 «Неизвестное действие». Описывается в разделе порядка проверок,
  тест действий его не считает.
- **`admin.audit`** — единственное действие, которому событие нужно, только если передано: без поля — общий журнал,
  с полем — журнал события (несуществующее — 404).
- **Разрешено в завершённом ради своей проверки**: `delivery.save` («адрес не нужен» раньше «завершено»), переписка и
  обращения (7 суток после завершения), `admin.event.invite_from` («Выбери другое событие.» раньше «приглашать нельзя»).
  В сводной таблице у них не «да», а своё значение; тест считает его «разрешено конвейером».
- **Владелец проверяется после «событие завершено»**: админ на завершённом событии получает 400, а не 403. Порядок
  записывается как есть.
- **Расхождения, похожие на ошибку кода** (служебный просмотр не требует слова «ОТКРЫТЬ» в API, `admin.rename` не пишет
  журнал), не исправляются: документ описывает код, а новое — в раздел «Решения владельца» плана рефакторинга.
- **Слова.** Тест слов проверяет только `src/`; сводный документ пишется для разработчика, но для единообразия в нём
  «событие», а не «эвент» (кроме имён в коде, например `event_id`).
- **Номера строк в файле шага** верны для коммита `24b85d3`; шаги 3–6 их сдвинули — расхождения ищутся по тексту.
  Часть пунктов уже закрыта предыдущими шагами (версия Node в README, «слова» в описании `npm test`) — проверяется,
  не правится повторно.

## Requirements *(mandatory)*

### Functional Requirements

**Инварианты (поведение не меняется)**

- **FR-2201**: Код Worker и мини-приложения (`src/`), схема базы, миграции, тексты для людей, ответы API — не меняются;
  быстрые и сквозные тесты проходят без правки ожиданий.
- **FR-2202**: Старые спецификации и контракты не переписываются: в контракты 001–014 добавляется только указатель в
  начале.
- **FR-2203**: Найденное расхождение, которое выглядит ошибкой кода, не исправляется: оно записывается в «Решения
  владельца» плана рефакторинга.

**Сводный документ**

- **FR-2204**: Один документ описывает все 59 действий API; для каждого — кто может вызвать (включая условия, которые
  зависят от данных), нужно ли событие, поведение в завершённом событии, поля запроса, поля ответа, отказы с кодом и
  текстом. Источник — код, а не старые контракты.
- **FR-2205**: В документе есть сводная таблица всех действий (действие, кто, событие, в завершённом) — машиночитаемая
  для теста.
- **FR-2206**: Отдельные разделы: формат запроса и ответа, порядок проверок доступа и общие отказы с кодами (включая
  401, 403, 404, 405, 500), коды журнала (кто пишет, к событию или общий, подробности), формат `users.pending`, кнопки
  бота (`callback_data`), параметры ссылки на мини-приложение.
- **FR-2207**: В документе закрыты расхождения «контракт ↔ код» из файла шага: кольцевую меняет `admin.ring`, а не
  `admin.game`; описаны поля `admin.transfer.events`, `admin.event.delete.notified`, `chat.get.writable`,
  `admin.state.me_member`, `admin.state.other_events`, `admin.state.removed[].username`; у `admin.state.settings` нет
  `owner_name` и `has_history` (`owner_name` — в `admin.users`); есть коды 405, 404 «Событие не найдено.», 500;
  коды журнала `draw.cancel.force`, `support.*`; формат режима ответа в переписку; тексты отказов — нынешние.
- **FR-2208**: `CLAUDE.md` указывает на сводный документ как на актуальное описание API (вместо цепочки контрактов
  005–014).

**Тест**

- **FR-2209**: Быстрый тест сверяет документ с таблицей действий кода в обе стороны: множество разделов действий и
  множество строк сводной таблицы равны множеству действий кода.
- **FR-2210**: Тот же тест сверяет строку сводной таблицы с полями строки таблицы действий (роль, событие, «в
  завершённом») и проверяет, что раздел действия содержит текст отказа «завершено», текст отказа не владельцу и слово
  подтверждения с текстом отказа, если они есть в строке таблицы.
- **FR-2211**: Тест сверяет коды журнала документа с кодами, которые пишет серверный код, в обе стороны.
- **FR-2212**: Новый тестовый файл включён в `npm test`; «от противного» проверено, что он падает на каждом виде
  расхождения из истории 2.

**Документы**

- **FR-2213**: `CLAUDE.md`: указатель на сводный документ; журнал — как есть (какие действия админа и бота журнал не
  пишут); блокировку `/setup` снимает смена `ADMIN_SECRET` или `BOT_TOKEN` (и отметка «ссылка использована» считается
  от обоих); миграции — версия схемы 11 и 7 файлов; в командах `npm run test:all`; артефакты фичи — «по
  необходимости»; таблица фич — строка 022.
- **FR-2214**: README: напоминания о письме — за 2 дня, за день и в день срока, только до жеребьёвки; описание
  `npm test` и `npm run test:all`; указатель на сводный документ в разделе для разработки.
- **FR-2215**: Конституция: принцип II согласован с лимитом письма в коде (4000 символов); прочие утверждения
  Конституции, расходящиеся с кодом (выдача ссылки владельца, проверки перед коммитом, список хранимых данных), —
  уточнены; новая версия по SemVer и отчёт о синхронизации вверху файла.
- **FR-2216**: Заголовок сквозного теста называет его нынешние сценарии.
- **FR-2217**: План рефакторинга (статус шага 7, новые «Решения владельца», если найдены), `baseline.md` (число тестов),
  память проекта — обновлены.

### Key Entities

- **Сводный документ API** — описание действий (разделы по одному на действие и сводная таблица) и общих правил.
- **Таблица действий** — `ACTIONS` в коде: источник истины для имён, ролей, события, «в завершённом», отказов
  владельца и слов подтверждения.
- **Код журнала** — строка `audit.action`: кто пишет (действие API, бот, cron), к событию или общий, подробности.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-2201**: Сводный документ описывает 59 действий из 59; тест соответствия зелёный.
- **SC-2202**: Проверки «от противного» роняют тест соответствия в 6 случаях из 6: нет раздела действия, лишний раздел,
  неверная роль в сводной таблице, неверное «в завершённом», убран текст отказа не владельцу, лишний код журнала.
- **SC-2203**: Поиск по `CLAUDE.md`, README, Конституции и `tests/e2e.test.mjs` не находит ни одного утверждения из
  пунктов 4–7 файла шага в прежнем виде.
- **SC-2204**: Конституция — новая версия, отчёт о синхронизации; принцип II называет лимит 4000 символов.
- **SC-2205**: `npm test` зелёный: 170 прежних тестов и новые проверки документа; `npm run test:e2e` зелёный;
  `git diff main -- src/ migrations/` пуст.
- **SC-2206**: У 16 файлов контрактов фич 001–014 — указатель на сводный документ, других правок в них нет.

## Assumptions

- Место сводного документа — `docs/api.md` (не папка фичи): папки `specs/NNN-…` — история фич, а сводный документ
  живёт дольше любой фичи. Контракт самой фичи (`specs/022-docs-contract/contracts/`) описывает формат документа и
  правила теста. Решение — в `research.md`.
- Тест сверяет документ со строками таблицы действий, а не с ответами Worker: ответы уже сверяют эталон отказов
  (`tests/fixtures/api-refusals.json`) и тесты прав; полный разбор полей ответа тестом не проверяется (поля
  описываются по коду и выборочно сверяются вручную, `quickstart.md`).
- «Каждое действие админа и бота пишет журнал» записывается как есть, без правки кода: перечисляются действия, которые
  журнал не пишут. Писать ли журнал `admin.rename` — уже в «Решениях владельца» плана.
- Конституция правится как PATCH (уточнения, принципы не переопределяются и не добавляются): 2.3.0 → 2.3.1.
- Замер жеребьёвки и число запросов не снимаются отдельно: серверный код не меняется (число запросов проверяет
  `npm test`).
- Уже исправленное предыдущими шагами (версия Node в README; «слова» в описании `npm test`) проверяется и не правится.
